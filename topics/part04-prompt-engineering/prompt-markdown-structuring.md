# プロンプトにおけるMarkdown活用

## これは何か

長いプロンプトを地の文(段落だけの文章)で書くと、AIは「ここは自分への指示なのか」「ここは参考として渡された資料なのか」を読み違えやすい。見出し(`#`)・箇条書き・番号リスト・コードブロック(` ``` `)・`<context>`のようなXMLタグ(HTMLに似た`<タグ名>〜</タグ名>`で囲む記法)でプロンプトを区切ると、AIが「指示」「背景情報」「参考データ」「出力形式」を取り違えにくくなり、出力の精度・再現性が上がる。[プロンプトの基本構成要素](./prompt-basic-structure.md)が「プロンプトに何を書くか」を扱うページだとすれば、本ページは「それをどう区切って書くか」という書き方の技術に絞って扱う。

## 仕組み・背景

なぜMarkdownやタグでの構造化が効くのか、理由は大きく2つある。

1. **学習データの偏り**: 生成AIの学習データにはプログラムのソースコード、GitHubのREADME、技術ドキュメントなど、Markdown・HTML・XMLが大量に含まれる。そのため`#`は見出し、` ``` `はコード、`-`は箇条書き、`<タグ>`は意味のあるまとまりという「型」をモデルは強く学習しており、同じ記法をプロンプト側で使うと、モデルがその型に沿って情報を正しく仕分けしやすくなる。
2. **文書のパース補助になる**: 「以下が指示です」のような自然文の合図は曖昧になりがち(どこまでが「以下」なのか、次の段落は指示の続きか別の情報かが不明瞭)だが、見出しやタグによる区切りは境界が明確で、指示・文脈・データ・出力形式の取り違えを構造的に防げる。

各社の公式ドキュメントでの推奨は少しずつ異なる。

- **Anthropic(Claude)**: 公式のプロンプトエンジニアリングガイドは、指示・背景・例示・入力データが混在する複雑なプロンプトでは**XMLタグ**(`<instructions>`, `<context>`, `<example>`, `<document>`など)を主たる構造化手段として推奨している。タグ名に決まりはないが、同じプロンプト内では一貫した名前を使うこと、階層がある内容(複数の文書など)は`<documents>`の中に`<document index="1">`のように入れ子にすることが挙げられている。Markdownとタグは競合するものではなく、タグでセクションの「役割」を示し、Markdownでそのセクションの「中身」を整形するという併用が想定されている。
- **OpenAI(GPT-4.1以降)**: 公式のGPT-4.1プロンプティングガイドは、プロンプトの冒頭からMarkdownの見出し(`#`〜`####`程度の階層)で大きな区分・小区分を作ること、コードはインラインバッククォートやバッククォート3つのコードブロックで囲むこと、番号付き・箇条書きリストで手順や条件を列挙することを推奨している。
- **Google(Gemini)**: 公式ガイドは、XMLタグまたはMarkdown見出しのどちらかで指示とデータの境界を明確にすることを推奨する一方、**同じプロンプト内でXMLとMarkdownを混在させない**ことを勧めている。統一されていない区切り記法は、かえってモデルの境界認識を妨げるためである。

長文の資料を読み込ませる場合の並び順にも根拠がある。Anthropicの公式ガイドでは、長文データはプロンプトの先頭に、実際の質問・指示は末尾に置くことで、複雑な複数文書の入力を伴うテストにおいて応答品質が最大30%向上したと報告されている。

## 使いどころ・使い分け

| 状況 | 構造化の要否 |
|---|---|
| 一言の質問・雑談・簡単な言い換え依頼 | 不要。地の文で十分。見出しやタグを付けるとかえって冗長になる |
| 「背景」「資料」「指示」「出力形式」など3ブロック以上を1つのプロンプトに詰め込む | 必須に近い。ブロックごとに見出し・タグで分離する |
| 出力のフォーマットを厳密に固定したい(決まった見出し構成、表、JSON等) | 有効。欲しい出力の型そのものをMarkdownで書いて見せる |
| 長文資料(規約・議事録・レポートなど)を読み込ませて分析・要約させる | 有効。資料をタグで囲み、質問は末尾に置く |
| コード生成・技術文書のレビュー | 必須に近い。コードは必ずコードブロックで囲み、言語名を指定する(` ```python `など) |
| Few-shot(複数の例を見せる)で出力トーンを制御したい | 有効。各例を`<example>`タグ等で囲むと、モデルが「これは例であって指示ではない」と区別しやすい |

判断の目安は「プロンプトの中に性質の異なるブロックが3つ以上あるかどうか」。役割・タスク・出力形式程度のシンプルな依頼なら地の文で書き、資料・複数の指示・出力テンプレートが同時に登場するタスクになったら構造化を検討するとよい。

## 実務での使い方

### Before/After例1: 資料・指示・出力形式が混在するケース

**Before(地の文で全部書いてしまう)**

```
うちは中小企業向けの会計クラウドサービスをやっている会社です。先月の解約率が
急上昇していて、以下が解約理由アンケートの自由記述です。マーケ担当と経営陣に
共有するレポートを作ってください。丁寧な文体で、原因・対策の順に書いてください。
「操作が分かりにくい」「サポートの返信が遅い」「価格が上がった」「他社に乗り換えた」…
(以下、自由記述が続く)
```

このままだと、どこまでが「会社の説明」でどこからが「分析対象のデータ」で、どこからが「指示」なのかがモデルにとって曖昧になりやすい。

**After(見出し・タグで分離)**

```
# 役割
あなたはSaaS企業のカスタマーサクセス責任者です。

<context>
中小企業向け会計クラウドサービスを提供している。先月、解約率が急上昇した。
</context>

<data>
[解約理由アンケートの自由記述をここに貼り付け]
</data>

<instructions>
1. 上記データを解約理由ごとに分類し、件数が多い順に並べてください
2. 各理由について、考えられる根本原因を1〜2行で分析してください
3. 対策案をそれぞれ1つずつ提案してください
</instructions>

<output_format>
- マーケティング担当と経営陣向けの丁寧な文体で書いてください
- 「## 現状」「## 原因別の分析」「## 対策案」の見出し構成にしてください
</output_format>
```

タグ・見出しで区切ることで、「会社説明(context)」「分析対象そのもの(data)」「やってほしいこと(instructions)」「見た目の指定(output_format)」がモデルにとって明確に分離される。

### Before/After例2: 出力フォーマットを厳密に指定したいケース

**Before**: 「比較表にしてまとめて」とだけ指示する → 列の数や順番がAIの気分次第でぶれる。

**After**: 欲しい表の骨組みそのものをMarkdownで書いて見せる。

```
以下のMarkdownテーブルの形式で、3つのプランを比較してください。

| 項目 | プランA | プランB | プランC |
|---|---|---|---|
| 月額料金 | | | |
| 主な機能 | | | |
| 向いている企業規模 | | | |
```

「表にして」という指示より、テンプレートそのものを渡す方が列構成のブレがなくなる。

### コピペで使えるテンプレート: XML+Markdown併用の汎用構造

```
# 役割
[例: "10年の実務経験を持つ社内SEです"]

<context>
[背景・前提条件を2〜3行で]
</context>

<documents>
<document index="1">
<source>[ファイル名や資料の出所]</source>
<document_content>
[本文をそのまま貼り付け]
</document_content>
</document>
</documents>

<instructions>
1. [具体的な手順・依頼を番号で]
2. [...]
</instructions>

<output_format>
[欲しい見出し構成やフォーマットをそのまま書く。例: "## 要約" "## 詳細" "## 次のアクション"]
</output_format>

[ここに実際に聞きたい質問・依頼を最後に置く]
```

長文の資料(`<documents>`)を先頭に、実際の質問を一番最後に置いているのがポイント。この並びだけで応答品質が上がりやすい。

### ツール横断の対応付け(2026年7月時点)

| ツール/モデル系統 | 推奨される区切り記法 | 備考 |
|---|---|---|
| Claude(Anthropic) | XMLタグ(`<context>` `<instructions>` `<example>`など) | 公式ガイドが明示的に推奨。タグ名は自由だが一貫させる。Markdownはタグの中身の整形に使う |
| ChatGPT(GPT-4.1以降) | Markdown見出し(`#`〜`####`) | 公式のGPT-4.1プロンプティングガイドが見出しでの階層構造化を推奨。コードは3つのバッククォートで囲む |
| Gemini(Google) | XMLタグ**または**Markdown見出し(どちらか一方に統一) | 混在させると境界認識を妨げるため非推奨とされている |
| Copilot・Dify・社内チャットボット等 | どちらでも動作するが、裏側で使っているモデル(GPT系/Claude系/Gemini系)の流儀に合わせると精度が安定しやすい | プロンプトテンプレートを社内で使い回す場合は、使用モデルを確認してから記法を統一する |

## 注意点・よくある誤解

- **プロンプトの見た目は出力に伝染する**: プロンプトにMarkdown装飾(太字・箇条書き)を多用すると、出力もMarkdownだらけの箇条書きになりやすい。逆に、なめらかな地の文の回答がほしい場合は「Markdownを使うな」と禁止形で書くより、プロンプト自体からMarkdown装飾を減らし、「段落形式のなめらかな文章で書いてください」と肯定形で指示する方が効きやすい。
- **短いタスクへの過剰な構造化は逆効果**: 一言二言の依頼にまでXMLタグや見出しを付けると、かえって冗長になり読みにくくなるだけで精度は上がらない。構造化は「ブロックが複数ある長めのプロンプト」で効果を発揮する技法であり、万能の魔法ではない。
- **記法を途中で混ぜない**: 同じプロンプト内で`<context>`というタグと`# Context`という見出しを両方使うなど、記法を混在させると、モデルが同じ意味の区切りだと認識できないことがある。1つのプロンプトでは記法を統一する。
- **ネストを深くしすぎない**: 見出しをH5・H6まで細分化したり、XMLタグを何重にも入れ子にすると、人間にとっても保守しづらいプロンプトになる。基本は「文書全体を囲むタグ」+「その中の2〜3階層の見出し」で十分なことが多い。
- **見出し名・タグ名は具体的に**: `<context>`や`## 背景`のように内容が想像できる名前を付ける。`<a>`や`## その他`のような曖昧な名前は、区切りとしての効果が薄れる。

## 最初の一歩

直近で使った5行以上の長めのプロンプトを1つ選び、「背景」「資料」「指示」「出力形式」の4ブロックに分けて見出しかXMLタグで区切り直し、同じ依頼を投げ直して結果を比較してみる。
