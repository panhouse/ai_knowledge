# Zero-shot・Few-shot・Chain-of-Thoughtプロンプティングの使い分け

## これは何か

生成AIに指示だけを投げて期待外れの回答が返ってきたとき、多くの人は「もっと詳しく指示を書く」か「例を貼り付ける」かで悩む。この2つの打ち手と、もう1つ「考え方の手順を踏ませる」という打ち手を体系立てたのが、Zero-shot(ゼロショット、例を見せない)・Few-shot(フューショット、少数の例を見せる)・Chain-of-Thought(CoT、思考の連鎖。段階的に考えさせる)の3つのプロンプティング手法である。分類・判定・要約・計算チェックなど、業務でAIに「これでいいか判断して」と頼む場面のほとんどは、この3つのどれかを選ぶか組み合わせる話に集約される。使い分けを知らないと、簡単な作業にまで長い例文を貼り付けて時間を無駄にしたり、逆に複雑な判断をさせるのにヒントなしで一発回答を求めて精度不足を「AIの限界」と誤解したりする。

なお2025年後半以降に主流になった「推論モデル」(内部で自動的に段階的思考を行うモデル。ChatGPTのThinking系、Claudeの拡張思考/Adaptive Thinking、GeminiのThinkingモデルなど)では、CoTの効果の多くがモデル側にすでに組み込まれている。「どのモデルに、どの手法が今も効くか」まで含めて理解しておく必要がある。

## 仕組み・背景

- **Zero-shot(ゼロショット)**: 例を1つも見せず、指示文だけでタスクを実行させる方法。「この問い合わせをカテゴリ分類して」のように、タスク名と出力形式だけを伝える。大規模言語モデルは学習データの中で既に類似タスクを大量に見ているため、指示だけでも一定の精度が出る。
- **Few-shot(フューショット)**: 指示文の中に「入力→望ましい出力」のペアを2〜5個程度含める方法。モデルは推論(学習ではなく、その場でのパターン認識)によって、例のパターンをその後の入力に当てはめる。この現象は文脈内学習(In-Context Learning)と呼ばれ、2020年のGPT-3論文「Language Models are Few-Shot Learners」(Brown et al., OpenAI)で広く知られるようになった。モデルの重み自体は変化しない(ファインチューニングとは別物)点がポイントで、プロンプトに書いた例だけがその場限りの「お手本」として働く。
- **Chain-of-Thought(CoT、思考の連鎖)**: 「ステップバイステップで考えてください」のように、結論を出す前に中間の推論過程を書き出させる方法。2022年のWei et al.論文でFew-shotの例に推論過程を書き加えると精度が上がることが示され、同年のKojima et al.論文では例を使わず「Let's think step by step(段階的に考えてみましょう)」という一文を足すだけでも同様の効果が出ること(Zero-shot CoT)が示された。複雑な計算・多段階の条件判定・論理的な整合性チェックのように「一発で答えを出すと間違えやすいが、途中式を書かせると正答率が上がる」タスクで特に効果が大きい。

**2026年時点の重要な変化: 推論モデルはCoTを内部に持っている。** ChatGPT(GPT-5.5 Thinking等)、Claude(Opus/Sonnet 5系の拡張思考・Adaptive Thinking)、Gemini(Gemini 3のThinkingモード)といった現行の主力モデルは、ユーザーに見えない「思考トークン」を内部で生成し、回答前に自分で下書き・検証・修正を行う。これは自然文で「段階的に考えて」と書くCoTプロンプトの効果を、モデルのアーキテクチャ側で肩代わりしているということであり、こうしたモデルに対して手動でCoTを書いても効果が薄い(場合によっては指示が冗長になるだけ)ことが多い。一方で、レイテンシ・コスト優先の高速モード(ChatGPTの「Instant」、Geminiの`thinking_level: MINIMAL/LOW`、Claudeの思考なしモデルなど)では推論を省略しているため、依然として手動のCoTプロンプトが有効に働く。

## 使いどころ・使い分け

| 手法 | 定義 | 向いているタスク | 弱点・注意点 |
|---|---|---|---|
| **Zero-shot** | 例を見せず指示だけで実行させる | 単純な分類・要約・翻訳・文章の手直しなど、モデルが「見たことのある」定型タスク | 出力フォーマットや判断基準の細かいニュアンスが伝わらず、ブレやすい |
| **Few-shot** | 入力→出力の例を2〜5個程度示す | 社内独自のフォーマット・トーン・分類基準に合わせたい、出力の粒度や語彙を揃えたいタスク | 例の作成に手間がかかる。例が偏っていると誤った規則を学習(過学習)し、例にない切り口の入力に弱くなる |
| **CoT(思考の連鎖)** | 結論の前に段階的な推論過程を書かせる | 多段階の条件判定、計算を伴う概算、契約書条項の該当・非該当判定など「途中で間違えやすい」タスク | 出力が長くなりトークン消費が増える。推論モデルでは重複効果でほぼ意味がない場合が多い |

### 判断フロー(どれを選ぶか)

1. **まずZero-shotで試す。** 指示を明確に書いて(役割・出力形式を指定)一度実行し、精度を確認する。単純作業ならこれで十分なことが多い。
2. **出力の「形」や「トーン」が思った通りにならない → Few-shotを足す。** 望ましい出力例を2〜3個、できれば紛らわしいエッジケースを1つ含めて追加する。
3. **出力の「判断の中身」が間違っている(条件の見落とし・計算ミス)→ CoTを足す。** ただし、使っているモデルが推論モデル(Thinkingモード・拡張思考が有効)なら、まずCoT抜きのZero-shotで試し、それでも精度が足りない場合のみ「判断基準を箇条書きで確認してから結論を出して」のように誘導する方が効率的。
4. **精度がなお足りない → Few-shot + CoTを併用する。** 例そのものに推論過程を書き込む(下記の実例参照)と、Few-shotの「型合わせ」とCoTの「論理チェック」を同時に効かせられる。

## 実務での使い方

以下は、同一の業務タスク「返金依頼メールを社内規定に照らして判定する」で、3手法の違いをそのまま比較できるプロンプト例である。

**前提となる社内規定(すべての例で共通)**

```
【返金規定】
- 購入日から8日以内の申請: 全額返金
- 購入日から9〜30日以内の申請、かつ「未使用」の場合: 50%返金
- 購入日から31日以上経過、または「使用開始済み」の場合: 返金不可
```

### 例1: Zero-shotプロンプト(指示だけ)

```
あなたはカスタマーサポート担当です。以下の返金規定に照らして、
顧客からの返金依頼メールを「全額返金」「50%返金」「返金不可」のいずれかに判定してください。

【返金規定】
- 購入日から8日以内の申請: 全額返金
- 購入日から9〜30日以内の申請、かつ「未使用」の場合: 50%返金
- 購入日から31日以上経過、または「使用開始済み」の場合: 返金不可

【顧客メール】
購入日: 2026年6月20日
返金依頼日: 2026年7月5日
利用状況: 未使用

【出力形式】
判定結果のみを1行で出力してください。
```

*向いている場面*: 件数が多く、規定もシンプルで、担当者が最終チェックする前提の一次仕分け。

### 例2: Few-shotプロンプト(判定例を添える)

```
あなたはカスタマーサポート担当です。以下の返金規定と判定例を参考に、
新しい問い合わせを判定してください。

【返金規定】
- 購入日から8日以内の申請: 全額返金
- 購入日から9〜30日以内の申請、かつ「未使用」の場合: 50%返金
- 購入日から31日以上経過、または「使用開始済み」の場合: 返金不可

【判定例】
入力: 購入日2026/6/1、依頼日2026/6/5、利用状況:未使用
出力: 全額返金

入力: 購入日2026/6/1、依頼日2026/6/20、利用状況:使用開始済み
出力: 返金不可 (未使用条件を満たさないため)

入力: 購入日2026/6/1、依頼日2026/6/25、利用状況:未使用
出力: 50%返金

【新しい問い合わせ】
購入日: 2026年6月20日
返金依頼日: 2026年7月5日
利用状況: 未使用

【出力形式】
「判定結果 (理由を一言)」の形式で1行出力してください。
```

*向いている場面*: 出力フォーマットや「理由の添え方」を社内の書式に揃えたいとき。特に2つ目の例のように、あえて「返金不可になる境界ケース」を混ぜておくと、モデルが安易に全額返金へ倒れるのを防げる。

### 例3: CoTプロンプト(推論を明示させる)

```
あなたはカスタマーサポート担当です。以下の返金規定に照らして、
顧客からの返金依頼メールを判定してください。

【返金規定】
- 購入日から8日以内の申請: 全額返金
- 購入日から9〜30日以内の申請、かつ「未使用」の場合: 50%返金
- 購入日から31日以上経過、または「使用開始済み」の場合: 返金不可

【顧客メール】
購入日: 2026年6月20日
返金依頼日: 2026年7月5日
利用状況: 未使用

【指示】
以下の手順で考えてから結論を出してください。
1. 購入日から返金依頼日までの経過日数を計算する
2. 経過日数がどの区分(8日以内/9〜30日/31日以上)に該当するか特定する
3. 利用状況(未使用/使用開始済み)を確認する
4. 1〜3を踏まえて判定結果を出す

【出力形式】
「思考過程」と「判定結果」を分けて出力してください。
```

*向いている場面*: 日数計算や複数条件の組み合わせなど、一発判定だとモデルが計算を誤りやすいとき。**ただし、ChatGPTのThinkingモード・Claudeの拡張思考・Gemini 3のThinkingモードのような推論モデルを使っている場合、この「手順1〜4」の明示は基本的に不要。** モデルが内部の思考トークンで同じことを自動的に行うため、まずは例1のZero-shotで試し、日付計算のミスが出た場合にだけ「経過日数を先に計算してから判定して」の一文を足す程度で十分なことが多い。

### ツール横断の対応付け(2026年7月時点)

推論(Thinking)機能そのものの有無・呼び出し方はツールによって異なる。CoTを手書きすべきか、モデル任せでよいかはここで判断する。

| ツール | 推論モードの呼び方 | 選び方・設定場所 |
|---|---|---|
| ChatGPT(GPT-5.5系) | Instant(高速・軽い推論) / Thinking(Medium・High・Extra High) | 画面下のモデルピッカーで選択。複雑な依頼はInstantでも自動的にThinkingへ切り替わることがある。API利用時は`reasoning_effort`パラメータ(none/low/medium/high)で指定 |
| Claude(Opus/Sonnet 5系など) | 拡張思考(Extended Thinking)/ Adaptive Thinking | claude.ai では回答欄の「思考」トグルで有効化。最新世代(Opus 4.7以降・Sonnet 5等)は常時オンのAdaptive Thinkingで、API利用時は`effort`パラメータ(low/medium/high/max等)で深さを調整 |
| Gemini(Gemini 3系) | Thinkingモード(`thinking_level`) | アプリでは「Thinking」表示のモデルを選択。API利用時は`thinking_level`を`LOW`/`HIGH`(Proの場合)などで指定。既定値は`HIGH` |
| 旧世代・軽量モデル全般(GPT-4o系、Claude Haiku等の非推論モデル) | 推論機能なし | 手動でのCoTプロンプト(「ステップバイステップで」)が引き続き有効 |

**判断基準**: 使っているのが「Thinking」「拡張思考」を謳うモデルかどうかをまず確認する。謳っていれば手動CoTは基本省略し、精度が出ない箇所だけピンポイントで手順を指定する。謳っていない・速度優先モードを使っている場合は、複雑な判定・計算タスクに手動CoTを積極的に足す。

## 注意点・よくある誤解

- **「思考過程を出力させる」ことと「精度が上がる」ことは別物**: 推論モデルが表示する思考の要約(サマリー)は、実際の内部計算を必ずしも忠実に反映していないという指摘がある。思考過程が表示されていても、それを「検算の証拠」として鵜呑みにしないこと。
- **推論モデルに手動CoTを重ねると、コストと待ち時間だけが増えることがある**: Thinkingモードは内部で既に多段階の推論トークンを消費している。そこに「ステップバイステップで」という指示を重ねても効果が頭打ちになりやすく、逆に出力が冗長になって読みにくくなる場合がある。
- **Few-shotの例は「揃えすぎ」に注意**: 例をすべて同じパターン(例: すべて「全額返金」になる例)にすると、モデルは表面的な共通点を学習してしまい、境界ケースで誤判定しやすくなる。例には必ず結論が割れるケース(却下・要確認など)を混ぜる。
- **例の数は多いほど良いわけではない**: 実務では3〜5個程度で十分な効果が出ることが多く、例を増やしすぎるとプロンプトが長くなりコスト・レイテンシが増える割に精度向上が頭打ちになる。
- **Zero-shotで失敗したら、まず指示の曖昧さを疑う**: 「うまくいかない=CoTが必要」と即断せず、出力形式や判断基準を明確にするだけで解決することも多い(関連: プロンプトの基本構成要素)。

## 最初の一歩

直近でAIに投げた「分類・判定」系の依頼を1つ選び、(1)まずZero-shotのまま結果を確認し、(2)結果がブレる/形式が揃わないならFew-shot例を2つ足し、(3)判断ロジックそのものが間違っているなら「手順を踏んで考えて」と一文だけ加えて、3パターンの出力を見比べてみる。使っているモデルがThinking/拡張思考ありなら、(3)は基本スキップしてよい。
