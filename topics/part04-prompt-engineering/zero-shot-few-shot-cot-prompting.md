# Zero-shot/Few-shot/Chain-of-Thoughtプロンプティング

## これは何か

「これ要約して」と例示ゼロで頼んでも大抵は通じるのに、「この問い合わせを社内ルールに沿って分類して」のような業務特有のタスクだと、AIは的外れなフォーマットや基準で答えを返してくることがある。こうした「効かない」ケースの多くは、**例を見せていない(Few-shot不足)**か、**答えに飛びついて考える過程を省いている(Chain-of-Thought不足)**ことが原因である。Zero-shot・Few-shot・Chain-of-Thought(CoT)は、プロンプトに「例」と「思考の道筋」をどれだけ・どう入れるかを整理した、プロンプト設計の最も基本的な3つの型である。

## 仕組み・背景

3つの手法は難易度順というより、「何を追加するか」の違いで整理すると理解しやすい。

- **Zero-shot(ゼロショット)**: 例を一切示さず、指示文だけでタスクを頼む最も基本的な形。大規模なAIは学習時に膨大なタスクを見ているため、多くの日常的な依頼はZero-shotで十分に通じる。
- **Few-shot(フューショット)**: 「入力例→期待する出力例」のペアを2〜5個程度プロンプトに含める手法。AIはその場で提示された例からパターンを読み取り(これを**インコンテキスト学習**と呼ぶ。追加学習なしにプロンプト内の例だけで振る舞いを調整する仕組み)、出力の形式・トーン・粒度・分類基準をその例に合わせてくる。「言葉で説明しにくいが、見せれば伝わる」タスクに強い。
- **Chain-of-Thought(CoT、思考の連鎖)**: 「ステップごとに考えてから答えてください」のように、最終的な答えを出す前に途中の思考過程を書かせる(あるいは書かせるよう誘導する)手法。2022年にGoogleの研究チームが発表した論文で、計算問題や論理パズルのような複数ステップの推論を要するタスクにおいて、途中経過を書かせるだけで正答率が大きく向上することが示された。人間が難しい問題を紙に途中式を書きながら解くのと同じ発想で、AIも一足飛びに結論を出すより、途中の根拠を言語化させたほうが誤りに気づきやすくなる。

3つは排他的ではなく組み合わせられる。例えば「Few-shotの例の中に、思考過程まで含めた出力例を示す」(Few-shot CoT)や、単に「ステップごとに考えてください」の一文を加えるだけで例は示さない「Zero-shot CoT」もよく使われる。

## 使いどころ・使い分け

| 状況 | 向いている手法 | 理由 |
|---|---|---|
| 定型的な要約・翻訳・文章の手直しなど、一般的なタスク | Zero-shot | AIが素の知識で十分対応できる。まず例なしで試すのが基本 |
| 出力の形式・トーン・分類基準を自社ルールに揃えたい | Few-shot | 「言葉で説明しにくいが例を見せれば伝わる」ものはFew-shotが最も確実 |
| 計算・論理的な判定・複数条件の組み合わせなど、一発で答えを出すとミスが出やすいタスク | Chain-of-Thought | 途中の根拠を書かせることで計算ミス・条件の見落としに気づきやすくなる |
| 出力形式は揺れやすいが、判断ロジックも複雑(例:問い合わせをカテゴリ分けしつつ、優先度の判定理由も示したい) | Few-shot + CoT の併用 | 例で形式を固定し、CoTで判断の質を上げる |
| OpenAI o3・GPT-5.x(Thinking)、Claude(拡張思考)、Gemini(Thinking)のような**推論モデル**を使っている | 基本はZero-shotで、CoTの明示的な指示は入れない | 後述の通り、モデルが内部で自動的に思考過程を生成するため、明示的なCoT指示は効果が薄いか、むしろ性能を下げる場合がある |

判断に迷ったら「まずZero-shotで試す→形式が揃わなければFew-shotを足す→計算や条件判定でミスが出るならCoTを足す」の順に段階的に強化するのが実務的な進め方。

## 実務での使い方

### Zero-shotの例(そのままコピペ可)

```
以下の会議メモを、決定事項・宿題(誰が・いつまでに)・懸念点の3項目に整理してください。
箇条書きで、各項目3行以内にまとめてください。

【会議メモ】
[ここに議事録の文章を貼る]
```

多くの定型業務はこれで十分に精度が出る。まずはこの形で試し、結果が期待とズレる場合にだけ次のFew-shotやCoTを足す。

### Few-shotの例(そのままコピペ可): 問い合わせメールの分類

「カテゴリ」と「優先度」の判定基準を言葉で説明するより、実例を2〜3個見せたほうが確実に揃う。

```
あなたはカスタマーサポートの一次仕分け担当です。
入力された問い合わせメールを、カテゴリと優先度に分類してJSON形式で出力してください。
以下の例を参考に、同じ形式で出力してください。

【例1】
入力: 「先月から契約しているプランの請求額が急に2倍になっています。理由を教えてください。」
出力: {"category": "請求", "priority": "高", "reason": "課金トラブルは信頼低下に直結するため"}

【例2】
入力: 「操作マニュアルのPDFが開けません。リンクが壊れているようです。」
出力: {"category": "技術", "priority": "中", "reason": "利用は継続できるが不便が発生している"}

【例3】
入力: 「サービスのロゴデータを、社内報で紹介する用に提供してもらえますか。」
出力: {"category": "その他", "priority": "低", "reason": "緊急性がなく営業影響もない依頼"}

【分類してほしい問い合わせ】
入力: 「アプリにログインできず、明日の会議で使う資料にアクセスできません。至急対応してほしいです。」
出力:
```

例を3つ入れたのは、カテゴリ・優先度それぞれで異なるパターンを1つずつ見せるため。例が1つだけだと「その1例の特徴」を過学習して汎化しにくいので、異なるパターンを含む2〜3例が目安になる。

### Chain-of-Thoughtの例(そのままコピペ可): 割引適用の判定

```
以下の注文について、当社の割引ルールに基づき、最終的な割引率を算定してください。
一発で結論を出さず、ステップごとに考えてから、最後に結論だけを1行でまとめてください。

【割引ルール】
- 累計購入額50万円以上: 5%
- 累計購入額100万円以上: 10%
- 初回契約から3年以上の継続顧客: さらに3%を加算
- ただし合計は最大15%を上限とする

【注文情報】
累計購入額: 120万円
契約継続年数: 4年

思考の手順:
1. 累計購入額から基本の割引率を特定する
2. 継続年数の条件に当てはまるか確認し、加算する割引率を計算する
3. 上限15%を超えていないか確認する
4. 最終的な割引率を結論として提示する
```

「ステップごとに考えてから答えてください」という一文を末尾に加えるだけの**Zero-shot CoT**でも一定の効果があるが、上記のように「思考の手順」まで番号付きで示すと、複数条件が絡む業務ロジックでの見落としがさらに減る。

### ツール横断の対応付け(2026年7月時点)

| 手法 | 主要ツールでの扱い |
|---|---|
| Few-shotの例示 | ChatGPT・Claude・Geminiいずれも、プロンプト本文やカスタム指示・プロジェクトの指示欄に例を直接書き込めば機能する。専用のUIはなく「プロンプトに書く」のが基本 |
| Chain-of-Thought | 通常モデル(GPT-4o系、Claude Sonnet系の非推論モード等)には「ステップごとに考えて」と明示するCoTが今も有効。OpenAIのo3・GPT-5.x「Thinking」モード、Claudeの「拡張思考(Extended Thinking)」、Geminiの「Thinking」モデルは、ユーザーがCoTを指示しなくても内部で自動的に思考過程を生成する |

### 推論モデル時代のCoT: 「明示的に指示する必要性」は薄れている

2022年にCoTが提唱された当時は、GPT-3クラスのモデルに「ステップごとに考えて」と一文を加えるだけで正答率が跳ね上がる、という使い方が主流だった。しかし2026年時点で主流になっているOpenAIのo系列・GPT-5.x(Thinking/reasoning_effortパラメータ搭載)、Claudeの拡張思考、Geminiの「Thinking」モデルは、そもそも**強化学習によって「回答前に内部で思考過程を生成する」動作自体を学習済み**である。ユーザーからは見えない(あるいは要約された形でのみ見える)思考トークンを生成してから最終回答を出すため、プロンプト側で「ステップごとに考えて」と重ねて指示しても効果が薄い。

OpenAIは公式ガイドで、o1・o3系モデルに対しては複雑なCoT指示や多数のFew-shot例を追加するとむしろ性能が下がる場合があると明言しており、シンプルで直接的な指示のほうが良い結果につながるとしている。Anthropicも拡張思考モードでは、まず高レベルの指示だけを与えてモデル自身の思考の運び方を観察し、必要な部分だけ自然言語で補足する進め方を推奨している。つまり実務では、**使っているモデルが「Thinking」「推論」系かどうかで、CoTを書き込むかどうかを切り替える**必要がある。

## 注意点・よくある誤解

- **Few-shotは「例の質」がそのまま出力品質になる**: 誤字・古い基準・偏った例を1つでも混ぜると、AIはそれも「お手本」として素直に模倣する。例は必ず見直したうえで、異なるパターンを2〜3個バランスよく入れる。
- **推論モデルにFew-shotを重ねると逆効果になることがある**: OpenAIのo1系での検証では、Few-shot例を追加したことでゼロショットより性能が下がったケースが報告されている。推論モデルではまず例なしで試し、それでも形式が揃わない場合だけ最小限の例を1つ足す、という順番が安全。
- **CoTは万能ではなく、コストとレイテンシが増える**: 思考過程を書かせる・生成させる分だけ出力トークンが増え、料金と応答時間がかさむ。単純な分類や短い要約のようなタスクにまでCoTを付けるのは非効率で、複雑な計算・条件判定・多段階の意思決定が必要なタスクに絞って使うのが実務的。
- **「ステップごとに考えて」だけでは思考が浅くなることがある**: 何をどの順で考えるべきかが自明でないタスクでは、Zero-shot CoTの一文だけでは効果が乏しい場合がある。上記の割引判定の例のように、考える手順そのものを番号付きで示すFew-shot CoT寄りの書き方のほうが安定する。

## 最初の一歩

直近でAIの出力形式やトーンが思ったように揃わなかった依頼を1つ選び、期待する出力例を2つ手作業で書いてプロンプトに追加し、Few-shot化して結果を比べてみる。
