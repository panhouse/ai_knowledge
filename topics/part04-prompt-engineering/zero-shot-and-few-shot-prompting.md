# Zero-shotプロンプティングとFew-shotプロンプティング

## これは何か

Zero-shot(ゼロショット)プロンプティングとは、例を一切見せずに指示文だけでAIにタスクをやらせる、最も基本的なプロンプトの書き方である。一方Few-shot(フューショット)プロンプティングは、「こういう入力にはこういう出力を返してほしい」という具体例を2〜5個ほどプロンプトに含めてから本番の指示を出す書き方を指す。

言葉でいくら「フォーマルな文体で」「この分類基準で」と説明しても、AIが意図通りに解釈するとは限らない。そんなとき、実例を1つ2つ見せるだけで、出力の形式・トーン・分類基準が劇的に安定する。逆に、例を用意する手間や入力トークン(AIが処理する文字の単位。詳細は[トークンとは何か](../part01-ai-llm-basics/token-basics.md)参照)の増加というコストもかかるため、「どんなときに例を足すべきか」を知っておくことが実務上重要になる。

## 仕組み・背景

現在の大規模言語モデル(LLM)は、指示文だけを与える「Zero-shot」でも、事前学習・指示チューニングによって身につけた一般知識だけである程度のタスクをこなせる。これは2022年前後から急速に向上した能力で、簡単な要約や翻訳、一般的な分類などはZero-shotで十分な精度が出ることが多い。

Few-shotは、この上に「文脈内学習(in-context learning)」と呼ばれる性質を利用する手法である。LLMはプロンプト内に並んだ「入力→出力」のペアを見ると、モデル自体のパラメータ(重み)を書き換えることなく、その場でパターンを読み取って以降の出力に反映させる。パラメータを更新する「学習」ではなく、あくまで1回の応答生成の中で一時的にパターンを模倣する点が特徴である。この考え方は2020年のOpenAIの論文「Language Models are Few-Shot Learners」(GPT-3の論文)で広く知られるようになった。例が1個だけの場合は特に「One-shot」と呼ぶこともある。

Zero-shot/Few-shotは、AIに「考え方の手順」まで教える発展形であるChain of Thought(CoT、AIに段階的に思考過程を書かせてから結論を出させる手法。本リポジトリでは別ページで扱う予定)の土台になる、プロンプト設計における最も基礎的な入門手法という位置づけである。

## 使いどころ・使い分け

| 状況 | 推奨される手法 | 理由 |
|---|---|---|
| 一般常識で答えられる質問、簡単な要約・翻訳・言い換え | Zero-shot | AIの事前知識だけで十分な精度が出やすく、例を作る手間が無駄になる |
| 誰もが知っている定型フォーマット(丁寧なビジネスメール等) | Zero-shot(必要なら指示文を丁寧に) | 一般的なパターンなので言葉での指示で足りることが多い |
| 独自の出力フォーマットに揃えたい(社内資料の型、JSON構造など) | Few-shot | 「見せた方が早い」パターン。言葉での説明よりも実例の方が正確に伝わる |
| 会社固有の分類基準がある問い合わせ分類・カテゴリ分け | Few-shot | 一般的なカテゴリ体系と異なる独自ルールは、例がないとAIが推測で外しやすい |
| 特定のトーン・文体に寄せたい(社長の口調を再現する等) | Few-shot | 「フォーマルに」等の形容詞的な指示よりも、実際の文章例の方が再現度が高い |
| 判断が割れる微妙な線引き・エッジケースの扱い | Few-shot(エッジケース例を含める) | 境界事例を例として見せることで、判断基準のブレを抑えられる |
| 数式やロジックを段階的に解かせたい | Zero-shot CoT(「ステップごとに考えて」等の一言を足す)またはCoT | 推論系タスクでは、下手なFew-shot例がかえって精度を下げる場合がある(後述) |
| 毎日・毎時間レベルで大量に発生する定型タスクを、プロンプト無しで安定させたい | ファインチューニング(モデル自体の追加学習)を検討 | Few-shotは都度プロンプトに例を含めるためトークン代がかさむ。同じパターンを大量・恒常的に処理するなら、モデルに直接学習させる方が長期的に安く安定する。ただし専門知識と追加コストが必要なので、まずはFew-shotで精度を検証してから判断するのが現実的 |

## 実務での使い方

### 同じタスクをZero-shot / Few-shotで書き比べる(問い合わせ分類の例)

**Zero-shot版**

```
以下の顧客からの問い合わせを、「返品」「不具合」「使い方の質問」「その他」の
いずれかに分類してください。分類名だけを出力してください。

問い合わせ: 「先週届いた商品のファスナーが壊れているのですが、
交換してもらえますか?」
```

これだけでもAIは「不具合」または「返品」のどちらかを返すが、社内では「不具合が原因の返品は"返品"ではなく"不具合"に分類する」という独自ルールがある場合、Zero-shotではAIがどちらを選ぶか安定しない。

**Few-shot版**

```
以下の顧客からの問い合わせを、「返品」「不具合」「使い方の質問」「その他」の
いずれかに分類してください。分類名だけを出力してください。

分類の考え方は以下の例を参考にしてください。

例1
問い合わせ: 「サイズが合わなかったので返品したいです」
分類: 返品

例2
問い合わせ: 「届いた商品の電源が入りません」
分類: 不具合

例3
問い合わせ: 「箱が破損していた商品を交換してほしい。中身は壊れていないと思う」
分類: 返品

例4
問い合わせ: 「壊れていて動かないので交換してほしい」
分類: 不具合

上記のように、「壊れている・動かない」など商品自体の欠陥が理由の場合は
"不具合"を優先し、サイズ違いや気に入らないなど顧客都合の場合のみ
"返品"に分類してください。

問い合わせ: 「先週届いた商品のファスナーが壊れているのですが、
交換してもらえますか?」
```

例4つを見せ、さらに判断基準を一言添えることで、「欠陥品の交換依頼」という紛らわしいケースでも狙った分類(この場合は"不具合")に寄せやすくなる。

### 出力フォーマットを揃えたい場合の例(会議メモの要約)

```
Zero-shot:
「以下の会議の文字起こしを要約してください」
→ 見出しの付け方、箇条書きの粒度、含める項目がAIの気分次第でばらつく

Few-shot:
「以下の会議の文字起こしを、次の例と同じ形式で要約してください。

【例】
入力: (過去の会議の文字起こし)
出力:
## 決定事項
- ・・・
## 未決事項
- ・・・
## 次回までのアクション
- 担当者名: 内容(期限)

このフォーマットに沿って、以下の文字起こしを要約してください。
(本番の文字起こしを貼り付け)」
→ 見出し・粒度・項目が毎回同じ形式に揃う
```

### 実務のコツ

- **例の数は2〜5個が目安**: Anthropicも公式ドキュメントで3〜5個程度を推奨しつつ、「まず1個(One-shot)で試し、出力が狙い通りにならない場合だけ増やす」段階的なやり方を勧めている。例を増やしすぎるとプロンプトが冗長になり、かえって精度が落ちることもある。
- **例は多様に・エッジケースを含める**: 同じパターンの例ばかり並べると、AIがその表面的な共通点(文章の長さ、特定の単語など)を「正解の条件」と誤学習してしまうことがある。境界線上の紛らわしい事例をあえて1つ混ぜると、判断基準がより正確に伝わる。
- **例の順番・比率にも要注意**: 例の並び順や、カテゴリごとの例の数の偏りが結果に影響することが実験で報告されている。特定のカテゴリの例ばかり並べると、そのカテゴリに判定が偏る「多数派バイアス」が起きやすいので、カテゴリ間で例の数をなるべく揃えるとよい。
- **トークン数(≒料金)に注意**: 例を足すたびに入力トークンが増え、API利用時は処理コストにも跳ね返る。同じ例を毎回貼り付けるくらいなら、ChatGPTの「カスタム指示」やClaudeの「プロジェクトの指示」に例を登録しておき、プロンプト本文を短く保つのも一つの方法(詳しくは[プロンプトの基本構成要素](./prompt-basic-structure.md)参照)。
- **例を目立たせて区切る**: 「例1」「例2」のような見出しや、`<example>`のようなタグで指示文と例を視覚的に分離すると、AIが「これは例だ」と正しく認識しやすくなる。

## 注意点・よくある誤解

- **「例を足せば足すほど良い」は誤り**: 例が増えるとプロンプトが長くなり、AIが本来の指示より例の表層的なパターンに引っ張られて精度が落ちることがある。効果を見ながら少数から試すのが基本。
- **推論(計算・論理)が絡むタスクでは逆効果のことがある**: 数学の文章題や複雑な条件分岐のような「考える力」が問われるタスクでは、下手なFew-shot例がかえって特定の解き方に引きずられて精度を落とすケースが報告されている。こうしたタスクでは「ステップごとに考えてください」と一言添えるだけのZero-shot CoTの方が有効なことも多い(CoTの詳細は別ページで扱う)。
- **Few-shotは魔法の杖ではない**: 例が指示内容と矛盾していたり、質が低かったりすると、AIはその悪い例の方を忠実に再現してしまう。「量より質」を優先し、実際の業務データに近い、正解が明確な例を選ぶこと。
- **機密情報を例に使う場合の注意**: 実際の顧客データや社内文書を例として貼り付ける場合、外部のAIサービスに送信して問題ない情報かを事前に確認する(社内規定・利用しているツールのデータ取り扱い方針を確認)。

## 最初の一歩

普段よく使っているプロンプトを1つ選び、「こう出力してほしい」という具体例を2〜3個追記して、Few-shot版として投げ直してみる。Zero-shotのときと比べて、フォーマットやトーンの再現度がどれだけ安定するかを比べてみるとよい。
