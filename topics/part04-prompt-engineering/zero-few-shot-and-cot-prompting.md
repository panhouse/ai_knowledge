# Zero-shot・Few-shot・Chain-of-Thoughtプロンプティング

## これは何か

同じ生成AIでも、聞き方を変えるだけで出力の質が大きく変わる。特に「毎回フォーマットがバラバラになる」「計算や複数条件の判断で単純なミスをする」という2つの困りごとは、指示文の書き方だけで大幅に改善できる。その基本手法が3つある。

- **Zero-shotプロンプティング**: 例を1つも示さず、指示だけでタスクをやらせる最も基本的な方法
- **Few-shotプロンプティング**: 入力と出力の組み合わせ例をいくつか示し、その通りのパターンで答えさせる方法
- **Chain-of-Thought(CoT、思考の連鎖)**: 最終的な答えだけでなく、途中の考え方を段階的に言語化させてから答えさせる方法

この3つは応用手法(Tree-of-Thought、ReActなど)の土台になる、プロンプトエンジニアリングの入門三種である。

## 仕組み・背景

### Zero-shot: まずはこれから試す

Zero-shotは「役割・タスク・出力形式」だけを書いて、例を一切示さない書き方である。OpenAI・Anthropicの公式ガイドともに「まずzero-shotで試し、精度が不十分な部分だけ手法を追加する」という順序を推奨している。要約・翻訳・分類など、モデルが事前学習で数多く見てきた定型タスクは、zero-shotだけで十分な精度が出ることが多い。

### Few-shot: 例で「型」を教える

Few-shotは、プロンプトの中に入力→出力の実例を複数入れておき、AIにそのパターンを模倣させる書き方である。この考え方は2020年のOpenAIの論文「Language Models are Few-Shot Learners」(GPT-3の論文)で示され、ファインチューニング(追加学習)なしで、プロンプト内の数個の例だけでタスクに適応できることが実証された。Anthropicの公式ガイドは、例は**3〜5個**、実際の使用ケースに近く(Relevant)、エッジケースを含む多様さ(Diverse)を持たせ、`<example>`タグのように「指示」と区別できる形で構造化して入れることを推奨している。

### CoT: 考える過程を言語化させる

CoTは、AIに最終的な答えの前に「途中の考え方」を書かせる手法である。2022年の研究(Kojima et al., “Large Language Models are Zero-Shot Reasoners”)で、プロンプトの末尾に**“Let’s think step by step”(段階的に考えてみましょう)**という一文を加えるだけで、例を1つも示さなくても数学・論理タスクの正答率が大きく向上することが示された。これは「Zero-shot CoT」と呼ばれる。Anthropicの公式ガイドも同様に、複雑なタスクでは`<thinking>`タグで思考過程、`<answer>`タグで最終回答を分けて書かせる構成を推奨している。

### 2026年時点の重要な変化:「思考モデル」がCoTを内蔵している

2022〜2024年頃のCoTは「プロンプトで明示的に指示する」ことが前提だった。しかし2026年7月時点の主要な推論特化モデル(思考モデル)は、**プロンプトに何も書かなくても、内部で自動的に段階的推論を行う**ように変わっている。

- **OpenAI**: 旧o1/o3系列はGPT-5ファミリーに統合され、日常タスク向けの軽量モデルと、深い推論が必要な場面で使う「Thinking」系モデルに分かれている。Thinking系は内部で連鎖的な推論を生成してから回答する。
- **Anthropic**: Claude Opus/Sonnet系では「Extended Thinking(拡張思考)」を`effort`(思考の深さ)パラメータで制御でき、最上位モデルでは質問の複雑さに応じて思考の深さを自動調整する「Adaptive Thinking」が標準になっている。
- **Google**: Gemini Proは既定で「動的思考(dynamic thinking)」が有効になっており、`thinking_level`パラメータやアプリの「思考レベル」メニューで深さを調整する。

つまり2026年時点では、CoTは「プロンプトのテクニック」から「モデル・機能の設定項目」に移りつつある。

## 使いどころ・使い分け

| 手法 | 向いているタスク | 必要な準備 | 精度への効果 |
|---|---|---|---|
| **Zero-shot** | 要約・翻訳・分類・簡単な文章作成など、AIが元々得意な定型タスク | 指示文(役割・タスク・出力形式)だけ | タスクが単純なら十分。複雑になるほど頭打ちしやすい |
| **Few-shot** | 出力フォーマット・トーン・分類ラベルなどを厳密に揃えたいタスク(問い合わせ分類、定型文書作成、独自の採点基準の適用など) | 入出力例3〜5個(多様でエッジケースを含むもの) | フォーマットの再現性・一貫性が大きく向上。例が少なすぎる/似すぎていると意図しないパターンを学習し逆効果になることもある |
| **CoT** | 計算、複数条件の比較、多段階の論理判断など「うっかりミス」が起きやすいタスク | 「段階的に考えてください」等の一文、または`<thinking>`タグでの誘導 | 推論系タスクの正答率が大きく向上。単純なタスクに使うと出力が冗長になり、コスト・待ち時間が増えるだけになりやすい |

**判断基準はシンプルに次の順で考えるとよい。**

1. まずZero-shotで試す。それで十分ならそこで止める(手間が最小)。
2. **出力の形式・トーン・粒度がブレる**のが課題なら → Few-shotで例を示す。
3. **計算・論理・比較判断で間違える**のが課題なら → CoTで思考過程を書かせる。
4. 両方が課題なら、Few-shotの例の中に思考過程も含めて示す「Few-shot CoT」を使う(下記の実例参照)。

## 実務での使い方

### 実例1: Zero-shot(会議議事録の要約)

```
以下の会議の文字起こしを読み、次の3項目に分けて日本語で要約してください。

1. 決定事項
2. 宿題(担当者名と期限を明記)
3. 次回への論点

【文字起こし】
[ここに文字起こしを貼り付け]
```

### 実例2: Few-shot(問い合わせメールの分類・ラベル付け)

分類ラベルの粒度や表記ゆれを揃えたい業務(カスタマーサポートの一次仕分けなど)に向く。3〜5例を目安に、内容が重複しない多様な例を入れる。

```
以下の例と同じ形式で、顧客からの問い合わせメールを
「カテゴリ」「緊急度(高/中/低)」「一言要約」の3項目に分類してください。

<example>
入力: 「注文した商品が届かないのですが、いつ届きますか?」
出力: カテゴリ=配送遅延 / 緊急度=中 / 要約=商品未着の問い合わせ
</example>

<example>
入力: 「サイトにログインできず、パスワードを何度リセットしても変わりません。」
出力: カテゴリ=ログイン障害 / 緊急度=高 / 要約=パスワードリセットが機能しない
</example>

<example>
入力: 「請求書の宛名を会社名に変更してほしいです。」
出力: カテゴリ=請求書修正 / 緊急度=低 / 要約=請求書の宛名変更依頼
</example>

分類してほしい入力:
「先週申し込んだプランのアップグレードがまだ反映されていません。」
```

### 実例3: Chain-of-Thought(発注先の比較検討)

複数条件を比較して結論を出すタスクは、途中の比較根拠を書かせることで判断ミスを減らせる。`<thinking>`と`<answer>`でタグを分けると、最終回答だけを後工程で抜き出しやすい。

```
以下の条件から、A社とB社どちらに発注すべきかを判断してください。
<thinking>タグの中で、コスト・納期・品質(過去の不良率)の3観点について
それぞれ段階的に比較し、根拠を書き出してください。
そのうえで<answer>タグの中に結論だけを1〜2行で書いてください。

【A社】単価480円、納期21日、過去の不良率0.8%
【B社】単価520円、納期14日、過去の不良率0.3%
発注数量: 10,000個、今回の優先事項: 品質重視だが納期にも余裕がない
```

### 実例4: Few-shot + CoTの組み合わせ

Few-shotの例の中に思考過程も含めておくと、AIはその「考え方の型」も一緒に模倣する。フォーマットと推論精度の両方を揃えたい場合に有効。

```
以下の例のように、<thinking>で判断根拠を段階的に書いたうえで、
<answer>に最終判定だけを書いてください。

<example>
入力: 見積金額98,000円(税込)、予算上限100,000円、納期は希望通り
<thinking>
金額は予算内(98,000 < 100,000)。納期も希望通り。特段の懸念なし。
</thinking>
<answer>承認</answer>
</example>

<example>
入力: 見積金額150,000円(税込)、予算上限100,000円、納期は希望通り
<thinking>
金額が予算を50,000円超過している。納期に問題はないが、
金額超過は上長承認が必要な水準。
</thinking>
<answer>要上長承認</answer>
</example>

判定してほしい入力:
見積金額105,000円(税込)、予算上限100,000円、納期は3日遅延
```

### 推論モデルではどう使い分けるか(2026年7月時点)

| ツール/モデル | 思考機能の名称 | プロンプトでCoTを明示する必要性 | 深さの調整方法 |
|---|---|---|---|
| ChatGPT(Thinking系モデル) | 内部推論(旧o1/o3系列がGPT-5ファミリーに統合) | **不要**。「段階的に考えて」と書いても効果は薄く、むしろ高レベルの目的・制約・完了条件を明確に書く方が精度が上がりやすい | モデル切り替え(軽量版/Thinking版/Pro版など) |
| Claude(Opus/Sonnet系) | Extended Thinking / Adaptive Thinking | **不要**(最上位モデルは常時オン)。オフのモデル・軽量モデルでは手動CoTがまだ有効な代替手段 | API: `thinking`パラメータの`effort`。画面: 拡張思考のトグル |
| Gemini(Pro系) | Thinking(動的思考) | **不要**。既定で動的に思考トークンを使用 | API: `thinking_level`。アプリ: 「思考レベル」メニュー |

**使い分けの結論**は次のとおり。

- **思考モデル(Thinking/Extended Thinking/動的思考が有効)を使うとき**: 「段階的に考えて」という手動CoTの指示は基本的に不要。むしろ「考える手順」を細かく指示しすぎると、モデル自身の推論の方が優れているケースを阻害することがある。書くべきは、達成したい高レベルの目的・制約・判断基準であり、思考の深さは効果度(effort)や思考レベルのパラメータ・UIトグルで調整する。
- **軽量・高速モデルを使うとき**: これらは思考機能がオフまたは最小構成なので、実例1〜4のような手動CoT・Few-shotは依然として有効な精度向上手段になる。
- どちらのタイプかわからない場合は、まず手動CoTなしで試し、精度が足りなければ「モデルをThinking系に切り替える」か「手動でCoTを追加する」かを選ぶ、という順序が実務的。

## 注意点・よくある誤解

- **CoTは万能ではない**: 単純なタスクに付けると、回答が冗長になるだけでなく、思考モデルでは思考トークン分のコスト・待ち時間が余分にかかる。まずタスクの難易度を見極める。
- **思考モデルに手順を指示しすぎると逆効果になりうる**: Anthropicも「思考過程を細かく指示するより、'よく考えて'のような一般的な指示のほうが良い推論を引き出せることが多い」と述べている。思考モデルの推論は、人間が書いた手順書より優れていることが多いため。
- **Few-shotの例は「量」より「質と多様性」**: 似たような例を10個並べるより、エッジケースを含む3〜5個の多様な例のほうが効く。逆に例が偏っていると、AIが「意図しないパターン」(例えば文字数や語尾の癖)まで模倣してしまうことがある。
- **思考モデルの「思考過程」の表示は要約されている場合がある**: 内部処理をそのまま出しているわけではなく、要約表示になる設定もある。中身を過信して業務上の証跡として使うのは避ける。
- **コスト管理**: Thinking/Extended Thinking/動的思考は、通常の応答より思考トークン分の料金・時間が余分にかかる。定型的な軽作業に高コストな思考モデルを使うのは非効率。

## 最初の一歩

直近使ったプロンプトを1つ選び、(1)Zero-shotのままなら入出力例を2〜3個追加したFew-shot版を作る、または(2)「結論の前に、判断根拠を段階的に書き出してください」という一文を追加したCoT版を作り、同じ依頼を投げ直して結果の違いを比べてみる。
