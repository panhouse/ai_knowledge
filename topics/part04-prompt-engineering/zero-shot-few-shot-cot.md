# Zero-shot/Few-shot/Chain-of-Thoughtプロンプティング

## これは何か

同じ生成AIでも、「例を見せずにいきなり頼む」「お手本を見せてから頼む」「考え方を書かせてから答えさせる」のどれで聞くかで、出力の正確さや形式の安定度は大きく変わる。この3つの聞き方——Zero-shot(ゼロショット)・Few-shot(フューショット)・Chain-of-Thought(CoT、思考の連鎖)——は、プロンプトエンジニアリングの中でも最も基本かつ効果が大きい入門手法である。これを知らないと、「なぜか毎回フォーマットが崩れる」「計算問題だけ答えを間違える」といった不具合の直し方が分からないままになる。

## 仕組み・背景

- **Zero-shot**: 例を一切見せず、指示文だけでタスクをやらせる方法。「この文章を要約して」のようにいきなり本題を頼む、最も自然な聞き方。現在のAIは大量のデータで学習済みのため、単純なタスクなら指示だけで十分にこなせる。
- **Few-shot(= multishot、少数例学習)**: 本番の入力を渡す前に、「入力→望ましい出力」のペアを2〜3個(公式には3〜5個程度が目安)示し、そのパターンを真似させる方法。モデルに新しい知識を教えるというより、「出力の形式・トーン・粒度」を例で指定するのに向く。
- **Chain-of-Thought(CoT、思考の連鎖)**: 「ステップごとに考えてから答えを出して」のように、最終的な答えの前に思考過程を出力させる方法。人間が暗算より筆算の方が計算ミスが減るのと同様、AIも途中式や根拠を言語化しながら進めると、複雑な論理・計算タスクの精度が上がることが分かっている。

3つは独立した選択肢ではなく組み合わせて使える。例えば「Few-shotの例の中でCoT的な思考過程まで示す」といった併用も有効とされる(Anthropic公式ドキュメントも、few-shot例の中に`<thinking>`タグで思考パターンを示す使い方を推奨している)。

### 2026年時点の重要な変化: 「思考モデル」の登場でCoTの役割が変わった

2023〜2024年ごろまでは、CoTは「プロンプト側で明示的に指示する小技」として広まった。しかし現在の主要モデル(ChatGPTのthinkingモード、Claudeの拡張思考・適応的思考、Geminiのdeep think等の「推論特化モデル/思考モデル」)は、複雑な問い合わせに対してユーザーが何も指示しなくても、モデル内部で自動的に段階的な思考(内部CoT)を行ってから答えを返す設計になっている。

そのため実務上は次のように使い分けが変わってきている。

- 思考モードが有効なモデル・プランを使っている場合、「ステップごとに考えて」という指示は基本的に不要(むしろ冗長になりがち)。Anthropicの公式ガイドも「手取り足取りの手順書きより『じっくり考えて』のような大まかな指示の方が良い推論を引き出せることが多い」としている
- 思考モードがオフのモデル・軽量モデル・API側で思考を無効化している場合は、CoTを明示的にプロンプトで指示する意味が依然としてある(公式にも「思考がオフのときのフォールバック手段」と明記されている)
- 見えている思考過程(可視化されたCoT)と、最終回答の正しさは必ずしも一致しない。もっともらしい理由を後付けしているだけの場合もあるため、CoTの出力を鵜呑みにせず、答えそのものの検証(ダブルチェック)は別途必要

## 使いどころ・使い分け

| タスクの性質 | 向いている手法 | 理由 |
|---|---|---|
| 単純な分類・翻訳・言い換えなど、一問一答で完結するタスク | Zero-shot | 例がなくても正答率が十分高く、プロンプトも短く済む |
| 出力フォーマット・文体・粒度を厳密に揃えたい(社内文書の統一、定型メールの分類ラベル固定など) | Few-shot | 「こう書いてほしい」を言葉で説明するより、実例を見せる方が正確に伝わる |
| 複雑な計算・多段階の論理判断・条件分岐が絡む業務ルールの適用 | CoT | 途中経過を出力させることで計算ミス・論理飛躍を減らせる |
| 上記が複合するタスク(例: 過去の見積もり例を参考にしつつ、計算過程も検証したい) | Few-shot + CoT の併用 | 例で形式を固定しつつ、思考過程も出させて精度を担保する |
| 思考モードが有効な最新モデル(拡張思考・deep think等)を使っている | 追加のCoT指示は基本不要。まずは指示なしで試し、精度が足りない場合のみ「じっくり考えて」程度を添える | モデル内部で既に段階的思考をしているため、細かい手順の指示はむしろノイズになりやすい |

判断の目安はシンプルで、「Zero-shotでまず試す→フォーマットが安定しないならFew-shotを足す→計算や論理でミスが出るならCoTを足す」という順に足し算していくのが実務的。

## 実務での使い方

### コピペで使える実例1: Zero-shot(問い合わせメールの一次分類)

```
以下の問い合わせメールを読み、「請求関連」「技術トラブル」「解約・退会」「その他」の
いずれか1つに分類してください。分類名だけを出力してください。

【メール本文】
先月から利用しているプランの料金が急に上がっていて驚いています。
何か変更があったのでしょうか。詳細を教えてください。
```

単純な分類タスクなら、これだけで十分な精度が出ることが多い。

### コピペで使える実例2: Few-shot(問い合わせメールの分類ラベルと文体を厳密に揃える)

```
以下は、問い合わせメールを分類した例です。この形式に厳密に従って、
最後のメールを分類してください。

【例1】
メール: 「先月から料金が急に上がっています。理由を教えてください」
分類: 請求関連 / 緊急度:中 / 一言要約:料金変動の問い合わせ

【例2】
メール: 「ログインしようとするとエラー画面が出て入れません」
分類: 技術トラブル / 緊急度:高 / 一言要約:ログイン不可の不具合報告

【例3】
メール: 「来月末で解約したいのですが、手続き方法を教えてください」
分類: 解約・退会 / 緊急度:低 / 一言要約:解約手続きの問い合わせ

【本番】
メール: 「複数端末で同時にログインできる契約に変更したいのですが可能ですか」
分類:
```

出力フォーマット(「分類 / 緊急度 / 一言要約」の3点セット)を例で固定しているため、Zero-shotより安定して同じ形式が返ってくる。

### コピペで使える実例3: Chain-of-Thought(見積もり計算のチェック)

```
以下の見積もり計算が正しいか検算してください。
まず「考え方」として計算過程を1行ずつ書き出し、
最後に「結論」として正誤と正しい合計金額だけを述べてください。

【見積もり内容】
・基本料金: 120,000円
・オプションA(数量3、単価8,000円)
・割引: 合計金額から5%引き
・記載されている合計金額: 143,200円

考え方:
結論:
```

「考え方:/結論:」で出力を分けて指示すると、思考過程と最終回答が混ざらず、後工程(結論だけ抽出してシステムに流す等)でも扱いやすい。

### 業務での具体的な適用イメージ

| 業務シーン | 適した手法 | 補足 |
|---|---|---|
| 問い合わせメールの一次振り分け | Zero-shot(慣れたら分類ラベルが安定しない場合のみFew-shotへ) | カテゴリ数が少なく定義が明確なら十分 |
| 社内文書・議事録のフォーマット統一 | Few-shot | 「見出しの付け方」「敬体/常体」などを実例で示す方が指示文より確実 |
| 見積もり・請求金額の検算、契約条件の適用判定 | CoT(思考モードのモデルなら追加指示なしでもよい) | 数値を含む多段階判断はCoTで途中式を出させると誤り箇所を発見しやすい |
| 過去の問い合わせ対応履歴を参考に返信文面を作る | Few-shot(良い対応例を2〜3件) | トーンや言い回しのブレを抑えられる |

### ツール横断の対応付け(2026年7月時点)

Zero-shot/Few-shot/CoTは特定のツール機能ではなく「プロンプトの書き方」そのものなので、どのチャットAI・API上でも同じ考え方が使える。ツールによる違いは主に「思考モードの有無・呼び方」の部分。

| ツール | 思考モードの呼び方 | 備考 |
|---|---|---|
| ChatGPT | Thinkingモード(推論モデル、o3系・GPT-5 thinking等) | 通常モードでは明示的なCoT指示が効きやすい |
| Claude | 拡張思考(Extended thinking)/ 適応的思考(Adaptive thinking) | 新しいモデル・プランでは思考が常時オンで、指示なしでも段階的に考える。オフの場合の代替として「ステップごとに考えて」と明示するのが公式ガイドの推奨 |
| Gemini | Deep Think / 「考える」表示のある応答 | 複雑な質問で自動的に長い思考過程を生成 |
| Copilot(Microsoft 365) | Copilotの「詳細な思考」系の応答 | 業務文書中心のため、Few-shot(過去文書の例示)との相性が良い |

## 注意点・よくある誤解

- **Few-shotは「例の質と順序」が結果を左右する**: 内容が本番タスクと近く多様な例(エッジケースを含む)ほど効果が高い一方、似た例ばかり・偏った順序で並べると、AIが本質と関係ないパターン(例の並び順や表現のクセ)まで学習してしまうことがある。例が弱いと感じたら差し替え・並べ替えを試す価値がある
- **CoTは出力トークンを増やし、コスト・応答時間が伸びる**: 思考過程を出力させる分だけ課金対象のトークン数が増えるため、単純なタスクにまでCoTを付けるとコスト効率が悪化する。「複雑な判断が必要なタスクにだけ絞って使う」のが基本
- **思考モードが常時オンのモデルに、さらに手順を事細かに指示すると逆効果になることがある**: 「まず〜して、次に〜して」と手順を細かく書くより、「じっくり検討してから答えて」のような大まかな指示の方が良い結果になりやすいという報告がある。まずは指示なしで試し、足りない部分だけ補うのがよい
- **見えているCoTの説明が正しいとは限らない**: モデルが出力する思考過程は、必ずしも実際の判断根拠を正確に表しているわけではなく、もっともらしい説明を後付けしているだけの場合もある。重要な意思決定にCoTの説明をそのまま根拠として使わず、最終的な答え自体を別途検証する
- **Few-shotの例に機密情報を使わない**: 実際の顧客データや社内の非公開情報をそのまま例として貼り付けると、入力内容が学習や外部ログに使われるリスクがある(APIやエンタープライズプランの設定によって扱いは異なる)。例は仮名・ダミーデータに置き換えるか、自社の学習除外設定を確認してから使う

## 最初の一歩

直近でAIに投げた分類系またはフォーマット系のタスクを1つ選び、Zero-shotの結果とFew-shot(実例2〜3個を追加)の結果を見比べて、フォーマットの安定度がどう変わるか確認してみる。
