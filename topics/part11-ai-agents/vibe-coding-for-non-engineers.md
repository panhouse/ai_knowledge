# 非エンジニアのための「バイブコーディング」実践ガイド

## これは何か

バイブコーディング(vibe coding)とは、**コードを1行も書かずに、AIに自然言語で指示するだけで
動くアプリ・ツールを作る**開発スタイルである。OpenAI共同創業者のAndrej Karpathyが
2025年2月に提唱した言葉で、2026年には非エンジニアによる業務ツールの「自作」の主流になっている。

[Claude Code](claude-code-basics.md)・[OpenAI Codex](openai-codex-basics.md)のようなコーディングエージェントは
本来エンジニア向けの製品だが、非エンジニアが「社内の小さな業務ツールを自分で作る」用途で使う場面が
増えている。本ページは特定ツールの使い方ではなく、**非エンジニアが安全に成果を出すための
進め方とレビューの型**を扱う。

## 仕組み・背景

### なぜ今、非エンジニアでも作れるのか

従来のノーコードツール(Part 10で扱う[Dify](../part10-nocode-lowcode/dify-basics.md)など)は
「決められたパーツを組み合わせる」発想だったが、バイブコーディングは
**AIエージェントが実際にコードを生成・実行する**ため、既存のパーツにない自由な機能を
自然言語だけで作れる。この自由度の高さが、便利さとリスクの両方を大きくしている。

### 「動いている」と「安全に運用できる」は別問題

AIが生成したコードは、見た目上は動作していても、エラー処理・入力値の検証・
依存パッケージの脆弱性といった**目に見えない部分**が欠けていることが多い。
非エンジニアはこうした欠落に気づきにくいため、「動いたから完成」と判断するのは危険である。

## 使いどころ・使い分け

### 用途別の向くツール

| やりたいこと | 向くツール |
|---|---|
| Webアプリ・簡易SaaSのプロトタイプを作る | Lovable、Bolt.new、v0、Replit(いずれも英語UIだが日本語プロンプトに対応) |
| 社内の資料作成・ファイル整理を自動化する | [Claude Cowork](claude-cowork-basics.md)、ChatGPT Work(コーディング不要) |
| 既存の社内リポジトリに手を加えたい | [Claude Code](claude-code-basics.md)、[OpenAI Codex](openai-codex-basics.md)(要最低限の環境理解) |
| 定型業務のワークフローを組みたい | [Dify](../part10-nocode-lowcode/dify-basics.md)、n8nなどのノーコードツール(構造化された安全性) |

**「コードを書かせたいのか、業務そのものを代行させたいのか」**を最初に区別すると選びやすい。
純粋な業務代行であれば、そもそもコーディングエージェントを使う必要がない場合も多い。

### 向く用途・向かない用途

| 向く | 向かない |
|---|---|
| 個人・小規模チームで使う業務効率化ツール | 顧客向けに公開する本番サービス |
| 使い捨て前提の一時的な集計・変換スクリプト | 個人情報・機密情報を扱う継続運用システム |
| プロトタイプを見せて要件を固める段階 | 社内の基幹システムと連携する重要な業務ツール |

## 実務での使い方

### 進め方の基本形

```
1. 小さく始める(1機能だけを最初に作る)
2. 動いたら、想定外の入力(空欄・異常な値・大量データ)を試す
3. 「エラー処理を追加して」「入力値を検証して」と明示的に追加依頼する
4. 公開・共有する前に、後述のレビューチェックリストを確認する
5. 保守する人(自分以外も分かる状態か)を決めておく
```

**最初から完璧な指示を書こうとしない。** 小さく作って試し、欠けている部分をAIに追加させる
反復のほうが、非エンジニアには現実的である。

### 公開・共有前のレビューチェックリスト

```
## セキュリティ
- [ ] パスワード・APIキー・顧客情報がコードやログに直接書かれていないか
- [ ] 入力フォームに誰でも変な値を入れられる箇所がないか

## データの扱い
- [ ] 個人情報・機密情報を外部のAIサービスやツールに送っていないか
- [ ] 保存先(どこにデータが残るか)を把握しているか

## 継続運用
- [ ] 自分がいなくても他の人が直せる状態か(最低限の説明を残す)
- [ ] 使っているツール・サービスが有料化・終了した場合の代替手段があるか

## ライセンス・利用規約
- [ ] 使用したライブラリ・テンプレートのライセンス条件に違反していないか
```

判断に迷う項目は、情報システム部門・開発チームに一度見てもらうのが安全である。

### 情報システム部門との連携

非エンジニアが個人で作ったツールが管理外で増えていく状態は、**シャドーAI・シャドーITの
新しい形**である。継続的に使うツールになりそうな場合は、早い段階で情報システム部門に共有し、
「一時的な個人利用」と「業務で継続利用するツール」の境界を決めておくとよい
([シャドーAI(無許可利用)対策](../part04-risk-security/shadow-ai-basics.md)を参照)。

## 注意点・よくある誤解

- **「動いた」は「安全」の証明にならない**: 見た目上正常に動作していても、
  エラー処理・入力値検証・依存パッケージの脆弱性が欠けていることが多い。
  実際に2026年にはMicrosoft Copilot関連でデータ漏洩につながりうる脆弱性(CVE-2026-26144)も
  報告されている
- **機密データを気軽に貼らない**: 「動かして試したいだけ」のつもりで実データをそのまま
  貼り込むと、外部のAIサービスに機密情報が渡ってしまう
  ([情報漏洩を防ぐデータ管理](../part04-risk-security/information-leakage-prevention.md))
- **保守できない人だけが分かるツールを作らない**: 作った本人が離席・退職すると、
  誰も直せない「野良システム」が残る。せめて仕組みの概要を1枚のメモに残す
- **仕様を先に固める「仕様駆動開発」も選択肢にする**: バイブコーディングの落とし穴
  (行き当たりばったりで作り込みが甘くなる)への対策として、要件を先にAIと一緒に
  文章化してから実装させる進め方(spec-driven development)が2026年に注目されている。
  重要度が上がるツールほど、この一手間を惜しまない
- **本番・顧客向けサービスには使わない**: プロトタイプ・社内向けの小規模ツールと、
  顧客に公開する本番サービスでは求められる品質が全く違う。境界を混同しない

## 最初の一歩

影響範囲が小さい業務(自分専用の集計ツールなど)を1つ選び、Lovable・Bolt.newのような
非エンジニア向けツールで小さく試作してみる。作った直後に、上記のレビューチェックリストを
実際に1周してみることが、「動く」と「安全に使える」の違いを体感する最短路になる。
