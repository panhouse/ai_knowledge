# マルチエージェント・オーケストレーションの基本

## これは何か

マルチエージェント・オーケストレーションとは、**1つの大きな作業を複数のAIエージェントに分担させ、
それを取りまとめる役(オーケストレーター)が並列に実行・統合する仕組み**である。

[Claude Code](claude-code-basics.md)の「サブエージェント」、[Antigravity](google-antigravity-basics.md)の
「Agent Manager」、[Codex](openai-codex-basics.md)の「クラウドでの並列実行」は、いずれもこの考え方を
実装したものである。本ページは各ツールの操作方法ではなく、
**いつ・どう複数のエージェントに分けるべきかという設計の考え方**を扱う。

## 仕組み・背景

### オーケストレーター・ワーカー型が基本形

Anthropicが自社の調査系エージェントで採用している構成が代表的なパターンである。

```
オーケストレーター(司令塔)
  1. 作業を独立したサブタスクに分解する
  2. サブタスクごとにサブエージェント(ワーカー)を立ち上げる
  3. 各サブエージェントが並列に作業し、結果を返す
  4. オーケストレーターが結果を統合・検証し、最終的な成果物にまとめる
```

サブエージェントはそれぞれ**独立したコンテキスト(会話の記憶領域)**を持つため、
1つのエージェントに全部を詰め込むより、**関係ない情報に邪魔されずに1つの作業に集中できる**。
これが並列化による速度向上に加えて、マルチエージェント構成のもう一つの利点になる。

### コストは跳ねる

並列化には代償がある。Anthropicの計測では、通常のエージェント作業はチャットの約4倍、
マルチエージェント構成の調査タスクは約**15倍**のトークンを消費する。
一方で、内部の評価では複数のサブエージェントを使う構成が単一エージェントを
**90.2%上回る**結果も出ている。つまり「**成果の価値がトークンコストを上回るか**」が
導入判断の分かれ目になる。

## 使いどころ・使い分け

### 向く作業・向かない作業

マルチエージェント構成が効くのは、**作業を並列の系統に分けられ、各系統がそれほど
互いに依存しない**タスクである。逆に、手順が一本道でお互いに強く依存し合うタスクでは、
分割してもオーケストレーターが結果を統合するコストのほうが大きくなりやすい。

| 向く | 向かない |
|---|---|
| 独立したトピックを並行して調べるリサーチ | 手順が一本道で前工程の結果に強く依存する作業 |
| 複数ファイル・複数モジュールの並行レビュー | **密結合なコーディング作業**(1つの設計判断が全体に影響する) |
| 大量の候補を並行して評価・スクリーニングする作業 | 対話しながら少しずつ方針を決めていく作業 |
| 観点の違うレビュー(セキュリティ・パフォーマンス・仕様適合など)を同時に走らせる | 単純にコストを増やしても精度が上がらない軽い作業 |

**まず単一エージェントで試し、「並列化すべき根拠(時間がかかりすぎる、
1つのコンテキストに収まらない、明確に独立した観点が複数ある)」が見えてから
マルチエージェント化する**のが実務上の基本である。Anthropic自身も、
複雑な仕組みを作り込んだ結果、単一エージェントのプロンプト改善だけで
同等の成果が出たと振り返っている。

### 並列実行数とレビューの関係

並列に走らせる本数を増やしても、成果物を確認する人間のレビュー速度は変わらない。
**律速(ボトルネック)は常に人のレビュー**であり、「5本並列で走らせたが3本しか
確認できなかった」という状態は珍しくない。並列数は、レビュー体制に見合った本数に
抑えるのが実務上の判断軸になる。

## 実務での使い方

### 主要ツールでの実装(2026年8月時点)

| ツール | 呼び方 | 特徴 |
|---|---|---|
| [Claude Code](claude-code-basics.md) | サブエージェント | 1セッション内で大きな作業を分割し、複数のエージェントを並列で走らせる |
| [Google Antigravity](google-antigravity-basics.md) | Agent Manager | 複数のローカルエージェントをGUIのダッシュボードで並列管理する司令塔 |
| [OpenAI Codex](openai-codex-basics.md) | クラウドでの並列実行 | 独立したタスクをクラウド側で多数同時に走らせ、あとで結果を回収する |

### 分解の設計手順

```
1. 作業を「本当に独立しているか」で切り分ける
   (お互いの結果を必要としないサブタスクだけを並列化する)
2. 各サブタスクに与える情報を最小限に絞る
   (オーケストレーター側の文脈をそのまま渡すとコストが増え、混乱の元になる)
3. 統合の方法を先に決める
   (誰が・どの基準で複数の結果を1つにまとめるかを、実行前に決めておく)
4. レビューできる本数に並列数を合わせる
```

## 注意点・よくある誤解

- **並列化はデフォルトの選択ではない**: 多くの業務タスクは単一エージェントのほうが速く・安く・
  デバッグしやすい。並列化はコストと複雑さが増える前提で、明確な根拠がある場合にのみ選ぶ
- **密結合なコーディング作業は不向き**: 1つの設計判断が他の部分に影響するようなコード変更は、
  サブエージェントに分割すると整合性が崩れやすい。コーディングでの並列化は
  「独立したファイル・モジュールの並行修正」のような場面に限定する
- **トークン消費は当たり前に4〜15倍になる**: 「並列にすれば早く終わる」という時間の視点だけでなく、
  コストの視点でも導入判断をする
- **並列数を増やすほど生産性が上がるわけではない**: 人のレビューが追いつかなければ、
  出てきた成果物は使われずに埋もれる

## 最初の一歩

いま単一エージェントで進めている作業のうち、「観点が明確に複数あり、お互いに依存しない」
ものを1つ選び、そのうち2つの観点だけをサブエージェントに分けて試してみる。
結果を統合する基準を先に決めておくことが、マルチエージェント化の感覚をつかむ最短路である。
