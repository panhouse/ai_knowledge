# Claude Codeの基本

## これは何か

Claude Code は Anthropic 公式のコーディングエージェントで、**「このバグを直して」「この機能を追加して」と
自然文で頼むと、コードベースを自分で読み、複数ファイルを編集し、テストを走らせ、
最後にPRを出すところまで一気に進める**ツールである。

AIチャットにコードを貼って答えをもらう使い方との決定的な違いは、**人がコピペをしない**点にある。
チャットは「こう書けばいい」と教えてくれるだけで、ファイルを開いて貼り付け、動かして、
エラーを持ち帰って再度聞く往復は人がやる。Claude Code はその往復ごとAIが回す。
結果として、人の仕事は「指示を出す」と「出てきた差分をレビューする」の2点に寄る。

エンジニア向けの製品だが、非エンジニアでも「社内向けの小さなツールを作る」「大量のファイルを
一括で変換する」といった用途で使われている。ただし後述のとおり、**出てきたものの妥当性を
判断できない領域では使わない**のが原則である。

## 仕組み・背景

### エージェントループ

Claude Code の中核は、[AIエージェントとは何か](ai-agent-basics.md)で扱った
「思考→ツール実行→結果観察」のループである。具体的には次を自分で選んで繰り返す。

1. ファイルを検索・読み込む(どのファイルを見るかをAIが決める)
2. ファイルを編集する
3. コマンドを実行する(テスト、ビルド、lint、git 操作)
4. 結果を見て、失敗していれば直して再実行する

「テストが落ちたら直して再実行」を人の介在なしに回せることが、チャットとの体験差を生んでいる。

### 動作する場所

2026年8月時点で、次の入口から同じエージェントを使える([Claude Code公式](https://claude.com/product/claude-code))。

| 入口 | 主な使い方 |
|---|---|
| ターミナル(CLI) | 中心的な使い方。`claude` で起動して対話 |
| IDE拡張 | VS Code、JetBrains などのエディタ内で使う |
| デスクトップアプリ | macOS / Windows / Linux のネイティブアプリ |
| Web(claude.ai/code) | ブラウザから。ローカル環境を用意せず使える |
| モバイル(iOS / Android) | 外出先で進捗確認・指示出し |
| Slack | Slack からタスクを投げる |

### 押さえておきたい機能概念

| 概念 | 何をするもの |
|---|---|
| **サブエージェント** | 大きな作業を分割し、複数のエージェントを並列で走らせる |
| **ルーティン** | 定期実行・API・イベントを起点に自動でタスクを走らせる |
| **MCP** | 外部ツール(GitHub、DB、社内システム)への接続口。[MCPの基本](../part09-api-development/mcp-basics.md)参照 |
| **コンピュータ操作** | アプリを開く、ブラウザを操作する、開発ツールを動かす |
| **CLAUDE.md** | プロジェクト固有の前提・規約をAIに常時読ませる設定ファイル |

## 使いどころ・使い分け

### 向く仕事・向かない仕事

| 向く | 向かない |
|---|---|
| 既存コードの調査(「この処理はどこで呼ばれている?」) | 仕様そのものを決める(何を作るべきかの判断) |
| 定型的な修正の一括適用(命名変更、APIの移行) | 出てきたコードの妥当性を誰も判断できない領域 |
| テストの追加、失敗しているテストの修復 | 本番データを直接触る作業 |
| ドキュメント・コメントの整備 | 障害対応の初動(状況把握を人がやるべき場面) |
| 大量ファイルの機械的な変換・整形 | セキュリティ設計・認証周りの新規実装 |

### 他のツールとの使い分け

| こういう場合 | これを使う |
|---|---|
| 自分でコードを書きながら補完してほしい | GitHub Copilot / Cursor([Part 8](../part08-specialized-ai-tools/coding-assistant-ai-comparison.md)) |
| タスクを丸ごと任せて、結果をレビューしたい | Claude Code |
| コードではない業務(資料作成・調査)を任せたい | [Claude Cowork](claude-cowork-basics.md) |
| ChatGPT系で揃えたい | [OpenAI Codex](openai-codex-basics.md) |
| Google系・IDEのGUIで管理したい | [Google Antigravity](google-antigravity-basics.md) |

## 実務での使い方

### 始め方(ターミナルの場合)

1. Node.js を入れた状態で `npm install -g @anthropic-ai/claude-code`
2. プロジェクトのディレクトリに移動して `claude` を実行
3. 初回はブラウザが開いて Claude アカウントで認証(サブスクを使う場合)
4. `/init` を実行すると、リポジトリを解析して `CLAUDE.md` の雛形を作ってくれる

**最初にやるべきは `CLAUDE.md` の整備である。** ここに書いた内容は毎回読まれるので、
「このプロジェクトのルール」を一度書けば毎回指示しなくて済む。

### コピペで使える CLAUDE.md の例

```markdown
# このプロジェクトについて
- 社内の請求書集計ツール。Python 3.12 / pandas を使用
- 実行は `make run`、テストは `pytest tests/` で走る

## 守ってほしいこと
- 既存のコードスタイルに合わせる(コメントの粒度・命名も周囲に揃える)
- 依存ライブラリを勝手に追加しない。必要なら理由を先に説明する
- `data/` 配下の実データは読み取り専用。絶対に書き換えない
- テストを追加せずに機能を変更しない

## やってはいけないこと
- git push、本番環境への接続、外部へのデータ送信は行わない
- 秘密情報(.env の値)を出力・ログに含めない
```

### 権限の考え方(ここが最重要)

Claude Code は**コマンドを実行するたびに許可を求める**のが既定の挙動で、
「今回だけ許可」「このコマンドは常に許可」を選べる。
一度「常に許可」にすると以後は確認なしで走るため、**何を常時許可にするかが実質的なリスク管理になる**。

| 常時許可にしてよい | 毎回確認すべき | 許可しない |
|---|---|---|
| ファイル読み取り、検索 | ファイルの書き換え | `git push`(共有ブランチへ) |
| テスト実行、lint、ビルド | `git commit` | 本番DBへの接続 |
| ローカルでの型チェック | 依存パッケージの追加 | 外部へのデータ送信、決済 |
| | ファイル・ディレクトリの削除 | 認証情報を含む操作 |

判断に迷う場合は、[AIエージェントとは何か](ai-agent-basics.md)の「権限ポリシー」の雛形と、
[Human in the Loop(人間参加型)の業務設計](../part12-business-practice/human-in-the-loop-basics.md)
の考え方をそのまま当てはめればよい。

### 使えるプラン(2026年8月時点)

| プラン | 月額 | 位置づけ |
|---|---|---|
| Pro | $17(年払い)/ $20(月払い) | 個人で試す。重い作業だと上限に当たりやすい |
| Max 5x | $100 | 日常的に使うならここから |
| Max 20x | $200 | 1日中回す使い方 |
| Team / Enterprise | シート課金(プレミアムシート) | 組織利用。管理機能・コンプライアンス対応込み |
| API(従量) | トークン課金 | CI等に組み込む場合 |

**コスト感の注意**: エージェントはファイルを読み、テストを流し、失敗して読み直すたびにトークンを消費する。
チャット利用の数十倍になることは普通にあるため、**サブスクの上限に当たる前提で計画する**。
詳しくは[生成AI利用コストの管理・予算配分](../part12-business-practice/ai-cost-management-and-budgeting.md)を参照。

### レビューのしかた

任せた結果をそのまま信じないための最低ラインは次の3つ。

1. **差分を必ず読む**(`git diff`)。特に「頼んでいないファイルが変わっていないか」
2. **テストが実際に通っているかを自分で確認する**。AIの「通りました」を信じない
3. **消えたコードを確認する**。動かすために既存の処理を消していることがある

## 注意点・よくある誤解

- **「自律的」は「無監督でよい」ではない。** レビューなしにマージすると、動くけれど筋の悪い実装、
  テストを通すためだけの実装が混ざる。**PRレビューの手間は減らない**(読む対象が人のコードからAIのコードに変わるだけ)
- **間接プロンプトインジェクションのリスクがある。** エージェントが読み込んだファイル・Issue・
  Webページに「これまでの指示を無視して〜」という文が仕込まれていると、それに従う可能性がある。
  外部から取り込んだ内容を扱う作業では権限を絞る([プロンプトインジェクションとは何か](../part04-risk-security/prompt-injection-basics.md))
- **非エンジニアが使う場合の落とし穴**: 動いているように見えるが、エラー処理がない・
  セキュリティ上問題がある、という成果物が普通に出てくる。**社外に出すもの・お金や個人情報を扱うものには使わない**
- **秘密情報**: `.env` などをAIに読ませると、その内容が出力やログに現れる可能性がある。
  読み取り対象から除外する設定を最初に入れておく
- **大きすぎるタスクを一度に投げると精度が落ちる。** 「認証機能を作って」ではなく
  「まず設計方針を3案出して」→選ぶ→「1案目で実装して」と刻む方が結果がよい
  ([タスク分解プロンプティング](../part05-prompt-engineering/task-decomposition-prompting.md))

## 最初の一歩

自分のプロジェクトで `claude` を起動し、**まず書き込みをさせずに**
「このリポジトリの構成を説明して。主要な処理の流れを図で示して」と聞いてみる。
コードベースをどれだけ正確に読めるかが分かり、任せられる範囲の見当がつく。
