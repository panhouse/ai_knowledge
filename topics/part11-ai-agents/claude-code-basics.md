# Claude Codeの基本

## これは何か

Claude Code は Anthropic 公式のコーディングエージェントで、**「このバグを直して」「この機能を追加して」と
自然文で頼むと、コードベースを自分で読み、複数ファイルを編集し、テストを走らせ、
最後にPRを出すところまで一気に進める**ツールである。

AIチャットにコードを貼って答えをもらう使い方との決定的な違いは、**人がコピペをしない**点にある。
チャットは「こう書けばいい」と教えてくれるだけで、ファイルを開いて貼り付け、動かして、
エラーを持ち帰って再度聞く往復は人がやる。Claude Code はその往復ごとAIが回す。
結果として、人の仕事は「指示を出す」と「出てきた差分をレビューする」の2点に寄る。

2026年9月時点では、確認なしで実行できる範囲を広げる「自動モード」やタスクを並列でこなす
「エージェントチーム」など、**自律度そのものを引き上げる方向の機能追加**が続いている。
便利さは増す一方でレビュー体制の設計が一段と重要になっている点は後述する。

エンジニア向けの製品だが、非エンジニアでも「社内向けの小さなツールを作る」「大量のファイルを
一括で変換する」といった用途で使われている。ただし後述のとおり、**出てきたものの妥当性を
判断できない領域では使わない**のが原則である。

## 仕組み・背景

### エージェントループ

Claude Code の中核は、[AIエージェントとは何か](ai-agent-basics.md)で扱った
「思考→ツール実行→結果観察」のループである。具体的には次を自分で選んで繰り返す。

1. ファイルを検索・読み込む(どのファイルを見るかをAIが決める)
2. ファイルを編集する
3. コマンドを実行する(テスト、ビルド、lint、git 操作)
4. 結果を見て、失敗していれば直して再実行する

「テストが落ちたら直して再実行」を人の介在なしに回せることが、チャットとの体験差を生んでいる。

### 動作する場所

2026年9月時点で、次の入口から同じエージェントエンジンを使える
([Claude Code Overview(公式)](https://code.claude.com/docs/en/overview))。

| 入口 | 主な使い方 |
|---|---|
| ターミナル(CLI) | 中心的な使い方。ネイティブインストーラで導入し `claude` で起動 |
| VS Code / JetBrains拡張 | エディタ内でインライン差分表示・@メンション・プラン確認 |
| デスクトップアプリ | macOS / Windows / Linux(Ubuntu・Debianはベータ)。差分を視覚的にレビューし、複数セッションを並列実行、定期実行の設定もできる |
| Web(claude.ai/code) | ブラウザからローカル環境なしで実行。iOS/Androidの Claude アプリからも同じセッションを継続できる |
| CI/CD | GitHub Actions・GitLab CI/CD に組み込み、PRレビューやIssueトリアージを自動化 |
| Slack | `@Claude` にバグ報告などをメンションするとPRを作って返す |
| Chrome | ブラウザ操作・実機デバッグをClaude Codeから直接行う(Claude in Chrome) |

同じ `CLAUDE.md`・設定・MCPサーバー構成がどの入口からでも共有される。

### 押さえておきたい機能概念

| 概念 | 何をするもの |
|---|---|
| **サブエージェント** | 専用のコンテキスト・権限を持つ子エージェント。読み取り専用のExplore/Plan、実装まで行うGeneral-purposeなど組み込み4種があり、Markdown+YAMLで自作もできる。[マルチエージェント・オーケストレーションの基本](multi-agent-orchestration-basics.md)参照 |
| **エージェントチーム(実験的)** | 複数のClaude Codeインスタンスを並列起動し、リード役が調整・統合する。既定は無効で環境変数での有効化が必要。トークン消費は通常セッションの約7倍にもなる |
| **ルーティン(Routines)** | クラウド側でスケジュール・API呼び出し・GitHubイベントを起点にタスクを自動実行する仕組み。`/schedule` やWeb/デスクトップから作成する |
| **フック(Hooks)** | ツール実行の前後にシェルコマンドを挟み、内容の書き換え・ブロック・ログ記録を行う仕組み(`PreToolUse`/`PostToolUse` 等) |
| **MCP** | 外部ツール(GitHub、DB、社内システム)への接続口。ツール定義は既定で遅延読み込みされ、実際に使うまでコンテキストを消費しない。[MCPの基本](../part09-api-development/mcp-basics.md)参照 |
| **サンドボックス** | Bashコマンドが到達できるファイルシステム・ネットワークの範囲をOSレベルで制限する仕組み(macOS/Linux/WSL2)。`/sandbox` で有効化 |
| **CLAUDE.md** | プロジェクト固有の前提・規約をAIに常時読ませる設定ファイル(200行程度に収め、詳細な手順はSkillsに逃がすのが推奨) |
| **Skills** | 特定作業の手順・知識を必要なときだけ読み込ませる部品。[AIエージェントのSkills機能とは何か](claude-skills-and-agent-skills-basics.md)参照 |

## 使いどころ・使い分け

### 向く仕事・向かない仕事

| 向く | 向かない |
|---|---|
| 既存コードの調査(「この処理はどこで呼ばれている?」) | 仕様そのものを決める(何を作るべきかの判断) |
| 定型的な修正の一括適用(命名変更、APIの移行) | 出てきたコードの妥当性を誰も判断できない領域 |
| テストの追加、失敗しているテストの修復 | 本番データを直接触る作業 |
| ドキュメント・コメントの整備 | 障害対応の初動(状況把握を人がやるべき場面) |
| 大量ファイルの機械的な変換・整形 | セキュリティ設計・認証周りの新規実装 |

### 他のツールとの使い分け

| こういう場合 | これを使う |
|---|---|
| 自分でコードを書きながら補完してほしい | GitHub Copilot / Cursor([Part 8](../part08-specialized-ai-tools/coding-assistant-ai-comparison.md)) |
| タスクを丸ごと任せて、結果をレビューしたい | Claude Code |
| コードではない業務(資料作成・調査)を任せたい | [Claude Cowork](claude-cowork-basics.md) |
| ChatGPT系で揃えたい | [OpenAI Codex](openai-codex-basics.md) |
| Google系・IDEのGUIで管理したい | [Google Antigravity](google-antigravity-basics.md) |

## 実務での使い方

### 始め方(ターミナルの場合)

1. ネイティブインストーラを実行する(推奨)。
   macOS / Linux / WSL: `curl -fsSL https://claude.ai/install.sh | bash`、
   Windows PowerShell: `irm https://claude.ai/install.ps1 | iex`。
   ネイティブ版はバックグラウンドで自動更新される。従来の `npm install -g @anthropic-ai/claude-code`
   も引き続き使えるが、Node.js 22以上が必要で自動更新はされない
2. プロジェクトのディレクトリに移動して `claude` を実行
3. 初回はブラウザが開いて Claude アカウントで認証する。**Pro / Max / Team / Enterprise のいずれか、
   またはConsoleのAPIキーが必要**(無料のClaude.aiアカウントだけではClaude Codeは使えない)
4. `/init` を実行すると、リポジトリを解析して `CLAUDE.md` の雛形を作ってくれる

**最初にやるべきは `CLAUDE.md` の整備である。** ここに書いた内容は毎回読まれるので、
「このプロジェクトのルール」を一度書けば毎回指示しなくて済む。

### コピペで使える CLAUDE.md の例

```markdown
# このプロジェクトについて
- 社内の請求書集計ツール。Python 3.12 / pandas を使用
- 実行は `make run`、テストは `pytest tests/` で走る

## 守ってほしいこと
- 既存のコードスタイルに合わせる(コメントの粒度・命名も周囲に揃える)
- 依存ライブラリを勝手に追加しない。必要なら理由を先に説明する
- `data/` 配下の実データは読み取り専用。絶対に書き換えない
- テストを追加せずに機能を変更しない

## やってはいけないこと
- git push、本番環境への接続、外部へのデータ送信は行わない
- 秘密情報(.env の値)を出力・ログに含めない
```

### 権限の考え方(ここが最重要。2026年9月に既定挙動が大きく変わった)

Claude Code の権限は「モード」(会話全体の既定の緩さ)と「ルール」(特定のツール・コマンドを
個別に許可/確認/拒否する設定)の2層で決まる
([Choose a permission mode(公式)](https://code.claude.com/docs/en/permission-modes))。

**2026年9月時点のモード一覧**

| モード | 確認なしで実行される範囲 | 向いている場面 |
|---|---|---|
| Manual(設定値 `default`) | 読み取りのみ | 機微な作業、見慣れないコードを1つずつ確認したい |
| Plan | 読み取りと調査コマンド。編集は計画の承認まで保留 | 変更前に方針を確認したい |
| Accept Edits(`acceptEdits`) | 読み取り、ファイル編集、`mkdir`/`mv`/`cp` 等の基本コマンド | 差分をあとでまとめてレビューしたい |
| Auto(`auto`) | ほぼすべて。ただし「分類器(classifier)」という別のAIモデルが危険そうな操作を審査してブロックする | 長時間タスクを任せ、確認疲れを減らしたい |
| Don't Ask(`dontAsk`) | 事前に許可したツールのみ。それ以外は自動で拒否 | CI・ロックダウンされた自動化 |
| Bypass Permissions | すべて確認なし | ネット接続のないコンテナ・VM内限定 |

**最大の変更点**: 従来はコマンド実行のたびに確認を求めるのが既定だったが、
**Pro / Max / Team プランでは新規セッションの既定モードが Auto に変わっている。**
Autoモードでは、Claude自身ではなく別のAIモデル(分類器)が「依頼から逸脱していないか」
「未知のインフラを触っていないか」「読み込んだファイルに仕込まれた悪意ある指示に従っていないか」
を審査し、危険と判定した操作だけをブロックする仕組みである。

Autoモードが既定で**ブロックする**ものの例: `curl | bash` のような外部コード実行、
シークレットの外部送信、本番環境へのデプロイ・マイグレーション、`git push --force`、
`terraform destroy` 等の破壊的インフラ操作、未承認PRの自己マージ。
逆に既定で**確認なしに通る**ものの例: ロックファイルに従った依存パッケージのインストール、
`.env` を読んで対応するAPIに認証情報を送る処理、読み取り専用のHTTPリクエスト、
そして**作業中リポジトリのデフォルトブランチを含む任意のブランチへのpush**。
最後の「pushが既定で通る」は特に見落としやすい変更で、共有ブランチへの誤pushを防ぎたい場合は
`permissions.deny` ルールで明示的にブロックしておく必要がある。

Autoモードは分類器による審査があるとはいえ、**「無監督でよい」という意味ではない**
(詳しくは後述の「注意点」を参照)。機微な作業やレビュー体制が整っていないチームでは、
`Shift+Tab` でManualまたはPlanモードに切り替えることを推奨する。

**もう1層の防御: サンドボックス。** Bashコマンドが到達できるファイルシステム・ネットワークの
範囲をOSレベルで制限する仕組みがmacOS/Linux/WSL2で使える。`/sandbox` で有効化でき、
権限モードとは独立して重ねて使える。

**常時許可・確認・拒否の目安**(モードを問わず、組織のルールとして決めておくとよい)

| 常時許可にしてよい | 毎回確認すべき | 明示的に拒否ルールを入れる |
|---|---|---|
| ファイル読み取り、検索 | 依存パッケージの追加 | 共有ブランチへの `git push`(既定で許可される点に注意) |
| テスト実行、lint、ビルド、型チェック | ファイル・ディレクトリの削除 | 本番DB・本番環境への接続 |
| ロックファイル通りの依存インストール | シークレットマネージャーへの書き込み | 外部へのデータ送信、決済 |
| | インフラ変更(Terraform等) | 認証情報を含む操作 |

判断に迷う場合は、[AIエージェントとは何か](ai-agent-basics.md)の「権限ポリシー」の雛形と、
[Human in the Loop(人間参加型)の業務設計](../part12-business-practice/human-in-the-loop-basics.md)
の考え方をそのまま当てはめればよい。

### 使えるプラン(2026年9月時点)

Claude Code はトークン消費に応じて課金される。サブスクの月額は「利用量込みの定額」、
Console(API)は純粋な従量課金である
([Manage costs effectively(公式)](https://code.claude.com/docs/en/costs))。

| プラン | 月額目安 | 位置づけ |
|---|---|---|
| Pro | $20(月払い)/ 年払いで実質$17前後 | 個人で試す。重い作業だと上限に当たりやすい |
| Max 5x | $100 | 日常的に使うならここから |
| Max 20x | $200 | 1日中回す使い方 |
| Team(Premiumシート) | 1シート$100(年払い)/ $125(月払い)、最低5シートから。Standardシートには含まれない | 組織利用の入口 |
| Enterprise | 個別見積り | SSO・拡張コンテキスト・監査API等のコンプライアンス対応込み |
| Console(API) | トークン従量課金 | CI等に組み込む場合 |

料金の出所について: 複数の第三者調査記事(例: [Claude Code Pricing 2026](https://duet.so/blog/claude-code-pricing))
が一致してこの金額を報告しているが、本セッションではネットワーク制限により
claude.com/pricing への直接アクセスができなかったため、契約前に必ず公式ページで再確認すること。

**利用枠の考え方**: Team/Enterpriseのシート枠は、5時間ごとに回るローリングウィンドウと
週次ウィンドウの組み合わせでリセットされ、Claudeチャット・Cowork と共有される。
上限に達すると「セッション上限」「週次上限」のメッセージが出て、`/usage-credits` で
追加利用(従量)をオンにするか、リセットを待つ運用になる。

**コスト感の実測値(Anthropic公式)**: エンタープライズ導入全体の平均は
**開発者1人1日あたり約$13**、**月$150〜250**で、90%のユーザーは1日$30未満に収まる
([Manage costs effectively(公式)](https://code.claude.com/docs/en/costs))。
チャット利用の数十倍になることは珍しくないため、小規模なパイロットで基準値を作ってから
展開するのが安全。`/usage` でセッションごとのトークン消費、`/insights` で使い方の傾向を
確認できる。詳しくは
[生成AI利用コストの管理・予算配分](../part12-business-practice/ai-cost-management-and-budgeting.md)
を参照。

### レビューのしかた

任せた結果をそのまま信じないための最低ラインは次の3つ。Autoモードの分類器はあくまで
「明らかに危険な操作」を止める安全網であり、**設計判断の妥当性までは審査しない**点に注意する。

1. **差分を必ず読む**(`git diff`)。特に「頼んでいないファイルが変わっていないか」
2. **テストが実際に通っているかを自分で確認する**。AIの「通りました」を信じない
3. **消えたコードを確認する**。動かすために既存の処理を消していることがある

## 注意点・よくある誤解

- **「自律的」「分類器が審査する」は「無監督でよい」ではない。** レビューなしにマージすると、
  動くけれど筋の悪い実装、テストを通すためだけの実装が混ざる。**PRレビューの手間は減らない**
  (読む対象が人のコードからAIのコードに変わるだけ)。Autoモードの分類器は「ユーザーの依頼から
  明らかに逸脱した操作」を止める設計であり、依頼の範囲内で品質の低い実装をすることまでは防げない
- **間接プロンプトインジェクションのリスクは分類器だけでは防ぎきれない。** 分類器が審査するのは
  ユーザーの発言とツール呼び出しの列であり、**ツールの実行結果(読み込んだファイルの中身)そのものは
  分類器に渡らない**。したがって、読み取り専用HTTPリクエストのように「通常業務に見える」操作に
  偽装した攻撃は今も見逃されうる。外部から取り込んだ内容を扱う作業では権限を絞る運用を続ける
  ([プロンプトインジェクションとは何か](../part04-risk-security/prompt-injection-basics.md))
- **Autoモードは `.env` を読んで対応するAPIに送る処理を既定で確認なしに許可する。**
  想定した送信先であれば問題ないが、`.env` に用途の異なる複数のシークレットが混在していると
  意図しない送信が起きうる。読み取り対象から除外するか、`permissions.deny` で明示的に止めておく
- **非エンジニアが使う場合の落とし穴**: 動いているように見えるが、エラー処理がない・
  セキュリティ上問題がある、という成果物が普通に出てくる。**社外に出すもの・お金や個人情報を扱うものには使わない**
- **大きすぎるタスクを一度に投げると精度が落ちる。** 「認証機能を作って」ではなく
  「まず設計方針を3案出して」→選ぶ→「1案目で実装して」と刻む方が結果がよい
  ([タスク分解プロンプティング](../part05-prompt-engineering/task-decomposition-prompting.md))

## 最初の一歩

自分のプロジェクトで `claude` を起動し、ステータスバーに表示されるモード
(`⏸ manual mode on` / `⏵⏵ auto mode on` など)をまず確認する。Pro/Max/Teamでは既定でAutoモードに
入っているため、`Shift+Tab` でManualモードに切り替え、**まず書き込みをさせずに**
「このリポジトリの構成を説明して。主要な処理の流れを図で示して」と聞いてみるとよい。
コードベースをどれだけ正確に読めるかが分かり、任せられる範囲の見当がつく。
