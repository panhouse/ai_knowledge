# AIエージェントの自律度レベルと権限設計の基本

## これは何か

「エージェントにどこまで任せるか」は、製品を選ぶ前に決めておくべき最も重要な設計事項である。
**任せる範囲(自律度)**と**チェックを入れる場所(権限設計)**を先に言葉にしておかないと、
「怖くて全部確認してしまい、結局チャットと同じ手間になる」か
「無審査で通してしまい事故が起きる」のどちらかに振れやすい。

[AIエージェントとは何か](ai-agent-basics.md)では権限ポリシーのテンプレート例を紹介しているが、
本ページは一歩進んで、**自律度を段階的に分類する枠組み**と、
**個々の操作の権限をどう決めるかという体系的な考え方**を扱う。

## 仕組み・背景

### 自律度は5段階で考えると整理しやすい

自動運転車のSAEレベル(0〜5)分類と同じ発想で、AIエージェントの自律度も段階的に整理できる。
厳密な業界標準ではないが、社内で「どこまで任せるか」を議論する共通言語として使いやすい。

| レベル | 呼び方 | 何が起きるか | 例 |
|---|---|---|---|
| L0 | 手動 | AIは提案するだけ。実行は人間 | 通常のチャット回答 |
| L1 | 補助実行 | 1手ごとに人間が承認してから実行 | Claude Codeの既定モード(コマンドごとに確認) |
| L2 | 条件付き自動実行 | 決めておいた種類の操作は無承認、それ以外は確認 | Claude Codeの`acceptEdits`(編集は自動、コマンドは確認) |
| L3 | 目標委任 | ゴールだけ渡し、達成までの手順はAIが決めて実行。**要所でのみ**人間が確認 | Claude Cowork、ChatGPT Work、Gemini Spark |
| L4 | 完全自律 | 事前に決めた範囲内は人間の介在なしで継続的に稼働 | Claude Code Routines、定期実行するエージェントパイプライン |

**レベルが上がるほど速いが、事故の被害も大きくなりうる。** 実務では「L4を目指す」ことが目的ではなく、
**その業務のリスクに見合ったレベルを選ぶ**ことが目的になる。

### 監視のしかたも3種類ある

自律度のレベルと別に、**人間がいつ関与するか**という軸もある。

| 呼び方 | 人間の関与のタイミング | 向く場面 |
|---|---|---|
| Human-in-the-Loop(HITL) | 実行**前**に承認しないと先に進まない | 取り消せない操作、影響範囲が大きい操作 |
| Human-on-the-Loop(HOTL) | 実行**中・後**に監視し、必要なら介入・停止する | 中リスクで、スピードが重要、かつ後から取り消せる操作 |
| Human-out-of-the-Loop | 事後ログの確認のみ | 低リスクで反復頻度が高い操作(定型レポート作成など) |

業務内の一連の作業でも、**操作ごとにこの3つを使い分けるのが実務上の基本**である
(例: 調査・ドラフト作成はHuman-out-of-the-Loop、送信・決済はHuman-in-the-Loop)。

## 使いどころ・使い分け

### 権限設計の3ステップ

```
1. 操作を洗い出す
   そのエージェントが実行しうる操作を具体的にリストアップする
   (読み取り/書き込み/送信/削除/決済/外部通知 など)

2. 各操作を「取り消せるか」「影響範囲」で3段階に分ける
   - 承認不要: 読み取り、社内向けドラフト作成など、失敗しても被害が小さい/簡単に戻せる
   - 要所で確認: ファイルの上書き、社外に見える文書の作成など
   - 必ず事前承認: 送信・決済・削除・本番環境への書き込みなど、取り消せない/影響が大きい

3. 業務のリスクに見合った自律度レベルを選ぶ
   上記の分類に応じて、L1〜L4のどこで運用するかを決める
```

このステップは、[AIエージェントとは何か](ai-agent-basics.md)の権限ポリシーテンプレートと
組み合わせて使うと、テンプレートの「承認不要」「承認必須」の欄を具体的に埋められるようになる。

### 「取り消せるか」を優先する判断軸にする

権限設計で迷ったときは、**「間違っていたときに、いつ・誰が気づき、どのくらいのコストで元に戻せるか」**
を最優先の判断軸にする。影響が社内に留まり、翌日には気づいて修正できる業務ほど自律度を上げやすく、
社外に出る・お金が動く・削除を伴う操作ほど承認を必須にする。

## 実務での使い方

### 主要ツールでの権限設定の対応(2026年8月時点)

| ツール | 権限の粒度 | 設定場所 |
|---|---|---|
| [Claude Code](claude-code-basics.md) | コマンド単位で「今回だけ許可」「常に許可」を選択。`default`/`acceptEdits`/`bypassPermissions`のモード切替、`auto`モード(Shift+Tab) | セッション中の確認プロンプト、`--permission-mode`フラグ |
| [OpenAI Codex](openai-codex-basics.md) | 承認モード(suggest/auto-edit/full-auto)とサンドボックスモード(read-only/workspace-write/danger-full-access)を組み合わせ | `~/.codex/config.toml`、CLIフラグ |
| [Google Antigravity](google-antigravity-basics.md) | エディタの承認済みツール制約、ブラウザ操作時の権限確認 | Agent Managerの設定 |
| [Claude Cowork](claude-cowork-basics.md) | フォルダ・外部ツール単位でアクセス範囲を明示的に選択。削除操作は明示承認必須 | 作業開始時のフォルダ・ツール選択画面 |

**「常時許可」に設定した操作が実質的なリスク管理そのものになる。** どのツールでも、
一度「常に許可」にした操作はその後確認なしで実行され続けるため、
設定直後だけでなく定期的に見直すことが実務上重要になる。

### コピペで使える権限ポリシーの書き出し方

```
## このエージェントに承認なしで実行してよい操作
- (例: 社内向けドラフトの作成、ファイルの読み取り、Web検索)

## 実行前に必ず確認を取る操作
- (例: 社外に送るメール・文書の最終版作成、既存ファイルの上書き)

## このエージェントには絶対にやらせない操作
- (例: 決済、本番環境への書き込み、認証情報を含む操作)
```

エージェントに作業を渡す前に、この3行を1分で書き出す習慣をつけるだけで、
「なんとなく怖いから使わない」と「気づかず事故る」の両方を避けやすくなる。

## 注意点・よくある誤解

- **自律度を上げること自体がゴールではない**: L4(完全自律)が最も進んでいるわけではなく、
  低リスクな定型業務ではL4が適切、影響が大きい業務ではL1〜L2に留めるのが正しい判断になる
- **「常に許可」の運用は積み重なる**: 便利さから「常に許可」を増やしていくと、
  気づかないうちに権限が広がっていく(スコープクリープ)。定期的な棚卸しが必要
- **監視(HOTL)は「見ているから安全」ではない**: 実行速度が人間の確認速度を上回ると、
  問題が起きてから気づくまでの間に被害が広がることがある。重要な操作はHITL(事前承認)に留める
- **ツールが用意する既定の権限モードをそのまま使わない**: 既定値は汎用的な設定であり、
  自社の業務のリスクに合わせて「常に許可」の範囲を狭める/広げる調整が必要になる
- **セキュリティはPart 4に丸投げしない**: 権限の過剰付与・認証情報の扱いはエージェント固有のリスクであり、
  [情報漏洩を防ぐデータ管理](../part04-risk-security/information-leakage-prevention.md)や
  [プロンプトインジェクションとは何か](../part04-risk-security/prompt-injection-basics.md)と
  合わせて各エージェントの運用ルールに組み込む

## 最初の一歩

いま使っている(または導入を検討している)エージェントについて、
上記の「承認なしで実行してよい操作」「必ず確認を取る操作」「絶対にやらせない操作」の3行を
実際に書き出してみる。書き出せない操作があれば、それがそのエージェントを本格導入する前に
詰めておくべき論点である。
