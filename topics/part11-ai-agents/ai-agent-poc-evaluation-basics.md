# AIエージェント導入PoCの評価指標・進め方の基本

## これは何か

AIエージェントのPoC(概念実証、Proof of Concept)は、**「動くかどうか」ではなく
「本番運用に進める価値があるかどうか」を判断するための検証**である。
2026年3月の調査では、78%の企業がパイロット導入を実施した一方、
本番運用に到達したのはわずか14%と報告されており、多くの企業が
**「PoC地獄」(検証はしたが本番に進めない状態)**から抜け出せていない。

[主要AIエージェントの比較と選び方](ai-agent-tools-comparison.md)では
PoCの進め方を簡潔に扱っているが、本ページでは**PoCで何を測るべきか(評価指標)**を
フェーズ別に掘り下げる。

## 仕組み・背景

### PoCは実験ではなくゲートである

PoC地獄に陥る典型的な原因は、「検証期間」「評価指標」「成功と判断する基準」を
**先に決めずに始めてしまう**ことである。PoCは自由な実験の場ではなく、
「続行するか、止めるか」を判断する関所(ゲート)として設計する必要がある。

### 従来のLLM評価指標では測れない

チャットボットの評価で使われていたパープレキシティ・BLEUスコア・単純な「高評価/低評価」
フィードバックは、自律的に複数のツールを呼び出しながら動くAIエージェントの評価には
**不十分**である。エージェントは「思考して行動する一連の手順(トラジェクトリ)」を持つため、
最終的な出力だけでなく、**その手順自体が正しかったか**を評価する必要がある。

## 使いどころ・使い分け

### フェーズによって測る指標が変わる

PoC期・本番初期・定常運用では、優先すべき指標が根本的に異なる。同じ指標をいつまでも
使い続けるのではなく、フェーズが進むごとに切り替える。

| フェーズ | 期間の目安 | 重視する指標の種類 |
|---|---|---|
| **PoC期** | 0〜3ヶ月 | 基本的な動作確認(ツール選択精度、計画遵守率)+価値仮説の検証 |
| **本番初期** | 3〜9ヶ月 | スケール前提の信頼性(一貫性、コスト)+定着状況 |
| **定常運用** | 9ヶ月以降 | 運用効率の継続改善+年間ROIの確定 |

### 3本柱で指標を整理する

技術指標(信頼性)・利用指標(定着率)・ビジネス指標(ROI)の3本柱で考えると、
偏った評価に陥りにくい。

**1. 信頼性・運用効率**

| 指標 | 内容 | PoC期の目安 |
|---|---|---|
| ツール選択精度 | 意図した通りのツールを呼び出せているか | 80%以上 |
| 引数ハルシネーション率 | ツール呼び出し時のパラメータが捏造されていないか | 5%以下 |
| 計画遵守率 | 最初に立てた計画通りの順序で実行できているか | 90%以上 |
| 成功タスクあたりのコスト(本番期) | 「トークンあたり」ではなく「成功1件あたり」で計算する(失敗を含めた実質コスト) | — |

**2. 定着率・利用パターン**

| 指標 | 内容 |
|---|---|
| ユーザーセンチメント(PoC期) | アンケート・ヒアリングで「使いたいか」を定性的に確認する |
| 出力摩擦(本番期) | エージェントの成果物を、人間がどれだけ手直し・差し戻ししているか(そのまま承認/編集して承認/差し戻しの比率) |
| 検証時間 | エージェントの完了から人間が承認するまでの時間。手動作業より短くなっているか |

**出力摩擦の差し戻し比率が高い(目安として25%超)場合**、エージェントに主導権を渡す
設計(プロアクティブ型)が早すぎる可能性がある。人間が主導し、エージェントが補助する
設計(リアクティブ型)に戻すことも検討する。

**3. ビジネス価値(ROI)**

| 指標 | 測り方 |
|---|---|
| 価値実現までの時間の加速 | 「導入前にかかっていた時間」対「導入後にかかる時間」を比較する(例: 資料修正30分→8分) |
| 運用コストの削減 | 削減できた手動作業の工数×時給で積算する |
| 新しい能力の解放 | 従来は人手で不可能だった作業(全件監査など)が可能になったか |

PoC期は「価値実現までの時間の加速」を1つのパイロット業務で示すだけで十分であり、
本番初期以降にコスト削減額・収益インパクトの定量化を進める。
効果測定の全体的な考え方は[生成AI導入のROI測定・効果測定の考え方](../part12-business-practice/ai-roi-measurement.md)を参照。

## 実務での使い方

### PoC設計の進め方

```
1. 検証する業務を1つに絞る(全社展開ではなく1職種・1業務)
2. 検証期間を決める(目安: 4〜8週間)
3. 上記3本柱から、この業務で意味のある指標を3〜5個選ぶ
4. 「継続」「本番初期へ移行」「中止」の判断基準を、検証開始前に数値で決めておく
5. 同じタスクを複数のツールで試す場合は、同じ評価基準で横並び比較する
6. 失敗パターン・想定外の挙動を記録する(社内ガイドラインの材料になる)
```

**判断基準を検証後に決めない。** 結果を見てから基準を後付けすると、
「なんとなく良さそうだから続ける」という水掛け論になりやすい。

### 本番初期に切り替えるタイミング

PoC期の指標(ツール選択精度80%以上、計画遵守率90%以上など)を満たし、
かつパイロット業務で明確な時間削減効果が確認できたら、本番初期の指標
(一貫性スコア、成功タスクあたりコスト、出力摩擦)に切り替える。
指標を切り替えずにPoC期の基準で運用を続けると、スケールに伴う新しい問題
(コストの跳ね上がり、摩擦の蓄積)に気づけない。

## 注意点・よくある誤解

- **「動いた」で判断を終わらせない**: PoCの目的は「技術的に動作するか」の確認ではなく、
  「本番運用に進める価値があるか」の判断である。動作確認だけで終わるPoCは、
  そのまま忘れられて次のPoCが始まる「PoC地獄」を招く
- **コストは「トークンあたり」で見ない**: 失敗して再試行するたびにコストが積み重なるため、
  「成功1件あたりの実質コスト」で評価しないと、実際の運用コストを過小評価する
- **オーナーシップを曖昧にしない**: 「エージェントが主導し、人間が確認する」設計にすると、
  誰も最初に動かない「傍観者効果」が起きて検証時間が伸びる。
  「人間が主導し、エージェントが補助する」形にすると承認が速くなりやすい
- **PoCの成功基準を後から決めない**: 検証を始める前に、続行・中止の基準を数値で決めておく。
  結果を見てから基準を作ると、恣意的な判断になりやすい
- **1つの成功事例で全社展開を決めない**: パイロット業務での成功は、その業務特有の条件
  (データの構造化度、担当者の慣れなど)に依存している場合がある。展開前に別の業務でも
  同様の効果が出るかを確認する

## 最初の一歩

現在検証中(または検証予定)のAIエージェント活用について、上記3本柱から
指標を3つだけ選び、「この数値がいくつになったら本番に進める」を今日中に数値で書き出す。
基準を先に決めることが、PoC地獄を避ける最初の一歩になる。
