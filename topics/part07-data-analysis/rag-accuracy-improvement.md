# RAGの精度を上げる方法

## これは何か

RAGを導入した直後によくある悩みが「動いてはいるが、思った通りの答えが返ってこない」というものだ。同じ質問をしても回答の内容が毎回微妙にブレる、資料に書かれているはずの内容が抜け落ちる、聞いていないことまで混ざって的外れな回答になる、といった症状が典型的。こうした問題の原因は、AIモデルそのものの性能ではなく、検索の手前にある「資料の切り分け方」「検索のやり方」「検索結果の並べ替え」「質問文の扱い方」「絞り込み条件」といった、実は利用者側が調整できるレバーにあることが多い。本ページは、[RAG(検索拡張生成)の基本](rag-basics.md)で説明したチャンク化・埋め込み・検索・生成という基本フローを前提に、実際に精度を上げるために触れる具体的な改善手法と、症状に応じてどれを試すべきかを整理する。

## 仕組み・背景

RAGの検索精度を左右する主なレバーは次の5つ。いずれも内部の数式を理解する必要はなく、「何をどう変えると何が起こるか」だけ押さえておけば使いこなせる。

1. **チャンキング戦略の調整**: 資料を切り分ける単位(チャンクサイズ)や、チャンク同士の重なり(オーバーラップ)を見直す
2. **ハイブリッド検索**: キーワード検索とベクトル検索(意味の近さで探す検索)を組み合わせる
3. **リランキング(再採点)**: 検索直後の候補チャンクを、専用モデルで「質問との関連度」に応じて並べ替え直す
4. **クエリ書き換え・拡張**: ユーザーの質問文を、検索に適した形にAIが言い換えてから検索する
5. **メタデータフィルタリング**: 部門・日付・文書種別などの属性で、検索対象そのものを事前に絞り込む

### チャンキング戦略の調整

チャンクサイズが大きすぎると、1チャンクに複数の話題が混在し、聞いていない内容まで検索結果に混ざってAIが混乱する。小さすぎると、文脈が途切れて質問の意図を正確に読み取れなくなる。どちらの症状が出ているかを見極めて、サイズとオーバーラップ(チャンクの境界をまたぐ文脈を保つための重なり幅)を反対方向に調整するのが基本的な対処になる。

### ハイブリッド検索

埋め込みモデルによるベクトル検索(意味の近さで探す)は表記ゆれには強いが、型番・法令名・固有名詞のような「完全一致」が重要な検索には弱い。逆に、BM25(単語の出現頻度に基づく古典的なキーワード検索アルゴリズム)は完全一致には強いが表記ゆれに弱い。両方を同時に実行し、RRF(Reciprocal Rank Fusion、複数の検索結果の順位を統合して1つの順位に変換する計算方法)などで結果を統合するのがハイブリッド検索。海外の比較検証では、ハイブリッド検索単体よりも「ハイブリッド検索+リランキング」の組み合わせの方が、検索結果の上位に正解が来ているかを測る指標(MRR)で意味検索単体より優位になる傾向が報告されている。

### リランキング(再採点)

検索の1段目でいったん候補を広めに集め(たとえば上位数十件)、Cohere RerankやJina Reranker、BGE rerankerなどの専用モデル(クロスエンコーダー)で「質問との関連度」を再計算し、上位数件だけをAIに渡す2段階方式。1段目の検索(ベクトル検索・キーワード検索)だけでは、意味が近いだけで的外れな候補が上位に紛れ込むことがあるため、これをもう一段絞り込む役割を持つ。

### クエリ書き換え・拡張

ユーザーの質問文が、そのままでは資料の言葉づかいと噛み合わないことがある。特に会話の途中で「それ」「さっきの件」のような指示語を含む質問は、そのまま検索してもヒットしにくい。検索の手前に「質問文を、指示語を解消した検索向けの文に言い換える」処理を1段挟むことで的中率を上げられる。

### メタデータフィルタリング

「部門」「文書の有効期限」「文書種別」などの属性(メタデータ)を文書に付与しておき、検索の前段でその属性による絞り込みをかける方法。ベクトル検索の対象範囲そのものを事前に減らせるため、同じ単語を含むが無関係な部門の文書などが紛れ込む余地を減らせる。

## 使いどころ・使い分け

どのレバーを試すべきかは、実際に出ている症状から逆引きするのが早い。

| 症状 | 疑われる原因 | 試す対処 |
|---|---|---|
| 質問のたびに回答の粒度がバラつく、資料に書かれている内容が抜け落ちる | チャンクが小さすぎて文脈が途切れている | チャンクサイズを大きくする、オーバーラップを増やす、親子チャンクモードにする |
| 聞いていない話(別の休暇制度など)まで混ざって的外れな回答になる | チャンクが大きすぎて複数の話題が1チャンクに混在している | チャンクサイズを小さくする、オーバーラップを減らす |
| 型番・法令名・固有名詞で聞くとヒットしないが、言い換えると当たる | ベクトル検索のみで完全一致に弱い | ハイブリッド検索に切り替え、重み設定でキーワード側を強める |
| 「有休」で聞くと「年次有給休暇」の資料がヒットしない(表記ゆれに弱い) | キーワード検索(経済的インデックス)のみで意味の近さを見ていない | 高品質インデックス+ベクトル検索、またはハイブリッド検索に切り替える |
| 文書量が多いナレッジで、上位の検索結果に関連度の低いチャンクが混ざる | 検索直後の順位をそのまま採用しており、再採点していない | リランキングモデルを有効化する |
| 会話の後半で指示語を含む質問がヒットしない、話が続くと的外れになる | 検索クエリが指示語のまま資料と比較され、意味的な手がかりが薄い | クエリ書き換え(検索前に質問文をAIで言い換える)を挟む |
| 同じ単語を含む複数部門の同名文書が混在してヒットする | 検索範囲がナレッジベース全体で絞られていない | メタデータ(部門・文書種別・日付など)でフィルタリングする |
| 目次ページや免責事項ばかりが検索結果に出る | 定型文・ノイズがチャンク化されている | 資料からノイズを削る、FAQはQ&A形式に変換する |
| 何が効いているのか分からない、印象で良し悪しを判断している | 定量的な評価の仕組みがない | 想定質問セット(ゴールデンセット)を作り、変更前後をスポットチェックで比較する |

改善は複数のレバーを同時に触ると何が効いたか分からなくなるため、上から順に「コストが低いもの」から1つずつ試すのが基本方針になる。目安としては、①資料のノイズ除去・Q&A化(設定変更不要) → ②チャンクサイズの調整 → ③ハイブリッド検索 → ④リランキング → ⑤クエリ書き換え → ⑥メタデータフィルタリング → ⑦評価の仕組み化、の順で着手すると無駄が少ない。

## 実務での使い方

ChatGPTのプロジェクトやNotebookLMなど手軽なツールは、これらの設定を利用者側で調整できないことが多い(自動で最適化される代わりに手を入れられない)。ハイブリッド検索・リランキング・メタデータフィルタリングを自分で細かく調整したい場合は、Dify(ノーコードでAIアプリを組み立てられるプラットフォーム)のような、ナレッジベースの検索設定を公開しているツールを使う必要がある。ナレッジベースの作成そのものの手順は[DifyでのRAG実装](../part10-nocode-lowcode/dify-rag-implementation.md)で解説済みのため、以下は精度改善のレバーに絞って設定場所を示す。

### Difyでハイブリッド検索とリランキングを設定する

1. Difyの管理画面で「ナレッジ」→対象のナレッジベースを開き、「設定」タブの「検索設定」を開く
2. 「検索方法」を「ベクトル検索」から「ハイブリッド検索」に切り替える
3. リランキングモデルを使わない場合は、その下の「重み設定(Weighted Score)」のスライダーで、セマンティック(意味)優先とキーワード優先の配分を調整する。型番や固有名詞の検索が多いならキーワード側を強める
4. 精度を優先するなら「Rerankモデル」をオンにし、事前に「設定」→「モデルプロバイダー」で登録したリランキングモデル(Cohere・Jina AIなど)を選択する。Top-K(取得件数)とスコア閾値は、このリランキングモデルを有効にしたときのみ効果を持つ
5. 画面右側の「検索テスト」タブに実際の質問文を入力し、狙った文書が上位に出るようになったかを変更前後で見比べる

### Difyでクエリ書き換えを組み込む(LLMノードを1段挟む)

Difyの検索設定そのものにはクエリ書き換え機能は用意されていないため、ワークフロー上でLLMノードを使って自作する。

1. 「スタジオ」でチャットフローを開き、「開始」ノードと「知識検索(Knowledge Retrieval)」ノードの間に新しく「LLM」ノードを追加する
2. このLLMノードのプロンプトに「これまでの会話履歴を踏まえ、ユーザーの直近の質問を、指示語を使わず検索に適した一文に書き換えてください」のように指示し、出力変数(例:`rewritten_query`)を作る
3. 「知識検索」ノードの「クエリ変数」を、既定の`sys.query`からこのLLMノードの出力変数に変更する
4. 「実行」でステップ実行し、書き換え後のクエリで意図した文書がヒットするようになったかを確認する

### Difyでメタデータフィルタリングを設定する

1. 「ナレッジ」→対象のナレッジベースの文書一覧で、メタデータフィールドを追加する(「文字列」「数値」「時間」の3種類から選べる。例:文字列で「部門」、時間で「有効期限」)
2. 各文書に対して、追加したメタデータの値を設定する(一括編集も可能)
3. 知識検索ノードの設定、またはナレッジベースの検索設定で、メタデータフィルターを「自動モード」(ユーザーの質問文からAIが条件を自動抽出)か「手動モード」(条件を自分でAND/ORで指定)から選ぶ
4. 手動モードの場合、「部門=人事部」のような条件を設定すると、その条件に合致する文書だけが検索対象になる。複数部門で同名の規程がある場合など、絞り込みが効果を発揮する

### 資料の整形(アップロード前チェックリスト)

チャンキング・ハイブリッド検索・リランキングをどれだけ調整しても、元の資料にノイズが多ければ効果は限定的になる。アップロード前に以下を確認するとよい。

- 目次・ヘッダー/フッター・ページ番号・免責事項などの定型文を本文から削る(検索結果がこれらの定型文ばかりになるのを防ぐ)
- 見出しを整理し、1見出し=1トピックになるよう構成を揃える(チャンク分割の境界が見出しと揃いやすくなる)
- FAQやマニュアルは、可能な限り「質問文」と「回答」のペア形式(Q&A形式)に整形する。ユーザーの質問文とベクトル的に近くなりやすく、ヒット率が上がりやすい(詳しくは[RAGの基本](rag-basics.md)の注意点を参照)

### 精度を評価する(スポットチェックの仕組み化)

設定を変えても「良くなった気がする」で終わらせず、次の手順で定量的に比較する。

1. 実際に聞かれそうな質問と、その正解(または正解が書かれている資料の箇所)を20〜30件程度のセットにしてスプレッドシートにまとめる(いわゆる「ゴールデンセット」)
2. 各質問をRAGツールに投げ、(a)正しいチャンクが検索結果に出たか、(b)そのチャンクをもとに正しい回答が生成されたか、を◯×で記録する
3. ×になった質問を「検索の失敗(そもそも該当箇所が検索結果に出てこない)」と「生成の失敗(該当箇所は出ているのに回答が違う)」に分類する。前者はチャンキング・ハイブリッド検索・リランキング・メタデータ側の対処、後者はLLMノードのプロンプト側の対処が効きやすい
4. 資料やチャンク設定を変更するたびに、同じ質問セットで再チェックし、◯の件数が増えたかを確認する(勘や印象ではなく同じ基準で比較する)
5. より厳密に評価したい場合は、RAGAS(Context Precision・Faithfulness・Answer Correctnessなどの指標を自動計算するオープンソースの評価ライブラリ)やLLM-as-a-judge(別のAIに採点させる方法)といった自動評価の仕組みもある。ただしLLM-as-a-judgeは実行ごとに評価がぶれることがある。業務担当者はまず手作業のスポットチェックから始めれば十分で、件数が増えて手作業が追いつかなくなった段階でエンジニアに自動評価の導入を相談するとよい

## 注意点・よくある誤解

- **ハイブリッド検索・リランキングは「有効にすれば必ず精度が上がる」わけではない**: 資料が少量で表記が統一されている場合は効果が薄く、リランキングは検索のたびに追加のモデル呼び出しが発生するため応答速度とコストがやや増える。まず症状を確認し、当てはまるレバーだけを試す
- **複数のレバーを同時に変えない**: チャンクサイズ・検索方法・リランキングなどを一度にまとめて変更すると、どれが効いたのか分からなくなる。1つ変えるごとに検索テストや評価セットで確認する
- **クエリ書き換えは応答が遅くなるトレードオフがある**: 書き換え用のLLM呼び出しが1段増えるため、会話が長くなるほど効果が出やすい一方、回答までの時間が数秒延びることがある
- **メタデータフィルタリングは付け忘れると機能しない**: 新規文書に必ずメタデータ(部門タグなど)を設定する運用ルールを決めておかないと、フィルター自体が空振りする
- **評価用の質問セットは作って終わりにしない**: 実際に社員から「回答が違った」と報告された質問を追加していくと、実態に近い評価に育っていく

## 最初の一歩

今使っているRAGツールで、実際によく聞かれる質問を5〜10個書き出し、期待する回答と実際の回答を比較してみる。ズレていた場合は、上記の診断テーブルで最も当てはまりそうな症状を1つ選び、対応するレバーだけをまず1つ試してみる。
