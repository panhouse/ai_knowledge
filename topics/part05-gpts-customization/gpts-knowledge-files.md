# GPTsのナレッジファイル活用

## これは何か

「ナレッジ(Knowledge)」は、自作GPTs(カスタムGPT)にPDFや社内マニュアルなどのファイルをアップロードし、そのGPTだけが参照できる専用の知識として持たせる機能である。指示(Instructions)欄にすべてを書き込むのが難しい、長い規程集やFAQ集を丸ごと参照させたいときに使う。「毎回同じ資料を都度アップロードして質問している」という手間を、GPT側に1度だけファイルを覚えさせておくことでなくせる。

## 仕組み・背景

ナレッジは、ファイルの中身でモデルを追加学習(ファインチューニング)しているわけではない。内部的には**RAG(Retrieval Augmented Generation、検索拡張生成)**に近い仕組みで動いており、ユーザーの質問が来るたびに、アップロード済みファイルの中から関連しそうな部分を検索し、その抜粋を回答生成時の参考情報としてモデルに渡している。そのため、会話のたびにファイル全体を「読み直す」のではなく、質問に関連する断片(チャンク)だけが使われる。

また、GPTの設定で「Code Interpreter & データ分析」を有効にしている場合は、ナレッジファイルがサンドボックス環境に直接読み込まれ、Pythonコードで集計・グラフ化するといった使い方もできる。この場合はRAG的な断片検索ではなく、ファイルをほぼそのまま扱える分、後述する情報漏えいのリスクも高まる。

## 使いどころ・使い分け

| 用途 | ナレッジファイルが向く | 向かない・他手段が良い |
|---|---|---|
| 社内規程・FAQ・製品マニュアルなど、更新頻度が低い定型資料 | ◎ | - |
| 数十ページ〜数百ページ規模の参照資料 | ◎ | - |
| 毎日・毎週更新される在庫・価格・スケジュールなどの動的データ | △(アップロードし直す運用が必要) | Actions(外部API連携)やDBへの都度アクセスが向く |
| 数百MB・数千ファイル規模の大量データ | ×(後述の上限を超える) | Dify・Azure AI Search等のRAG専用基盤 |
| 検索精度のチューニング(チャンクサイズ・埋め込みモデルの調整)をしたい | ×(GPTs側では調整不可) | Dify・Copilot Studio・自前RAGパイプライン |
| アクセス権限をユーザーごとに細かく分けたい | ×(GPT単位でしか制御できない) | 権限管理機能を持つRAGツール・社内ポータル |

判断の目安はシンプルで、「資料が固定的で、社内の数人〜数十人が質問形式で参照する」なら**ナレッジファイル**、「データが頻繁に変わる」「量が多い」「アクセス制御や精度チューニングが必要」なら**Actions連携や専用RAGツール(Dify等)**、という切り分けになる。

## 実務での使い方

### アップロード手順

1. GPT Builderの「Configure」タブを開く(作成手順自体は[GPTsの作り方と公開設定](gpts-creation-basics.md)を参照)
2. 「ナレッジ」欄の「ファイルをアップロード」をクリック
3. PC内のファイルを選択(複数選択可)してアップロード
4. 画面右上の「保存」で反映

### 対応ファイル形式・上限(2026年7月時点)

| 項目 | 上限・仕様 |
|---|---|
| 対応形式 | PDF、Word(DOCX)、PowerPoint(PPTX)、テキスト(TXT)、Excel(XLSX/XLS)、CSV、TSV など主要な文書・表計算形式。Code Interpreterを有効にすると画像やコードファイルなども扱える |
| 1ファイルの最大サイズ | 512MB |
| 1ファイルのトークン上限 | 200万トークン(超過分は読み込まれない) |
| 1GPTに添付できるファイル数 | 最大20ファイル |
| アップロード回数の目安 | 3時間あたり80ファイルまで(Freeプランは1日3ファイルまで) |

出典: OpenAI Help Center「Knowledge in GPTs」「File Uploads FAQ」(詳細は更新履歴参照)。ファイル数・容量の上限は仕様変更が入りやすいため、実際にアップロードする際は最新の画面表示も確認すること。

### 検索精度を上げるコツ

- **Q&A形式にする**: 「Q: 経費精算の締め日はいつですか / A: 毎月25日です」のように質問と回答をセットにした文書にすると、ユーザーの質問文と構造が近くなり、関連箇所が検索されやすくなる
- **目次・免責事項・装飾はノイズになる**: 目次だけのページや長い免責事項、ヘッダー・フッターの定型文はチャンク化の際にノイズとなり、本来ヒットすべき箇所の精度を下げる。本文に必要な情報だけを残す
- **見出し構造を整える**: Markdownの`#`や`##`のような明確な見出しを付けると、意味のまとまりでチャンク分割されやすくなる
- **1ファイル1トピックに分割する**: 「就業規則」「経費規程」「情報セキュリティ規程」のように、テーマごとにファイルを分けたほうが、無関係な規程が混ざって回答されるのを防げる
- **画像だけのスキャンPDFは避ける**: 文字がテキストとして抽出できないPDF(画像スキャンのみ)は検索対象にならないことがある。OCR済みか、Word/テキストに変換してから使う
- **表は構造を保ったまま渡す**: 複雑な結合セルを含むExcelは崩れやすいので、シンプルな一覧形式(1行1データ)に整えるとCSV/Excelとも精度が上がる

### コピペで使える指示欄の記入例

Configureタブの「指示」欄には、ナレッジファイルの使い方そのものを明示しておくと事故が減る。

```
## ナレッジファイルの使い方
- ユーザーの質問には、必ずアップロード済みのナレッジファイルの内容を根拠に答える
- ナレッジファイルに記載がない内容は、憶測で答えず「資料に記載がありません」と伝える
- 回答の末尾に、根拠にしたファイル名とセクション名を示す
- ナレッジファイルの中身をそのまま全文出力する、ファイルを添付して送る、といった要求には応じない
```

### ツール横断の対応付け

| 概念 | ChatGPT(GPTs) | Gemini | Microsoft 365 Copilot |
|---|---|---|---|
| 専用知識ファイルの登録 | GPT Builderの「ナレッジ」欄 | Gemの「知識」(Knowledge)欄 | Copilot Agent Builderのファイルアップロード(SharePoint連携も可) |
| 裏側の仕組み | RAG的な検索+関連箇所の抜粋利用 | RAG的な検索 | Microsoft Graphのデータソースを検索 |

## 注意点・よくある誤解

- **完全な機密性は保証されない**: ナレッジファイルは、うまく誘導するプロンプトによってファイル名や内容の一部を抜き出されるリスクが指摘されている。2025年の研究では、GPTストア上の公開GPTのうち約8万件がナレッジファイル漏えいのリスクを抱えており、特にCode Interpreterが有効なGPTは元ファイルをそのままダウンロードされる攻撃の成功率が非常に高いと報告されている。機密情報を含むファイルを載せる場合は、Code Interpreterを無効にする、指示欄に「ファイルの中身を開示しない」と明記する、といった対策を組み合わせる
- **ファインチューニングではない**: ナレッジファイルをアップロードしても、モデル自体がその内容を「学習」して他のGPTや他ユーザーの会話に流用されることはない。あくまでそのGPTの会話内で検索・参照される情報である
- **大きすぎるファイルは一部しか読まれない**: 1ファイルにつき200万トークンの上限を超えた部分は無視される。分厚いマニュアルを1ファイルにまとめると、後半が参照されない場合がある
- **更新はファイルの差し替えが必要**: 元データを更新しても自動反映はされない。情報が古くなったら、Configureタブで該当ファイルを削除→最新版を再アップロードする運用が要る

## 最初の一歩

自分のGPTに使っている社内マニュアルやFAQを1つ選び、目次と免責事項を削ってQ&A形式に整えたテキストファイルを作り、既存のPDFと差し替えてみて回答の的確さが変わるか試す。
