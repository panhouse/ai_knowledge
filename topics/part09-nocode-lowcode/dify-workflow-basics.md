# Difyワークフローの作り方

## これは何か

「問い合わせ内容によって回答テンプレートを変えたい」「社内ナレッジを検索してから回答してほしい」「外部の在庫システムを呼び出してから返信したい」——こうした一問一答では収まらない複雑な処理は、Difyの通常のチャットボット機能(プロンプトを1つ書くだけの単純な仕組み)では組めない。これを解決するのがワークフロー(Workflow)機能で、「開始」「LLM呼び出し」「条件分岐」「外部API呼び出し」といった処理の単位(ノード)を画面上でドラッグ&ドロップして線でつなぎ、AIの処理手順を視覚的に組み立てる機能である。Dify自体の概要は[Difyとは何か](dify-basics.md)を参照。

## 仕組み・背景

ワークフローは「ノード」と呼ばれる処理ブロックを矢印でつないだ一本(または枝分かれした複数本)の流れとして表現される。各ノードは「入力変数を受け取り、処理をして、出力変数を渡す」という単純な仕組みで動くため、複雑なタスクを小さなステップに分解でき、結果としてLLM(大規模言語モデル、ChatGPTやClaudeなどの文章生成AI)を使ったアプリの精度と保守性が上がる。

Difyのアプリ作成画面では、似た機能として「Chatflow(チャットフロー)」と「Workflow(ワークフロー)」の2種類のアプリタイプが選べる。両方ともノードをつなぐ点は同じだが、性質が異なる。

| | Chatflow | Workflow |
|---|---|---|
| 主眼 | 会話(チャット画面でのやり取り) | 処理の自動化(1回の実行で完結) |
| 会話履歴 | 保持する(前の発言を踏まえて応答) | 基本的に保持しない |
| 起動方法 | ユーザーがチャット欄にメッセージを送るたび | ユーザー入力のほか、API呼び出しやスケジュール実行などの「トリガー」でも起動可能 |
| 向いている用途 | 社内問い合わせボット、ガイド付きQ&A | レポート自動生成、データ処理パイプライン、バッチ処理 |

迷ったら「会話が主役ならChatflow、裏方の処理が主役ならWorkflow」で判断すればよい。以下の説明・ノード構成はどちらのアプリタイプでも共通して使える。

### 主要なノードの種類

| ノード | 役割 |
|---|---|
| 開始 | ワークフローの起点。ユーザー入力として受け取る変数(テキスト・数値・ファイルなど)を定義する |
| LLM | GPTやClaudeなどのAIモデルを呼び出し、文章生成・要約・翻訳などを行う |
| 知識取得(ナレッジ検索) | 事前に登録したナレッジベース(社内文書などを取り込んだ検索用データベース)からユーザーの質問に関連するテキストを検索し、後続のLLMノードに渡す。RAG(検索拡張生成。検索結果を根拠にAIが回答を生成する仕組み)を実現する中心ノード |
| 質問分類器 | ユーザーの質問文をAIが読み取り、あらかじめ定義したカテゴリ(例:「製品について」「料金について」「クレーム」)のどれに当てはまるかを判定し、後続の処理を振り分ける |
| IF/ELSE(条件分岐) | 変数の値や条件式に応じて処理を2方向以上に分岐させる |
| コード実行 | Python または JavaScript のコードを実行し、データの加工・計算など込み入ったロジックをその場で処理する。サンドボックス(隔離された安全な実行環境)内で動き、pandasやrequestsなど主要ライブラリも利用できる |
| HTTPリクエスト | GET/POST/PUT/DELETEなどの方法で外部のWeb APIを呼び出す。Slack通知、外部システムからのデータ取得、Webhook送信などに使う |
| テンプレート | Jinja2(Pythonのテンプレート言語)を使い、複数の変数を組み合わせて定型文やデータ整形を行う |
| パラメータ抽出 | ユーザーの自然文からAIが構造化されたパラメータ(日付・数量・商品名など)を抽出し、後続のツール呼び出しやHTTPリクエストに渡す |
| 変数代入 | 変数に値を書き込む・更新する |
| イテレーション(反復) | リスト(配列)の要素1つ1つに対して、内部のノード処理を繰り返し実行する |
| ツール | Dify組み込みのツール(Google検索、画像生成など)やカスタムツール、他のワークフローをサブフローとして呼び出す |
| エージェント | LLMに自律的な思考をさせ、複数ステップにわたるツールの使い分けを判断させる |
| 終了/回答 | ワークフローの最終出力を定義する(Workflowでは「終了」、Chatflowでは「回答」ノードを使う) |

## 使いどころ・使い分け

| やりたいこと | 向いている機能 |
|---|---|
| 決まった1つの役割(要約する、翻訳するなど)だけをこなすシンプルなボットでよい | 通常のチャットボット機能(ワークフロー不要。プロンプト1本で十分) |
| 質問内容によって回答の出し方を変えたい(FAQ振り分け、一次対応の切り分けなど) | ワークフロー(質問分類器+条件分岐) |
| 社内文書を根拠にした回答が必要 | ワークフロー(知識取得ノードによるRAG) |
| 外部システム(在庫DB、CRM、Slackなど)と連携したい | ワークフロー(HTTPリクエストノード・ツールノード) |
| 会話の流れを保ったまま複雑な処理を挟みたい(ヒアリング→分類→回答) | Chatflow |
| 1回のリクエストで完結する自動化(レポート生成、定期実行のバッチ処理) | Workflow |

他ツールとの対応関係で言うと、Difyのワークフローはn8nの「ワークフロー」、Makeの「シナリオ」にあたる概念で、いずれも処理単位をつないで自動化を組む点は共通する。ただしn8n/Makeは「システム間連携」が主眼のオーケストレーターであるのに対し、Difyのワークフローは「LLMによる生成・判断」を中心に据えている点が異なる(詳細は[Difyとは何か](dify-basics.md)の使い分け表を参照)。単純なSaaS間の定型連携が中心ならn8n/Make、AIによる分類・生成・RAGが処理の核ならDifyのワークフロー、という住み分けが目安になる。

## 実務での使い方

### 作成手順(画面操作)

1. Difyのスタジオ画面(ログイン後のトップ)で、左側中央の「最初から作成」ボタンをクリックする
2. アプリタイプの選択画面で「Workflow」または「Chatflow」を選び、アプリ名・簡単な説明を入力する
3. 編集画面が開くと、キャンバス上に「開始」ノードが1つ置かれている。開始ノードの右にある「+」ボタンをクリックすると使用可能なノード一覧が表示されるので、必要なノードを選んで追加する
4. 追加したノードをクリックすると右側にプロパティパネルが開き、入力変数・使用モデル・プロンプト・条件式などを設定できる
5. ノード同士は端の丸いハンドルをドラッグして線でつなぐ。複数のノードを追加する場合は各ブロックの「+」から同様に追加し、必要ならドラッグして配置を調整する
6. 最後に「終了」(Workflow)または「回答」(Chatflow)ノードを配置し、どの変数を最終出力とするかを指定する
7. 右上の「実行」(プレビュー)ボタンでテスト実行し、各ノードの入出力を確認しながらデバッグする
8. 問題なければ「公開する」ボタンで公開し、Web埋め込み・API・Slack連携などの形で提供する

### 具体例: 問い合わせ内容を分類して回答テンプレートを出し分けるワークフロー

社内の問い合わせ対応を想定した、以下のようなノード構成が典型例になる。

```
[開始]
  └─ 変数: inquiry_text(ユーザーからの問い合わせ本文、テキスト型)

[質問分類器]
  └─ 入力: inquiry_text
  └─ カテゴリ定義:
       - 「製品仕様」: 製品の機能・スペックに関する質問を含む場合
       - 「料金」: 価格・プラン・見積りに関する質問を含む場合
       - 「クレーム・苦情」: 不満や返金要求を含む場合
       - 「その他」: 上記に当てはまらない場合

  ├─ 分岐「製品仕様」→ [知識取得]製品マニュアルのナレッジベースを検索 → [LLM]検索結果を根拠に回答文を生成
  ├─ 分岐「料金」→ [テンプレート]料金プラン一覧の定型文を差し込み
  ├─ 分岐「クレーム・苦情」→ [HTTPリクエスト]Slackの担当者チャンネルへ通知 → [LLM]お詫びと一次受付の返信文を生成
  └─ 分岐「その他」→ [LLM]一般的なFAQ回答を生成

[終了/回答]
  └─ 変数: 各分岐で生成された回答文
```

このように、質問分類器で入口の振り分けを行い、出口(各分岐の末尾)で最終的な回答を確定させる「分類→分岐→生成」の型が実務での鉄板パターンである。

### LLMノードのプロンプト記入例(製品仕様の分岐)

```
## 役割
あなたは自社製品のサポート担当です。以下の検索結果のみを根拠に、
丁寧な日本語で回答してください。検索結果に無い情報は「マニュアルには
記載がないため、担当者に確認します」と答えてください。

## 検索結果
{{#knowledge_retrieval.result#}}

## ユーザーの質問
{{#start.inquiry_text#}}
```

`{{#ノード名.変数名#}}` の形式で他ノードの出力を差し込める点はDify全体で共通のルールなので、覚えておくと他のノードでも応用が利く。

### RAG(検索拡張生成)を組み込む場合

知識取得ノードを使うと、事前にアップロードしたナレッジベース(PDF・Word・PowerPoint等を取り込んだ検索用インデックス)から関連文書を検索し、LLMノードのプロンプトに `{{#knowledge_retrieval.result#}}` のような形で差し込める。検索方式は「N-to-1リトリーバル」(複数のナレッジベースからAIが最も関連性の高い1つを選んで検索)と「マルチパスリトリーバル」(すべてのナレッジベースを同時検索し、Rerankモデルで結果を再採点して絞り込む)から選べる。複数の部門資料を横断して検索したい場合はマルチパスリトリーバルが有利だが、Rerankモデル(Cohereのrerank-multilingual-3.0など)の追加設定が必要になる。

### 外部API連携(HTTPリクエストノード)

HTTPリクエストノードではGET/POST/PUT/DELETEを選び、URL・ヘッダー・パラメータ・認証情報(APIキー等)を設定できる。cURLコマンドをそのまま貼り付けて設定を自動生成する「cURLからのインポート」機能もあるため、社内システムやSlack、外部SaaSのAPIドキュメントに載っているcURLサンプルをそのまま流用しやすい。ワークフロー内での使い方は主に2パターンで、(1) 処理の冒頭で外部データを取得してLLMに渡す「事前取得型」、(2) LLMが生成した内容を最後に外部サービスへ送信する「事後送信型」がある。ステータスコードが200以外の場合に備え、IF/ELSEノードでエラー分岐(「現在データを取得できません」といった固定応答を返す)を用意しておくと運用時のトラブルを避けやすい。

### コード実行ノードの使いどころ

質問分類やIF/ELSEだけでは表現しづらい細かい計算・データ整形(日付の変換、文字列の抽出、複数変数の合成など)は、コード実行ノードでPythonまたはJavaScriptを書いて処理する。以下は入力文字列を大文字に変換して返すだけの最小例。

```python
def main(input_text: str) -> dict:
    return {
        "result": input_text.upper()
    }
```

関数名は `main` 固定で、戻り値は出力変数名をキーにした辞書にする必要がある点に注意。実行は隔離されたサンドボックス環境で行われ、実行時間には上限(数十秒程度)がある。

### ツール横断の対応付け

| Difyでの呼び方 | 他ツールでの対応 |
|---|---|
| ワークフロー(Workflow / Chatflow) | n8nの「ワークフロー」、Makeの「シナリオ」 |
| ノード | n8n/Makeの「モジュール」「ステップ」 |
| 知識取得ノード(RAG) | n8nの「Vector Store」系ノード + 検索ステップの組み合わせ |
| HTTPリクエストノード | n8n/Makeの「HTTP」「Webhook」モジュール |
| 質問分類器 | Makeの「Router」に近いが、条件をAIが自然言語で判定する点が異なる |

## 注意点・よくある誤解

- **「ワークフローを使えば何でも精度が上がる」わけではない**: ノードを増やすほど設計・保守のコストも増える。単純なQ&Aにまでワークフローを組むと、かえって変更のたびに複数ノードを触る手間が発生する。まずは通常のチャットボットで足りないかを確認してから導入する
- **知識取得ノードの検索精度はナレッジベース側の作り込みに左右される**: 文書を単純にアップロードしただけでは検索精度が伸びないことが多い。目次や免責事項などノイズになりやすい部分を除いたり、Q&A形式に整形したりすると検索精度が上がりやすい
- **HTTPリクエストノードは実行のたびに外部APIの利用料・レート制限がかかる**: 想定より多く呼び出されると想定外のコストや制限超過につながるため、IF/ELSEでのエラー処理とあわせてリトライ回数の設計もしておく
- **コード実行ノードのサンドボックスには実行時間・利用可能ライブラリの制限がある**: 重い処理や外部ネットワークアクセスを前提にしたコードは動かないことがあるため、複雑な処理は外部API化してHTTPリクエストノードから呼ぶ方が安定する場合がある
- **ChatflowとWorkflowは後から相互変換できない**: アプリ作成時にどちらかを選ぶと、途中でもう一方に作り替えるのは手間がかかる。会話を続けるか、1回で完結させるかを事前に決めてから作り始める

## 最初の一歩

Difyのスタジオ画面で「最初から作成」→「Chatflow」を選び、開始ノードの後ろに質問分類器ノードを1つ追加して、「製品について」「料金について」の2カテゴリだけの簡単な振り分けを試してみる。
