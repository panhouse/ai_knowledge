# Difyのワークフロー機能(ノードの基本)

## これは何か

「LLM(大規模言語モデル)に1回プロンプトを投げるだけでは、条件分岐や社内資料の検索、外部システムとの連携までを含む業務は自動化できない」という悩みに応えるのが、Difyの「ワークフロー」機能である。処理の最小単位である「ノード」をキャンバス上に並べて線(エッジ)でつなぐことで、フローチャートを描く感覚でAIの処理手順をコードなしに組み立てられる。[Difyとは何か](dify-basics.md)で触れた4機能(ワークフロー/チャットボット/エージェント/RAGナレッジベース)のうち、業務自動化の中核を担う機能がこのワークフローである。

## 仕組み・背景

- **ノードとエッジ**: 各ノードは「LLMを呼ぶ」「条件を判定する」「コードを実行する」など特定の処理を担う部品。前のノードの出力を、後続ノードの設定画面で変数として参照でき、依存関係(どのノードの出力を使うか)を満たした順に自動で実行される。手動で実行順を管理する必要はない。
- **アプリタイプは2種類、後から作り直しに近い手間がかかる**: Difyでワークフロー系のアプリを作る際は「Workflow」と「Chatflow」のどちらかを選ぶ。
  - **Workflow(ワークフロー)**: 会話ID・会話履歴を持たない単発実行型。API呼び出し1回ごとに入力→処理→出力が完結する「バッチ処理」的な用途(データ分析、翻訳、メール分類、レポート生成など)に向く。
  - **Chatflow(チャットフロー)**: 会話ID・会話ターン数・「会話変数」(同じ会話IDの中で値を保持できる変数)など、複数ターンの対話を前提にした機能を備える。カスタマーサポートのように、ユーザーとの往復を伴うシナリオに向く。
  両者は設計思想が異なるため、公式にも相互変換をシームレスに行う手段は用意されておらず、途中でアプリタイプを変えたくなると作り直しに近い作業が発生する。最初に「単発処理か、対話を継続するか」を決めてから着手すること。

## 使いどころ・使い分け

| やりたいこと | 向いている機能 |
|---|---|
| 1回の入力に対して、複数ステップの判断・処理をして結果を返したい(メール分類、要約、翻訳、データ整形など) | Workflow |
| ユーザーと複数回やり取りしながら会話の文脈を保ったまま処理したい(問い合わせ対応、ヒアリングボットなど) | Chatflow |
| プロンプト調整だけで完結する単純なQ&Aボット | [チャットボット機能](dify-basics.md)(ワークフローほど複雑な分岐は不要) |
| 「次に何をすべきか」自体をLLMに判断させたい(手順が固定できない探索的なタスク) | ワークフロー内の**エージェントノード**、または[エージェント機能](dify-basics.md) |

判断に迷ったら「入力→出力が1往復で終わるか」を基準にするとよい。1往復で完結するならWorkflow、会話を重ねる前提ならChatflowを選ぶ。

## 実務での使い方

### ワークフローを作成する画面操作

1. Difyのスタジオ(ダッシュボード)画面で「最初から作成」を選ぶ
2. アプリタイプで「Workflow」または「Chatflow」を選択し、アプリのアイコン・名前・説明を入力して「作成する」をクリック → ワークフローエディタ(キャンバス)画面が開く
3. キャンバス左上・またはノード間の接続線にカーソルを合わせると出る「+」ボタンから、追加したいノードを選んでドラッグ&ドロップで配置する
4. ノードの端子(左右の丸印)をドラッグして線でつなぎ、処理の順番を組む
5. 各ノードをクリックすると右側に設定パネルが開くので、入力変数・プロンプト・条件式などを設定する
6. 画面右上の「実行」で動作テストを行い、各ノードの入出力(ログ)を確認しながらデバッグする
7. 問題なければ「公開する」を押すとAPIエンドポイントが発行され、外部システム(社内システムやZapier等)からワークフローを呼び出せるようになる

### 代表的なノードの種類

| ノード名 | 役割 |
|---|---|
| 開始(Start) | 全ワークフローに必須の起点ノード。ユーザー入力やAPI呼び出し時のパラメータをここで定義する |
| 終了(End)/回答(Answer) | 結果を返すノード。Workflowでは「終了」、Chatflowでは「回答」という名称になる |
| LLM | プロンプトを実行し、文章生成・要約・分類などを行う中心ノード |
| 知識検索(Knowledge Retrieval) | 登録済みのナレッジベースから入力内容に関連する文書を検索し、結果を後続のLLMノードにコンテキストとして渡す(RAGの実装部分) |
| 質問分類器(Question Classifier) | あらかじめ定義したカテゴリの中からLLMに1つ選ばせるノード。IF/ELSEより多い選択肢での分類に向く |
| 条件分岐(IF/ELSE) | 数値比較や文字列一致などの条件式で、処理をTrue/ELSEの2方向に分岐させる |
| コード実行(Code) | Python/Node.jsのコードを書いて、データ整形など独自ロジックを実行する |
| HTTPリクエスト | 外部API・社内システムを呼び出し、データの取得・送信を行う |
| ツール(Tool) | Difyに組み込み・連携済みのツール(Web検索、Slack通知など)を呼び出す |
| テンプレート(Template) | 変数を組み合わせて文字列を整形・合成する |
| パラメータ抽出(Parameter Extractor) | 自由な文章から、後続処理で使えるパラメータ(JSON形式など)を抽出する |
| 変数集約(Variable Aggregator) | IF/ELSEなどで分岐した複数ルートの出力を1つの変数にまとめ、後続ノードでの参照を単純にする |
| 反復処理(イテレーション) | リストの各要素に対して同じ処理を繰り返す(ループ処理) |
| エージェント(Agent) | 定型フローの一部を「LLMの自律判断」に委ねるノード。ReAct(思考→行動→観察を繰り返す)やFunction Callingといった「エージェント戦略」に沿って、次に使うツールや手順をLLM自身が動的に決める |

### 業務フロー例:問い合わせメールの自動分類→回答案生成

1. **開始**: メールの件名・本文・送信者情報を入力として受け取る(実際の運用では、メールシステム側からWebhookやAPI経由でこのワークフローを呼び出す形になる)
2. **コード実行**: 署名・引用された過去のやり取りなどを除去し、最新の本文だけを取り出す
3. **質問分類器**: 「製品不具合」「請求・支払い」「解約」「その他」など、あらかじめ定義したカテゴリに分類する
4. **条件分岐(IF/ELSE)**: 「解約」など優先度の高いカテゴリなら人間へのエスカレーション経路へ、それ以外は自動回答案の生成経路へ振り分ける
5. **知識検索**: FAQ・製品マニュアルのナレッジベースから関連情報を検索する
6. **LLM**: 検索結果を踏まえた返信ドラフトを生成する
7. **終了**: 分類ラベル・信頼度・返信ドラフトをまとめて出力し、CRMやメールシステム側に渡す

「解釈が必要な部分だけをLLMに任せ、フロー全体の制御構造は固定しておく」という設計は、Dify自身のサポートチームが問い合わせメールのトリアージ(優先順位付け)自動化で採用している考え方でもある。メール受信をトリガーにワークフローを起動し、メタデータと本文を取得したあと、分類前に署名・購読解除リンク・転送スレッドの履歴を除去してユーザーの最新メッセージだけを残し、LLMを固定ノードの「分類アナリスト」として機能させ、事前定義したカテゴリからインテント・信頼度・検証情報を構造化して返す、という流れが紹介されている。

### 料金・制限との関係(2026年7月時点の目安)

Dify Cloudのプラン体系自体は[Difyとは何か](dify-basics.md)で解説した通りだが、ワークフローの実務利用では特に以下の制限が影響しやすい。数値は変更されやすいため、必ず公式サイト(dify.ai/pricing)で最終確認すること。

- 無料のSandboxプランはAPI呼び出し回数やナレッジベースの文書数・容量(目安として数十件・数十MB程度)、ログの保存期間が短く抑えられており、本番運用のワークフローを継続的に動かして監視するには不向き。あくまで検証・お試し用と割り切る
- 知識検索ノードを組み込む場合、登録できる文書数・データ容量はプランごとに上限が段階的に広がる設計になっている
- 有料プラン(Professional以上)ではAPIレート制限が緩和されるため、外部システムから高頻度にワークフローAPIを呼び出す構成にする場合は無料プランでは詰まりやすい点に注意する

## 注意点・よくある誤解

- **WorkflowとChatflowは後から相互変換しにくい**: アプリ作成時にどちらかを選ぶと、会話機能の有無を前提にした設計になる。「単発処理のつもりで作ったら、途中から会話継続に対応させたくなった」というケースでは作り直しに近い手間がかかるため、最初に用途を見極めてから着手する。
- **ノードを増やしすぎるとレイテンシとコストが積み上がる**: LLMノードを何度も経由するフローは、その分だけAPI呼び出し回数が増え、応答時間と料金の両方に跳ね返る。1回のLLM呼び出しで複数の判断をまとめられないか、まず検討するとよい。
- **IF/ELSEの条件はLLM出力のゆらぎに弱い**: LLMが返す文字列表記のゆれ(「はい」/「Yes」など)をそのままIF/ELSEの条件式にすると分岐に失敗しやすい。選択肢を固定できる質問分類器を使うか、LLMノードの出力形式をJSON等に固定してから条件判定する設計にする。
- **変数のスコープを混同しやすい**: Chatflowの「会話変数」は会話ID単位で保持されるが、Workflowにはこの概念がなく実行のたびに状態がリセットされる。複数回の呼び出しをまたいで情報を持ち越したい場合はChatflowを選ぶか、外部DBに保存する設計にする。
- **エージェントノードは便利だが挙動の予測がしづらい**: 手順を固定するIF/ELSEやコードノードと違い、エージェントノードはLLM自身が手順・ツール利用を動的に決めるため、コストや処理時間が読みにくくなることがある。重要な判断や、必ず特定の手順を踏ませたい業務では、フロー全体は固定ノードで組み、判断が難しい一部分だけをエージェントノードに任せる設計が安全。

## 最初の一歩

Difyのスタジオ画面で「最初から作成」→「Workflow」を選び、「開始」→「LLM(『入力文を1文で要約して』という指示)」→「終了」という3ノードだけの最小構成を作り、右上の「実行」ボタンで動かしてみる。
