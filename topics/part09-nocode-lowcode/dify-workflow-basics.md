# Difyのワークフロー機能の基本

## これは何か

「1回のプロンプトでは複雑すぎる処理を、AIチャットではなく自動処理として組みたい」というときに使うのがDifyの**ワークフロー**機能である。画面上に並んだ「ノード」と呼ばれる処理ブロックを線でつなぎ、入力→分類→検索→生成→出力という一連の処理手順をコードを書かずに視覚的に組み立てられる。Difyそのものの概要は[Difyとは何か](./dify-basics.md)で扱ったので、本ページではワークフロー機能そのものの使い方に絞って解説する。

## 仕組み・背景

ワークフローの実体は「有向グラフ」である。各ノードが1つの処理(LLM呼び出し、条件判定、外部API呼び出しなど)を担当し、ノード同士を線(エッジ)でつなぐことで、あるノードの出力を次のノードの入力として渡す。この出力は「変数」としてキャンバス上で管理され、後続のどのノードからでも `{{#ノード名.変数名#}}` のような形で参照できる。

### アプリの種類: チャットフロー と ワークフロー

Difyでノード編集の画面(キャンバス)を使うアプリには2種類あり、どちらを選ぶかで使えるノードや挙動が変わる。

- **チャットフロー(Chatflow)**: チャット画面から会話形式で使うアプリ向け。ユーザーの発言1件ごとにフローが実行され、会話ID(conversation ID)に紐づく「セッション変数」で過去のやり取りを参照できる。回答を途中で返す専用の「回答(Answer)」ノードがあり、複数回に分けて返信を流すことも可能。
- **ワークフロー(Workflow)**: 入力を1回受け取り、最初から最後まで一気に処理して結果を返す単発実行型。会話IDの概念がなく、実行ごとに独立している。バッチ処理・API連携・定型レポート生成など「毎回同じ手順を自動でこなす」用途に向く。最終出力は「終了(End)」ノードで確定する。

迷ったら「人と対話しながら複数ターンで進めたいか」で判断するとよい。対話が必要ならチャットフロー、1回の入力で完結する自動処理ならワークフロー、というのが基本の使い分けである。

### 主なノードの種類

2026年7月時点でDifyには10種類以上のノードがあり、代表的なものは以下の通り。

| ノード | 役割 |
|---|---|
| 開始(Start) | フローの起点。ユーザーからの入力項目(テキスト・数値・ファイルなど)をここで定義する |
| LLM | GPTやClaude、Geminiなど大規模言語モデルを呼び出し、要約・分類・文章生成などの「思考」を担当する中核ノード |
| 知識取得(Knowledge Retrieval) | 事前に登録したナレッジベース(社内文書など)から、入力内容に関連する情報をRAG(検索拡張生成)方式で取得する |
| 質問分類(Question Classifier) | LLMを使って入力をあらかじめ決めたカテゴリに分類し、そのままIF/ELESと同様に後続の分岐先を決める。分類+分岐を1ノードで済ませたいときに使う |
| IF/ELSE(条件分岐) | 変数の値に応じて処理を複数の経路に分岐させる |
| コード実行(Code) | Python/Node.jsのコードを書いて、GUIのノードだけでは表現しづらいデータ整形・計算を行う |
| HTTPリクエスト | 外部のWeb APIを直接呼び出す。DifyにないSaaSや社内システムとの連携に使う |
| ツール(Tool) | Dify組み込みの50以上のツール(Web検索、画像生成など)や外部連携ツールを呼び出す |
| イテレーション(Iteration) | リスト(配列)の要素1つずつに対して、指定した一連のノード処理を繰り返し実行する |
| パラメータ抽出(Parameter Extractor) | 自然文からLLMを使って構造化されたパラメータ(日付・金額など)を取り出す |
| 回答(Answer) / 終了(End) | チャットフローでは回答ノードが応答を返し、ワークフローでは終了ノードが最終出力を確定する |

これ以外にもテンプレート(Jinja2形式でのテキスト整形)、変数集約、エージェント(LLMに自律的なツール選択・実行ループを行わせるノード)などがあり、組み合わせ次第で単純な自動応答から自律型のAIエージェントに近い挙動まで実装できる。

## 使いどころ・使い分け

| 状況 | 向いている選択 |
|---|---|
| 1回のプロンプトで完結する単純作業(1文の要約・翻訳など) | ワークフロー化は過剰。ChatGPTやClaudeへの単発の質問で十分 |
| 「分類→検索→生成」のように複数のLLM呼び出しやロジックを毎回同じ手順で自動化したい | Difyのワークフロー(GUIで組めて、エンジニア不在でも保守できる) |
| 開発者を介さずAPIエンドポイントやサイト埋め込みのチャットウィジェットが欲しい | Difyのワークフロー/チャットフロー(公開ボタン一つでAPIキー・埋め込みタグが発行される) |
| ユーザーと複数ターンで対話しながら情報を引き出しつつ処理したい | Difyのチャットフロー |
| SlackやスプレッドシートなどSaaS間の連携が主目的で、LLMは処理の一部にすぎない | n8nやMake(SaaS用コネクタの種類・条件分岐の柔軟さで優位。詳細は今後掲載する「その他自動化ツール」の章を参照) |
| 状態管理が複雑、既存システムと密結合、テストやバージョン管理を厳密に行いたい | 通常のコード実装(Python/TypeScriptなど)+ APIを直接呼ぶ。ノード数が数十を超えるとGUI上での可読性・差分管理が難しくなる |

## 実務での使い方

### 具体例: 問い合わせメールの自動振り分けワークフロー

「顧客からの問い合わせ本文を受け取り、内容ごとに異なるテンプレート回答を生成する」ワークフローを例に、ノード単位の組み方を示す。

1. **アプリ作成**: Difyのダッシュボードで「最初から作成」→ アプリタイプで「ワークフロー」を選択(今回は1回の入力で完結する単発処理のため)。
2. **開始ノード**: 入力変数として「問い合わせ本文」(テキスト、必須)と「顧客名」(テキスト、任意)を定義する。
3. **LLMノード(分類)**: プロンプトに「以下の問い合わせ本文を『料金』『不具合』『解約』『その他』のいずれか1語に分類してください」と指示し、出力変数 `category` を得る。分類と分岐をまとめたい場合は、このLLMノードの代わりに「質問分類」ノード1つで済ませることもできる。
4. **IF/ELSEノード(分岐)**: `category` の値に応じて4方向に分岐させる。
5. **知識取得ノード(カテゴリごと)**: 例えば「料金」分岐では、料金FAQをまとめたナレッジベースを検索し、関連する回答候補を取得する。
6. **LLMノード(回答生成)**: 検索結果と「丁寧なビジネスメール調で回答文を作成してください」といった指示を組み合わせ、カテゴリ別の回答文を生成する。
7. **終了ノード**: 生成した回答文とカテゴリを出力変数として確定する。
8. **公開**: 画面右上の「公開する」からWebアプリのURL発行、またはAPIエンドポイントとしての利用(`curl` でPOSTして入力変数を渡し、結果をJSONで受け取る)を選ぶ。社内システムに組み込みたい場合はAPI、担当者が直接使うだけならWebアプリで十分。
9. **デバッグ**: 公開前に画面上部の「実行」でテスト入力を流し、各ノードをクリックして入出力の変数を確認する。想定外の分岐に入っていないか、実行ログ(トレース)で1ノードずつ追えるため、期待通りに動くまでここで調整する。

### ナレッジベースとの連携

知識取得ノードを使うには、事前に「ナレッジ」画面でPDFやWord、Markdownなどのファイルをアップロードし、チャンク(検索単位の断片)に分割・インデックス化しておく必要がある。元データの構造が崩れているとチャンク分割や検索精度が落ちるため、ドキュメントの前処理については[AIが扱いやすいデータ形式](../part06-data-analysis/ai-friendly-data-formats.md)も参考にするとよい。

### ツールノードとFunction Calling

ツールノードやエージェントノードは、LLMが「どの関数(ツール)をどんな引数で呼ぶか」を判断する仕組みの上に成り立っている。この基本原理は[Function Callingの基本](../part08-api-development/function-calling-basics.md)で扱っているので、ツールノードの挙動を理解したい場合はあわせて参照するとよい。

## 注意点・よくある誤解

- **LLMノードを連結するほどコストは線形に増える**: 分類→検索→生成と3回LLMを呼べば、それだけAPI利用料がかかる。分類のような軽い処理は安価な小型モデル、最終的な文章生成だけ高性能モデルにするなど、ノードごとにモデルを使い分けるとコストを抑えられる。
- **「動いているが中身が見えない」状態に陥りやすい**: ノード数が増えるとブラックボックス化しやすい。実行ログ・トレース機能で各ノードの入出力を都度確認し、テストケースを何パターンか流してから公開する習慣をつける。
- **社外秘データはCloud版の送信先に注意**: Dify Cloudを使うと入力データや検索対象のナレッジベースが海外リージョンのサーバーに送信される。個人情報や社外秘の情報を扱う場合は、自社サーバーに構築するセルフホスト版の検討や、[生成AI利用における情報漏洩対策](../part03-risk-security/information-leakage-prevention.md)の確認を先に行う。
- **「ノーコードだからコード知識は不要」は半分だけ正しい**: 単純な分岐まではGUIだけで組めるが、細かいデータ整形や複雑な条件式が必要になった途端、結局コード実行ノードでスクリプトを書く場面が出てくる。多少のPython/JavaScriptの知識があると表現の幅が大きく広がる。
- **チャットフローとワークフローは後から変換しづらい**: アプリ作成時にどちらのタイプかを選ぶ必要があり、途中で作り直すのは手間がかかる。用途(対話か単発処理か)を先に決めてから着手する。

## 最初の一歩

Dify Cloudにログインし、テンプレートギャラリー(Explore/テンプレート一覧)から自社の業務に近いワークフローを1つ複製する。キャンバスを開いて各ノードを順にクリックし、どんな入力変数・プロンプト・出力変数が設定されているかを観察するところから始めるとよい。
