# Difyワークフローの基本(ノードの種類と組み方)

## これは何か

「問い合わせメールの内容を読んで、種類ごとに振り分けて、それぞれ違う文面の返信案を作り、担当チームのSlackに知らせる」——こうした「複数の判断・複数のステップ」を含む業務は、1問1答のチャットボットだけでは組み立てられない。Difyの「ワークフロー」は、こうした一連の処理を「ノード」というブロック(部品)に分解し、キャンバス上でつなぐだけで自動化する機能である。エンジニアが書くプログラムの「条件分岐」や「関数呼び出し」を、ノーコードの画面操作で表現できると考えるとよい。

## 仕組み・背景

ワークフローは、開始ノードから終了ノードまで、各ノードが「入力変数を受け取る→処理する→出力変数を次のノードに渡す」というバケツリレーの構造になっている。ノード同士は矢印(エッジ)でつなぎ、途中でIF/ELSEのような条件分岐を挟むと、処理の流れは1本の線ではなく枝分かれした木構造になる。この「入力→処理→出力」の単位がノードであり、Difyには2026年7月時点で以下のような主要ノードが用意されている。

| ノード名 | 役割 |
|---|---|
| 開始(Start) | ワークフローの入力パラメータ(ユーザーが渡す変数)を定義する。すべての処理の起点 |
| LLM | 大規模言語モデルを呼び出し、文章生成・要約・分類・翻訳などを行う。ワークフローの中核となることが多い |
| 知識取得(Knowledge Retrieval) | ナレッジベース(社内文書などを取り込んだ検索用データベース)から質問に関連する文章を検索し、後続のLLMノードに渡すコンテキストにする。RAG(検索拡張生成)の中心部品 |
| 質問分類器(Question Classifier) | LLMの判断で、入力内容をあらかじめ定義した複数のカテゴリのどれかに振り分ける。分岐先ごとに別のノードをつなげられる |
| 条件分岐(IF/ELSE) | 「含む」「等しい」「より大きい」などの条件式で、処理をIF側とELSE側の2方向(条件を追加すればさらに多方向)に分ける |
| コード実行(Code) | Python または Node.js のコードを書いて、他のノードでは組みにくい細かいデータ加工(正規表現での文字列抽出、集計、フォーマット変換など)を行う |
| HTTPリクエスト(HTTP Request) | GET/POST/PUT/DELETEなどの方法で外部のAPIやWebhookを呼び出す。DifyのワークフローをSlackや自社システムなど「外の世界」につなぐ役割 |
| テンプレート(Template) | Jinja2という記法を使い、変数をテキストに埋め込んで整形する。通知文やレポートの体裁を整えるのに使う |
| 変数集約(Variable Aggregator) | IF/ELSEや質問分類器で分岐した複数のルートの出力を、1つの変数名にまとめる。分岐後の処理をシンプルにする「合流地点」 |
| パラメータ抽出(Parameter Extractor) | 自由記述のテキストから、LLMの力を借りて「氏名」「日付」「金額」のような構造化データ(JSON項目)を抜き出す |
| イテレーション(Iteration) | 配列(リスト)の各要素に対して、決められたサブフローを繰り返し実行する。メール一覧の一括処理などバッチ処理向け |
| ループ(Loop) | 条件を満たすまで処理を繰り返す。前回の結果を使って次の計算をする再帰的な処理に向く(2025年にIterationより柔軟な反復手段として追加されたノード) |
| エージェント(Agent) | LLMが状況に応じて自律的にツールを選び、実行する。Function CallingやReActといった推論方式を選べる |
| ツール(Tool) | Dify組み込みツール・カスタムツール・他のワークフローをサブフローとして呼び出す |
| ドキュメント抽出(Doc Extractor) | PDFやWordなどのファイルからテキストを取り出す |
| リスト操作(List Operator) | 配列の絞り込み・並べ替え・件数指定などを行う |
| 回答(Answer) | **Chatflow専用**。会話の各ターンでユーザーに返す応答内容を定義する |
| 終了(End) | **Workflow専用**。処理が完了したときの最終的な出力内容を定義する |

一部のノード(質問分類器、パラメータ抽出、エージェントなど)は内部でLLMを呼び出すため、これらのノードを増やすほど処理時間とAPIコストが増える点は覚えておきたい。

## 使いどころ・使い分け

Difyのアプリ作成画面では「Chatflow(チャットフロー)」と「Workflow(ワークフロー)」という似た2つの種類を選べる。どちらもノードをつなぐ点は同じだが、向いている業務が異なる。

| 観点 | Chatflow | Workflow |
|---|---|---|
| 想定シーン | 会話・対話がある(社内FAQボット、注文サポート) | 1回の入力→処理→出力で完結する定型業務(レポート生成、メール自動処理) |
| 会話の記憶 | 会話ID・複数ターンの文脈を保持できる | 実行ごとに完全に独立。前回の実行内容は覚えない |
| 完了ノード | 回答(Answer)ノード。ターンごとに応答を返す | 終了(End)ノード。処理完了時に最終出力を1回だけ返す |
| 起動方法 | チャット画面でのメッセージ送信 | API呼び出し、Webhook、他アプリからの呼び出し、スケジュール実行など |
| 向いている例 | 社内問い合わせボット、FAQ検索対応 | 問い合わせメール分類→Slack通知、日次レポートの自動生成、大量データのバッチ処理 |

判断基準はシンプルで、**「ユーザーと何度もやり取りしながら会話を継続する必要があるか」**で選べばよい。継続的な対話が必要ならChatflow、1回のきっかけ(メール受信、フォーム送信、API呼び出しなど)から自動で処理を完結させたいならWorkflowを選ぶ。

## 実務での使い方

### 具体シナリオ: 問い合わせメールを分類し、カテゴリ別の回答テンプレートを作ってSlackに通知する

自動転送などで問い合わせメールの「本文」と「送信者アドレス」がテキストとして渡されてくる状況を想定し、以下のようにノードを組む。

1. **開始ノード**: 入力変数として `email_body`(問い合わせ本文・テキスト型)と `sender_email`(送信者アドレス・テキスト型)を定義する。
2. **質問分類器ノード**: `email_body` を入力にし、「製品の不具合」「使い方の質問」「請求・契約について」「その他」の4カテゴリに分類するよう分類基準を記述する。出力側には4つの分岐(エッジ)が生成される。
3. **各分岐にLLMノードを配置**(合計4つ): カテゴリごとに異なるシステムプロンプトを設定し、そのカテゴリに合った返信ドラフトを生成する。例えば「製品の不具合」分岐のLLMノードには次のようなプロンプトを入れる。

   ```
   あなたはカスタマーサポート担当です。以下の問い合わせは「製品の不具合」に分類されています。
   共感の一言→状況確認のお願い→サポート窓口への引き継ぎを一次回答として300字程度で作成してください。

   問い合わせ本文: {{#開始.email_body#}}
   ```

4. **IF/ELSE条件分岐ノード**: 「製品の不具合」カテゴリかどうかを判定し、真の場合は緊急対応フラグ(`is_urgent = true`)を立てるルートに、偽の場合は通常ルートに分ける。緊急対応ルートでは、後続のテンプレートノードで通知文の先頭に「🚨要対応」を付けるようにする。
5. **変数集約ノード**: 質問分類器で分かれた4つのLLMノードの出力(回答ドラフト)を、`reply_draft` という1つの変数名に集約する。これにより、後続のノードは「どの分岐を通ったか」を意識せず `reply_draft` を参照するだけで済む。
6. **テンプレートノード**: `reply_draft` と `sender_email`、緊急フラグを使って、Slackに投稿する通知文を整形する(例: 「📩新規問い合わせ({{sender_email}})\n{{reply_draft}}」)。
7. **HTTPリクエストノード**: Slack側で発行した「Incoming Webhook」のURLに対してPOSTリクエストを送る。

   - メソッド: `POST`
   - URL: `{{#env.SLACK_WEBHOOK_URL#}}` (URLを直接書かず環境変数を参照する。詳細は後述)
   - ヘッダー: `Content-Type: application/json`
   - ボディ(JSON):
     ```json
     { "text": "{{#テンプレート.output#}}" }
     ```
8. **終了ノード**: `reply_draft` を出力変数として返す。これにより、このワークフローをAPI経由で呼び出した側(自社システムなど)も生成された回答ドラフトを受け取れる。

RAG(社内のFAQ・製品マニュアルを検索させて回答精度を上げたい)場合は、手順3のLLMノードの前に「知識取得ノード」を挟み、検索結果をLLMノードのコンテキストとして渡す。メールを1件ずつでなく複数件まとめて処理したい場合は、開始ノードの入力を配列にして「イテレーションノード」で全体を包み、内部に2〜7の処理を入れる構成にする。

### スタジオでの基本操作

1. **ワークフローの作成**: Difyにログイン後、左サイドバーの「スタジオ」→右上の「最初から作成」→「Workflow」(会話が必要な場合は「Chatflow」)を選び、アプリ名を入力して「作成する」をクリックする。
2. **ノードの追加**: キャンバス上のノードの右端にある「+」ボタン、または画面上の「ブロックを追加」からノードを検索し、キャンバスにドラッグ&ドロップで配置する。ノードの端子(丸いポイント)をドラッグして次のノードの入力側につなぐと、処理の順序と変数の受け渡しが定義される。
3. **変数の参照**: 各ノードの設定パネルでは、直前までのノードで定義済みの変数が `{{#ノード名.変数名#}}` の形式で候補表示される。手入力よりも変数ピッカー(入力欄の `{}`アイコンや`/`)から選ぶ方が誤字を防げる。
4. **テスト実行**: 画面右上の「実行」(テスト実行)をクリックし、開始ノードで定義した入力値をその場で入力して「実行開始」を押す。実行後は各ノードの右下に✓または✕が表示され、ノードをクリックするとそのノードの入力・出力・処理時間を個別に確認できる。分岐が想定通りに動いているか、変数集約後の値が正しいかをここで必ず確認する。
5. **公開**: テスト結果に問題がなければ、画面右上の「公開」→「更新を公開」をクリックする。公開すると、Web公開用のURL・埋め込みタグ・API(APIキー発行)経由での呼び出しが可能になる。ノードを編集しただけでは本番には反映されず、この「公開」操作をした版のみが本番で動く点に注意する。

### 外部ツールでの近い概念

| Dify | 近い概念 |
|---|---|
| HTTPリクエストノード | n8nの「HTTP Request」ノード、Zapierの「Webhooks by Zapier」 |
| コード実行ノード | n8nの「Code」ノード、Makeの「カスタムJavaScript」 |
| 変数集約ノード | n8nの「Merge」ノード(概念上は近いが、Difyは分岐後の型を揃える用途に特化) |
| 環境変数(Secret) | n8nの「Credentials」、Makeの「接続(Connection)」 |

## 注意点・よくある誤解

- **ノードが増えるほど保守性が落ちる**: 分岐が5つ、10つと増えると、後から見た人(数か月後の自分も含む)がフロー全体を目で追えなくなる。ノードには分かりやすい名前(「LLM_不具合対応文面生成」など)を付け、まとまった処理は「ツールノード」からサブワークフローとして呼び出す形に切り出すと、キャンバスが肥大化しにくい。
- **エラーハンドリングを設定しないと、1か所の失敗で全体が止まる**: 特にHTTPリクエストノードは、外部サービスのタイムアウトや一時的な障害で失敗しうる。ノードの設定パネルにある「エラー処理」で、①何もしない(失敗したら全体を停止)、②デフォルト値を使う(失敗時に既定の値で処理を継続)、③失敗時分岐(あらかじめ用意した代替ルートに流す)のいずれかを選べる。加えてHTTPリクエストノードには再試行(リトライ)回数と間隔の設定もあるため、Slack通知のような「多少遅れてもよいが確実に届けたい」処理では、リトライと失敗時分岐を組み合わせておくと安全である。
- **外部APIキー・Webhook URLは直接ノードに書き込まない**: SlackのWebhook URLやAPIキーをHTTPリクエストノードの設定に直接貼ると、そのワークフローをDSL(設定ファイル)としてエクスポート・共有した際に漏えいするおそれがある。アプリ設定の「環境変数」でSecret型の変数として登録し、ノード側では `{{#env.変数名#}}` の形で参照する。Secret型はエクスポート時に確認ダイアログが出る、画面上でも値がマスク表示されるなど、通常の変数より安全に扱える。
- **質問分類器とIF/ELSEを混同しない**: 質問分類器は「LLMの意味理解に基づいてカテゴリ分けする」ノードで、IF/ELSEは「あらかじめ決めた条件式(等しい・含む・以上など)で機械的に分岐する」ノードである。前者は曖昧な自然文の振り分けに、後者は「フラグがtrueかどうか」のような確定的な条件判定に向く。両方を安易に増やすと分岐が複雑になりすぎるため、まずはIF/ELSEで足りないかを検討するのが無難。

## 最初の一歩

DifyスタジオでWorkflowを新規作成し、開始ノード→LLMノード(簡単な要約でよい)→終了ノードの3つだけをつないでテスト実行し、変数が正しく次のノードに渡ることを確認する。
