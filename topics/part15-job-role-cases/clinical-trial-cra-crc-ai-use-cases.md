# 臨床開発・治験担当者(CRA・CRC)における生成AI活用事例

## これは何か

CRA(Clinical Research Associate、臨床開発モニター。製薬企業やCRO(Contract Research Organization、医薬品開発受託機関。IQVIA・パレクセル・シミック・EPS等)に所属し、治験実施医療機関を訪問してプロトコル(治験実施計画書)・GCP(Good Clinical Practice、医薬品の臨床試験の実施の基準)通りに治験が進んでいるかを確認する職種)とCRC(Clinical Research Coordinator、治験コーディネーター。SMO(Site Management Organization、治験施設支援機関)や医療機関に所属し、治験参加患者への説明同意、来院・検査対応、症例報告書(CRF、Case Report Form)作成の補助を担う職種)は、いずれも「治験を1件動かすたびに、決まった書式の文書を大量かつ正確に作り続ける」仕事である。生成AIはモニタリング報告書・CRF・説明同意文書(ICF、Informed Consent Form)・治験総括報告書(CSR、Clinical Study Report)といった定型文書の下書きを高速化できる一方、記載内容は規制当局への提出・査察(GCP監査)の対象になるため、「どこまでAIに任せてよいか」の線引きが他職種以上に厳格に問われる。本ページは、CRA・CRCという**治験を実際に動かす現場職種**が日々の業務で生成AIをどう使うかに焦点を当てる。

**他ページとの境界**: [製薬業界における生成AI活用事例](../part14-industry-cases/pharmaceutical-industry-ai-use-cases.md)は創薬・治験文書作成・ファーマコビジランス(PV)・MR/MSLまで含む**業種全体**を扱う業種カタログであり、本ページはその中の「治験の実施・モニタリングという業務を担うCRA・CRCという職種」に絞った職種カタログである。[研究開発(R&D)職における生成AI活用事例](rd-ai-use-cases.md)は創薬段階の文献調査・実験計画・特許明細書作成を扱い、[品質管理・QA職における生成AI活用事例](quality-assurance-ai-use-cases.md)は製造業・ソフトウェアの品質保証(検査報告書・バグトリアージ等)を扱う。いずれも治験の実施そのもの(モニタリング訪問・CRF作成・患者同意取得)は扱っておらず、本ページが唯一その領域を扱う。

## 仕組み・背景

### CRAの業務フェーズ別・生成AI活用マップ

| フェーズ | 業務内容 | 生成AIの入り方 |
|---|---|---|
| 治験開始準備(SIV) | 実施医療機関の選定・立ち上げ、施設向け説明資料の準備 | 施設情報の要約、説明資料のドラフト作成 |
| モニタリング訪問(定期訪問) | SDV(Source Data Verification、カルテ等の原資料とCRF記載の突合)、逸脱の有無確認 | 訪問前チェックリストの準備、過去訪問記録の要点整理 |
| モニタリング報告書作成 | 訪問結果を定型フォーマットで報告書化、英語で本社・海外治験依頼者に共有 | 報告書のドラフト作成、日英翻訳・文体調整 |
| 逸脱(プロトコルデビエーション)管理 | 逸脱事象の記録・分類・是正措置のフォロー | 事象の要約、過去の類似逸脱との照合、報告文面のドラフト |
| 中間・完了報告 | 治験進捗の社内・治験依頼者向け報告 | 進捗データの文章化、複数施設分のとりまとめ |

### CRCの業務フェーズ別・生成AI活用マップ

| フェーズ | 業務内容 | 生成AIの入り方 |
|---|---|---|
| 患者スクリーニング | 選択・除外基準への適合確認、候補患者のリストアップ補助 | 基準の読み替え・チェックリスト化 |
| 説明同意(IC)支援 | 治験責任医師の説明に同席し、患者の理解を助ける補助説明・資料作成 | ICF(説明同意文書)の平易な言い換え案の作成 |
| 来院対応・検査調整 | 来院スケジュール調整、検査・投薬のリマインド | 案内文・スケジュール表の下書き作成 |
| CRF入力・記録作成 | カルテ等の原資料からCRFへの転記、記載整合性の確認 | 転記候補の抽出補助、記載表現の統一チェック |
| 有害事象(AE)対応記録 | AE(Adverse Event、有害事象)の発生・経過の記録、CRAへの報告 | 経過記録の文章化・要約 |

治験関連文書に生成AIを使う際に他部門と最も違う点は、**出力が「原資料(source document)との一致」を厳密に要求される**ことである。GCPの根底には ALCOA+(Attributable=記録者が特定できる、Legible=判読可能、Contemporaneous=同時記録性、Original=原本性、Accurate=正確、+ Complete=完全性、Consistent=一貫性、Enduring=保存性、Available=入手可能性)というデータ信頼性の原則があり、CRFやモニタリング報告書に生成AIの[ハルシネーション](../part04-risk-security/hallucination-and-countermeasures.md)(事実と異なる内容をもっともらしく生成する現象)が紛れ込むと、この原則そのものに反する記録が規制当局への提出物として残ってしまう。そのため治験文書での生成AI活用は、他部門より一段階厳しく「AIは下書きまで、原資料との照合・最終責任は人」という運用が前提になる。

日本国内では、厚生労働科学研究費補助金による特別研究「生成AIを用いた治験・臨床研究関連文書のデジタルトランスフォーメーションに向けた研究」(研究代表者:浅野健人、2023年度)が、研究計画書の自動生成、説明文書の平易化、電子カルテからのeCRF自動入力・項目抽出の可能性を検証している。同研究では、大規模言語モデル(LLM)を使って説明文書を約3,447字から701〜1,108字に圧縮したところ、全体としては理解度が向上した一方、50〜70代の回答者では逆に理解度が下がったケースも見られたと報告されており、「平易化すれば誰にとっても分かりやすくなる」とは限らない点が示唆されている([厚生労働科学研究成果データベース](https://mhlw-grants.niph.go.jp/project/167945))。

規制の枠組みとしては、ICH(医薬品規制調和国際会議)のGCPガイドライン改訂版であるICH E6(R3)のAnnex 2が2026年6月3日に最終化され、分散型臨床試験(DCT、Decentralized Clinical Trial。来院を減らし遠隔診療・在宅検査等を組み合わせる治験手法)・プラグマティックな試験デザイン・リアルワールドデータへのGCP適用指針が整理された。この改訂は「適合性を証明できればどのような技術を使ってもよい」という技術中立性(technology neutrality)を原則としており、生成AIの利用自体を否定も推奨もせず、使う場合の妥当性検証・文書化を求める立て付けになっている([pharmaeducenter.com](https://pharmaeducenter.com/blog/ich-gcp-e6-r3-annex-2/)、[Sidley Austin](https://www.sidley.com/en/insights/newsupdates/2025/12/us-fdas-adoption-of-ich-e6r3-good-clinical-practice-key-takeaways-for-sponsors-and-investigators))。

## 使いどころ・使い分け

### 汎用チャットAIで足りる範囲と専用ツールが必要な範囲

| 業務 | 汎用チャットAI(ChatGPT/Claude/Gemini等) | 専用ツール・体制が必要 |
|---|---|---|
| モニタリング報告書・メールの日英翻訳・文体調整 | 対応可(社内規程で承認されたツールに限る) | 治験依頼者から特定翻訳ツールの使用を指定される場合あり |
| ICF(説明同意文書)の平易な言い換え案作成 | 対応可(下書きのみ、年齢層による理解度差に留意) | 最終文面は治験責任医師・倫理審査委員会(IRB)の承認が必須 |
| CRF記載の整合性チェック・表現統一 | 対応可(匿名化済みテキストに限る) | 電子カルテからのeCRF自動転記はEDC(Electronic Data Capture、治験データの電子的収集システム)側のAI機能や専用連携基盤が必要 |
| 治験総括報告書(CSR)の章立て・下書き | 定型フォーマットへの流し込みは可 | 治験の計画書・解析結果全体からの自動生成は、専用に開発されたAIソフト(下記事例)が実績を出している |
| SDV(原資料照合)の対象施設・優先度判定 | 不向き | リスクベースモニタリング(RBM)の専用アルゴリズム・中央モニタリング機能が必要 |
| 患者の個人情報・治験の未公開データを含む相談 | 不向き(法人契約でデータ学習利用オプトアウトが確認できない限り使わない) | 治験依頼者が提供するセキュリティ確保済みの環境を使う |

### 具体的な事例で見る「どこまで実用化されているか」(2026年時点)

- **CSR(治験総括報告書)の自動作成**: 国立がん研究センター中央病院はAI翻訳企業のロゼッタと2024年4月から共同研究を行い、治験の計画書とデータ解析結果を入力すると章立てを自動生成する医師主導治験向けのCSR作成AIソフトを開発した。2025年3月に発表された初年度の検証結果では、119件の報告書のうち「ほぼそのまま利用可能」が5割、「微修正で利用可能」が3割で、合計8割が実用レベルに達したという。従来は専門ライターへの外注で1件あたり約500万円・入札から提出まで半年を要していたが、作成期間は数日に短縮された。2026年2月27日には政府の医薬品開発協議会でも継続的な開発状況が報告されている([日本経済新聞](https://www.nikkei.com/nkd/industry/article/?DisplayType=1&n_m_code=071&ng=DGXZQOUF23AOZ0T20C25A3000000)、[内閣官房 医薬品開発協議会資料](https://www.cas.go.jp/jp/seisakukaigi/kenkouiryou/iyakuhin/iyakuhinkyougikai_dai2/shiryo4.pdf))。
- **グローバルCROのAIスイート**: パレクセル(Parexel)は臨床開発全体を支える「ParexelAI」を展開し、治験実施施設の選定プロセス期間を50%短縮、メディカルライティングによる治験報告書作成時間を30%短縮、安全性文献スクリーニングとファーマコビジランス症例処理を20%削減したとベンダー公表している([Parexel公式](https://www.parexel.com/japan/news-insights/press-releases/Parexel-Launches-ParexelAI-Delivering-AI-Innovation-to-Accelerate-Clinical-Development))。
- **AIエージェントによるモニタリング業務の自動化**: IQVIAはNVIDIAと協力し、音声からテキストへの文字起こし・臨床コーディング・構造化データの抽出・データ要約といった一連のワークフローを担うオーケストレーター型のAIエージェントを開発している([NVIDIA Japan Blog](https://blogs.nvidia.co.jp/blog/iqvia-ai-agents-clinical-research/))。IQVIAサービシーズジャパンでは、Amazon Bedrockのナレッジベースを用いたRAG(検索拡張生成)ベースのAIチャットを構築し、GCP等の規制情報調査の効率化にも活用している。
- **リスクベースモニタリング(RBM)によるCRA工数の最適化**: 全件SDVを前提とせず、データの異常検知やリスク評価にもとづいて訪問頻度・SDV範囲を調整するRBM(Risk Based Monitoring)は、2015年のICH E6改訂で明示的に位置付けられた手法である。RBMを導入した組織では、適用期間中にCRAのFTE(フルタイム相当人員)を15%以上削減できたとする報告があり、1人のCRAが担当できる施設数の最適化にもつながっている([EFPIA Japan資料](https://efpia.jp/link/RBM_for_CRA.pdf))。国内ではEPS・シミック・新日本科学PPDなどのCRO各社がRBMサービスを提供している。
- **分散型臨床試験(DCT)の広がり**: NTTドコモビジネスとNTTデータは、がん患者向け治験で分散型臨床試験(DCT)基盤「PhambieLINQ」を用いた実証を2026年7月に開始した([NTTドコモビジネス](https://www.ntt.com/about-us/press-releases/news/article/2026/0707_2.html))。DCTでは遠隔診療・在宅検査・eConsent(電子的な説明同意)が組み合わされ、CRCの業務も「来院対応」から「遠隔での進捗管理・患者サポート」へ比重が移りつつある。

## 実務での使い方

### プロンプト例1: モニタリング報告書の英語版ドラフト作成(CRA)

```
以下は国内治験のモニタリング訪問後の報告メモです。海外の治験依頼者(スポンサー)向けに、
英語のモニタリング報告書の下書きを作成してください。

- 訪問日、施設名、対応した治験責任医師・CRCの役職(氏名は「Dr. [施設担当医]」等の記号に置き換えています)
- SDV(原資料照合)で確認した項目と結果
- 発見された逸脱(プロトコルデビエーション)の有無と内容
- 次回訪問までのフォローアップ事項

[訪問メモを貼り付け。患者名・患者ID・医療機関名など特定につながる情報は
 事前に記号(施設A、患者001など)に置き換えてから入力する]

出力は社内標準のモニタリング報告書フォーマットの見出し構成に合わせ、
事実と異なる推測が入りそうな箇所には[要確認]と明記してください。
```

出力は必ず原資料・訪問時のメモと突合し、逸脱の分類・重大性判定はCRA本人が最終確認する。患者・医療機関を特定できる情報は入力前に必ず匿名化・記号化する。

### プロンプト例2: 説明同意文書(ICF)の平易な言い換え案作成(CRC)

```
以下は治験の説明同意文書(ICF)の一部です。医学的な正確性を変えずに、
中学生でも理解できる平易な日本語に言い換えた案を作成してください。

- 専門用語は言い換えた上で、初出時に元の用語も括弧書きで残す
- 数値(有効率・副作用の発生率など)は原文の表記のまま変更しない
- 3つのバージョン(平易度: 標準/やや平易/かなり平易)を並べて出力する

[説明同意文書の該当セクションを貼り付け]

出力後、言い換えによって医学的な意味やリスクの重大さの印象が変わっていないか、
チェックすべき論点を箇条書きで示してください。
```

年齢層によっては平易化した文章の方が理解度が下がる場合があることが研究で示されているため、最終的な文面と説明方法は治験責任医師・IRB(治験審査委員会)の確認と承認を経る。1つの言い換え案を全患者に一律適用せず、患者の理解度に応じて説明方法を調整する運用が望ましい。

### プロンプト例3: CRF記載の整合性チェック依頼(CRA/CRC)

```
以下は同一患者(記号:患者003)について、来院時期の異なる複数のCRFページの記載内容です。
記載内容に矛盾や表現の不統一がないか確認してください。

- 日付・数値の矛盾がないか
- 同じ症状・所見について表現がページごとに揺れていないか
- 前回記載と比較して不自然な変化がある場合は指摘する

[各来院時のCRF記載(匿名化済み)を貼り付け]

出力は「要確認箇所」の一覧のみとし、記載内容そのものの修正案は提示しないでください。
```

生成AIには「矛盾点の指摘」までを依頼し、実際の修正・原資料との突合はCRA・CRC本人が行う。CRFの記載内容そのものをAIに生成させると、原資料に基づかない記載(ALCOA+のOriginal/Accurateに反する記録)になりかねないため、この線引きを崩さない。

### プロンプト例4: プロトコル逸脱(デビエーション)記録の要約(CRA)

```
以下のプロトコル逸脱の発生報告から、社内の逸脱管理台帳に登録するための
要約を作成してください。

- 発生日、発見日、発見の経緯
- 逸脱の内容(何がプロトコルのどの規定と異なったか)
- 患者への影響の有無(分かっている範囲)
- 治験依頼者への報告要否について、確認すべき論点

[逸脱の発生報告(匿名化済み)を貼り付け]

重大性の分類(軽微/重大/緊急)は提案のみとし、「最終判断は治験責任医師・
治験依頼者の確認が必要」と明記してください。
```

逸脱の重大性判定・当局報告の要否は必ず治験責任医師・治験依頼者・場合によってはIRBの判断を経る。AIの提案はあくまで一次分類のたたき台である。

### ツール横断の対応表

| 用途 | ツール例 |
|---|---|
| モニタリング報告書・CRFの下書き・翻訳(汎用) | ChatGPT/Claude/Gemini(法人契約、データ学習オプトアウト確認済みのもの) |
| CSR(治験総括報告書)の自動生成 | 国立がん研究センター中央病院×ロゼッタの共同研究AIソフト(医師主導治験向け、外部提供は今後の展開次第) |
| CRO独自のAIエージェント・スイート | ParexelAI(パレクセル)、IQVIA×NVIDIAのオーケストレーターエージェント |
| 規制情報・GCP関連の社内検索 | IQVIAサービシーズジャパンのAmazon Bedrock RAGチャット(社内利用) |
| リスクベースモニタリング(RBM) | EPS・シミック・新日本科学PPD等のCRO各社が提供するRBM/中央モニタリングサービス |
| DCT基盤・eConsent | NTTデータ「PhambieLINQ」、3Hメディソリューション、DCT Japan等のDCT/eConsentベンダー |

## 注意点・よくある誤解

- **CRF・モニタリング報告書はAIに「生成」させず「下書き」までにとどめる**: これらは規制当局への提出・GCP監査の対象になる記録であり、ALCOA+の原則上、記載内容は必ず原資料(カルテ等)に基づく必要がある。AIの出力を原資料と照合せずにそのまま登録すると、記録の信頼性そのものが崩れる。
- **患者・治験参加者の個人情報は入力前に必ず匿名化・記号化する**: 生成AIサービスに入力したデータが学習・改善に利用され得るリスクは個人情報保護委員会も注意喚起している。患者名・患者ID・医療機関名など特定につながる情報は、記号(患者001、施設Aなど)に置き換えてから入力する。
- **ICF(説明同意文書)の平易化は年齢層で効果が異なる**: 厚生労働科学研究の検証では、説明文書を大幅に短く平易化したことで全体の理解度は向上したが、50〜70代では逆に理解度が下がったケースもあった。1つの平易化案を全患者に一律適用せず、対象患者層に応じて説明の仕方を調整する。
- **治験依頼者(スポンサー)ごとに生成AI利用の可否・範囲が異なる**: CRO・SMOに所属するCRA・CRCは、自社の判断だけでなく治験依頼者との契約・SOP(標準作業手順書)でAI利用の範囲が制限されている場合がある。新しいツールを使い始める前に、担当する治験の契約条件・依頼者の方針を確認する。
- **「AIが治験文書を作った」という記録も残す運用にする**: ICH E6(R3)は技術中立の立場を取るが、使う技術が目的に適合していることの説明・文書化を求めている。どの文書のどの部分にAIを使ったかを社内で追跡できる状態にしておく。

## 最初の一歩

まずはリスクの低い業務から試す。CRAであれば匿名化済みのモニタリング報告書メモの英訳・体裁整えを、CRCであればICF(説明同意文書)の一部を平易な言い換え案として汎用チャットAIに作らせ、原資料・原文との突合にどれだけ時間がかかるかを比較してみる。
