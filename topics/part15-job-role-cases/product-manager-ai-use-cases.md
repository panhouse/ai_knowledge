# プロダクトマネージャー(PdM)職における生成AI活用事例

## これは何か

プロダクトマネージャー(PdM、既存のデジタルプロダクトの仕様・バックログ・ロードマップの実行に責任を持つ職種)の仕事は、「ユーザーインタビュー・レビュー・問い合わせのテキストを読み込んで課題を見つける」「PRD(Product Requirements Document、製品要件文書)やユーザーストーリーを書く」「開発チーム向けのチケットに落とし込む」「経営陣・営業向けにロードマップを説明する」といった、大量のテキストの読み書きが業務時間の多くを占める。生成AIはこの「読む→整理する→書く」の各工程を下書きレベルまで自動化できるため、PdMが本来集中すべき「何を作るか・なぜ作るかの意思決定」に時間を回せるようになる。

なお本ページは「企画職」とは異なる職種を扱う。[企画職における生成AI活用](./planning-ai-use-cases.md)が扱うのは、まだ形になっていない事業・商品アイデアを0→1で発想し、企画書として通す仕事(発散→収束→提案のサイクル)である。それに対し本ページのPdMは、**既に存在するプロダクトの仕様・バックログ・ロードマップの実行責任者**であり、日々の仕事は「ユーザーの声を要件に変換する」「要件をエンジニアが着手できる粒度に分解する」「進行中の開発の状況を関係者に説明する」という、1→10・10→100フェーズの継続的な運用業務が中心になる。ブレインストーミングやTAM/SAM/SOMのような0→1の話は[企画職のページ](./planning-ai-use-cases.md)を参照してほしい。

## 仕組み・背景

PdMの業務が生成AIと相性がよい理由は、扱う情報の多くが「構造化されていない大量のテキスト」と「型の決まった構造化ドキュメント」という、生成AI(特に大規模言語モデル、LLM)が得意な2つの形に集約されるためである。

1. **非構造化テキストの要約・分類**: ユーザーインタビューの逐語録、アプリストアのレビュー、サポートチケット、Slackでの社内フィードバックなどは、量は多いが1件ずつは短く、人が全部読んで頭の中でテーマ分けするのは時間がかかる。LLMは大量のテキストを読み込んで「頻出する不満・要望を◯個のテーマに分類する」といった集約処理を得意とする。
2. **型の決まった文書の下書き生成**: PRD・ユーザーストーリー・受け入れ基準・チケットのタイトルと説明文は、業界・チームごとにある程度定型のフォーマットが存在する。箇条書きのメモや会話の要約を渡せば、その型に沿った文章の初稿をAIに作らせやすい。

この2つの用途に対応する形で、ツールも二層構造になっている。ChatGPT・Claude・Geminiのような汎用チャットAIは、その場でテキストを貼り付ければ要約・下書きができる汎用性の高さが強みである。一方、Productboard・Dovetail・Atlassian Intelligence(Jira組み込みのAI機能)のようなPdM向け専用ツールは、AIが**自社の蓄積された顧客フィードバックやチケット履歴に直接アクセスできる**状態で組み込まれている点が異なる。たとえばProductboardのAI機能「Spark」は、過去にひもづけられた顧客フィードバックを参照しながら機能仕様の草稿を作成でき、DovetailのAI機能「Magic AI」は蓄積されたインタビュー・調査データ全体を横断してテーマ抽出を行う。汎用チャットAIは「今貼り付けた分だけ」を処理するのに対し、専用ツールは「これまで溜めてきたデータ全体」を背景知識として使える、という違いが使い分けの軸になる。

## 使いどころ・使い分け

### PdM業務フェーズ別のAI活用マップ

| 業務 | 主なタスク | 向くツール | 理由 |
|---|---|---|---|
| フィードバック収集・分析 | インタビュー逐語録・レビュー・サポートチケットのテーマ抽出、頻出要望の集計 | 汎用チャットAIまたはDovetail等の専用ツール | 件数が少なければ汎用AIで十分。継続的・大量に溜まるなら専用ツールで自動化 |
| 要件定義・仕様策定 | PRDドラフト作成、ユーザーストーリー・受け入れ基準の作成 | 汎用チャットAI(過去のPRDをコンテキストに読み込ませる)、またはProductboardのAI機能 | 型の決まった文章の生成はどちらでも可。過去フィードバックとの紐づけまで自動化したいなら専用ツール |
| 競合分析 | 競合機能の比較表作成、差分の整理 | 汎用チャットAI(Web検索・Deep Research機能併用) | 事実確認が必要な調査は[Deep Research系機能](../part12-business-practice/ai-research-and-information-gathering.md)の使い方に準じる |
| 実験設計 | A/Bテストの仮説設計、成功指標の設定 | 汎用チャットAI | その場の壁打ちに向く。統計的な有意性の判断は人・データアナリストが担う |
| 開発チームとの連携 | Jira/Linearチケットの下書き、エピックのユーザーストーリーへの分解 | Atlassian Intelligence(Jira組み込み)または汎用チャットAI | Jira上で完結させたいならAtlassian Intelligence、下書きを別途作ってから貼り付けるなら汎用AIでも可 |
| ステークホルダー向け説明 | ロードマップの進捗説明、経営会議向けのナラティブ作成 | 汎用チャットAI | 読み手のレベルに応じた言い換えが得意。詳細は[文章作成・編集の実務活用](../part12-business-practice/ai-writing-and-editing.md) |

### 汎用チャットAI vs PdM専用ツールの判断基準

| 判断軸 | 汎用チャットAI(ChatGPT/Claude/Gemini) | PdM専用ツール(Productboard/Dovetail等) |
|---|---|---|
| 参照したいデータの量 | 今回貼り付けた分だけで十分 | 過去に蓄積した大量のフィードバック・チケットを横断したい |
| 導入のハードル | 既存の法人契約があればすぐ使える | 別途契約・データ連携(Zendesk・Intercom等との統合設定)が必要 |
| コスト | 個人〜チームプランで数千円/月台から | 専用ツールは追加でmaker(編集者)課金が発生することが多い |
| 向くタスク | 単発の下書き・壁打ち・要約 | 継続的なフィードバック収集・自動テーマ分類・仕様と顧客の声の自動紐づけ |

判断の軸は「同じ処理を何度も繰り返すか」「参照すべき過去データが社内システムに蓄積されているか」。単発の作業や小規模チームは汎用チャットAIで十分間に合うことが多く、フィードバック件数が多く継続的に分析が必要になった段階で専用ツールの導入を検討するのが実務的な順序である。

## 実務での使い方

### プロンプト例1: ユーザーフィードバック要約(テーマ抽出)用プロンプト

インタビューメモ・レビュー・サポートチケットなど雑多なテキストを、意思決定に使えるテーマに集約する。

```
あなたはプロダクトマネージャーの分析アシスタントです。以下は、直近1ヶ月分の
ユーザーインタビューの逐語録・アプリストアのレビュー・サポートチケットの抜粋です。

【入力データ】
(インタビュー逐語録・レビュー・チケット本文を貼り付け。出典の種類がわかるように
「[インタビューA]」「[レビュー]」「[サポートチケット#123]」のように印をつける)

【依頼内容】
1. 頻出する課題・要望を5〜8個のテーマに分類してください
2. 各テーマについて、該当する発言の件数と、代表的な発言を1〜2件引用してください(出典の印も残す)
3. 各テーマがユーザーのどんな業務・状況で発生しているかを1文で補足してください
4. 単発の意見と、複数のユーザーから共通して出ている意見を区別して明記してください
5. テーマの緊急度・影響度についてのあなたの推測は「推測」と明記し、断定しないこと
```

「出典の印を残す」「単発意見と共通意見を区別する」の2点が、後で「本当にそのテーマが多数派の声か」を検証する際の頼りになる。件数の少ないテーマを多数派であるかのように書かせないため、必ず件数を出力させる。

### プロンプト例2: PRDドラフト生成用プロンプト

箇条書きのメモから、PRDの初稿を作らせる。いきなり全文を書かせず、まず骨子を確認してから肉付けさせる2段階が手戻りを減らす。

```
あなたはプロダクトマネージャーのPRD作成を支援するアシスタントです。
以下の機能アイデアについて、まずPRDの章立て(骨子)だけを提案してください。本文はまだ書かないでください。

【機能アイデアの概要】
[例: サポートチケットの一次回答をAIが下書きするアシスト機能]

【背景・課題(前段のフィードバック要約から転記)】
[プロンプト例1で出てきたテーマのうち、該当するものを貼り付け]

【対象ユーザー】
[例: カスタマーサポート担当者、1日50件以上のチケットを処理]

【出力条件】
- 一般的なPRDの型(背景・課題 / ゴールと非ゴール / 想定ユーザー / 要件 / 受け入れ基準 /
  計測指標 / リスク・未解決の論点)をベースに、この機能特有の論点を追加提案してほしい
- 「非ゴール(やらないこと)」の章を必ず含める
```

骨子を確認・修正したら、「要件の章を肉付けしてください」のように章ごとに依頼していくと、一度に長文を書かせて論点がぼやける事故を防げる。

### プロンプト例3: ユーザーストーリー・受け入れ基準の作成

```
以下の要件をもとに、開発チームがそのままバックログに追加できる粒度で
ユーザーストーリーと受け入れ基準(Acceptance Criteria)を作成してください。

【要件】
[例: サポート担当者がチケット一覧画面でAIの回答下書きをワンクリックで挿入できるようにする]

【出力形式】
- ユーザーストーリーは「〜として、〜したい。なぜなら〜だから」の形式で書く
- 受け入れ基準はGiven-When-Then形式(前提条件・操作・期待結果)で3〜5個
- エッジケース(下書き生成に失敗した場合、チケットが空の場合など)も1〜2個含める
- 見積もりや技術的な実現方法には踏み込まない(エンジニアの領域として空欄にする)
```

「技術的な実現方法には踏み込まない」と明記しておくと、AIが実装方法まで断定してエンジニアとの認識齟齬を生むのを防げる。

### プロンプト例4: 競合機能比較表の作成

```
あなたはプロダクト戦略のリサーチアシスタントです。以下の競合3社について、
Web検索を使って直近の情報を調べ、機能比較表を作成してください。

【対象】
自社: [製品名・現在の主要機能]
競合: [競合A]、[競合B]、[競合C]

【比較したい機能軸】
[例: AIによる回答下書き機能の有無、対応言語数、料金プランごとの上限、SSO対応]

【出力条件】
- 各セルの情報には出典URLと確認日を明記する
- 公式サイトで確認できなかった項目は「不明」とし、推測で埋めない
- 料金・機能は変更されやすいため、閲覧日時点の情報である旨を明記する
```

競合の機能情報は変更頻度が高く、AIの学習データが古い場合があるため、Web検索・Deep Research機能を使わせ、必ず出典を明記させる(考え方は[生成AIによる情報収集・リサーチの実務活用](../part12-business-practice/ai-research-and-information-gathering.md)を参照)。

### プロンプト例5: A/Bテスト仮説設計用プロンプト

```
あなたはプロダクトのグロース施策を検討するアナリストです。以下の課題について、
A/Bテストの仮説設計のたたき台を作成してください。

【課題】
[例: チェックアウト画面の離脱率が業界平均より高い]

【出力条件】
1. 想定される原因仮説を3つ挙げ、それぞれ「なぜそう考えるか」の根拠を添える
2. 各仮説に対応する具体的な施策案(ボタン文言変更、入力項目削減など)を1つずつ
3. 各施策の成功指標(メインKPIと、悪化していないか確認すべきガードレール指標)を提案する
4. サンプルサイズ・実施期間の目安を、想定トラフィック(下記)から概算する

【前提】
[例: 該当画面の月間訪問者数は10万人、現在の離脱率は45%]

このたたき台はあくまで仮説であり、実際のテスト設計・統計的な有意性判定はデータアナリストと
すり合わせる前提とする、と最後に明記してください。
```

サンプルサイズの概算はAIに出させても構わないが、実際のテスト設計・有意水準の判定は必ずデータアナリストや統計の知識を持つ担当者が確認する。

### プロンプト例6: ロードマップのステークホルダー向けナラティブ作成

```
以下は開発チーム内部で使っているロードマップのメモ(機能名・優先度・想定時期)です。
これを経営会議向けに、「なぜこの順序で進めるのか」が伝わるナラティブ(物語形式の説明文)に
書き換えてください。

【読み手】製品の技術的な詳細には詳しくないが、投資判断を行う経営陣
【元のロードマップメモ】
(社内向けメモを貼り付け)

【出力条件】
1. 各施策を「顧客のどんな課題を解決するか」から書き始める(機能名を主語にしない)
2. 優先順位の理由(なぜこれが先か)を1文ずつ添える
3. 未確定の時期については「予定」であり確約でないことを明記する
```

### ツール横断の対応付け(2026年7月時点)

| PdMの業務 | 汎用チャットAI(ChatGPT/Claude/Gemini) | PdM特化ツール |
|---|---|---|
| フィードバックのテーマ抽出 | 貼り付けた逐語録・レビューをその場で要約 | **Dovetail**の「Magic AI」: 蓄積したインタビュー・調査データを横断してテーマ検出・感情分析・ハイライト抽出を自動化。Professionalプランは1エディター月39〜49ドル程度(年払い)、Freeプランあり |
| PRD・機能仕様の下書き | ChatGPTの「Projects」・Claudeの「Projects」・Geminiの「Gems」に過去のPRDや製品コンテキストを読み込ませて生成 | **Productboard**の「Spark」: 紐づけ済みの顧客フィードバックを参照しながら機能仕様のドラフト・課題文の要約を生成。2026年時点の主要プランは「Spark」1名月15ドル(年払い)〜19ドル(月払い)で、AI利用はクレジット制(月250クレジット/人、追加購入可) |
| PRD・仕様書のドキュメント管理 | 汎用AIで下書きを作り、社内ドキュメントツールに転記 | **Notion AI**: ワークスペース内のPRDテンプレートに直接AIで加筆・要約を生成。企業向け契約ではOpenAI/Anthropicへの学習利用がされない契約になっている |
| Jira/Linearチケットの下書き・分解 | 汎用AIで下書きし手動でJira/Linearに転記 | **Atlassian Intelligence**(Jira組み込み): 自然文からJQL(Jira Query Language)への変換、大きなエピックをユーザーストーリーに分解する「AI Work Breakdown」、長いチケットの要約機能。Jira Premiumプラン(1名月14.54ドル程度)にAI機能が含まれ、追加のライセンス費用は不要 |

判断の目安は前掲の「使いどころ・使い分け」の表の通り、継続的に大量のデータを扱うかどうかである。立ち上げ期のチームやフィードバック件数がまだ少ないチームは、まず汎用チャットAIで運用してみて、件数が増えて手作業が追いつかなくなった段階で専用ツールの導入を検討すればよい。

## 注意点・よくある誤解

- **競合機能比較表の情報は必ず一次情報で裏取りする**: 競合の機能・料金は変更頻度が高く、AIの学習データは常に最新とは限らない。特に「競合が◯◯機能を持っている」という記述は、AIが古い情報や別製品の情報と混同して生成することがある(ハルシネーションの詳細は[ハルシネーションとは何か・対策](../part04-risk-security/hallucination-and-countermeasures.md)を参照)。重要な意思決定に使う比較表は、公式サイト・料金ページのスクリーンショットや直接確認したURLを添えて社内共有する。
- **フィードバックのテーマ抽出は「声の大きさ」に引っ張られやすい**: AIによるテーマ抽出は、入力したテキストの中で頻出する表現に反応しやすいため、たまたま同じ言い回しで書かれた少数の意見を「多数派の要望」であるかのように集約してしまうことがある。件数・出典を必ず出力させ、実際に元データに戻って確認する運用にする。
- **AIが生成した受け入れ基準・見積もりをそのまま鵜呑みにしない**: ユーザーストーリーの受け入れ基準の下書きは有用だが、技術的な実現可能性や工数の判断はエンジニアの領域であり、AIに代替させるべきではない。プロンプトで「技術的な実現方法には踏み込まない」と明示し、エンジニアとの認識齟齬を防ぐ。
- **未リリースのロードマップ・非公開の顧客データを無料プランの汎用AIに入力しない**: ロードマップや価格戦略、顧客の個人情報を含むフィードバックデータは機密性が高い。学習利用のポリシーが契約によって異なるため、法人向けプラン(学習への非利用が原則の契約)を使うか、社内承認済みのPdM専用ツールを使う(詳細は[生成AI利用における情報漏洩対策](../part04-risk-security/information-leakage-prevention.md)を参照)。
- **A/Bテストの統計判断はAIに任せきりにしない**: サンプルサイズ・有意水準の概算はAIに出させても構わないが、実際のテスト設計・結果の統計的な解釈は、必ずデータアナリストや統計の知識を持つ担当者が確認する。表形式のデータをAIに読ませて分析する際の一般的な注意点は[AIが扱いやすいデータ形式](../part07-data-analysis/ai-friendly-data-formats.md)も参照。

## 最初の一歩

直近1〜2週間分のユーザーレビューやサポートチケットを1つのテキストにまとめ、プロンプト例1のテーマ抽出プロンプトで要約させてみる。出てきたテーマのうち件数が多いものを1つ選び、元データに戻って本当にその件数だけの声があったかを確認する。
