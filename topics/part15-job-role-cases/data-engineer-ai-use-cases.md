# データエンジニアにおける生成AI活用事例

## これは何か

データエンジニアは「アプリケーションを作る」のではなく、**社内外の様々なデータソースを、分析やAIが使える形に集めて・整えて・届け続ける**仕事を担う。具体的にはETL/ELT(Extract-Transform-Load、データを抽出・変換・格納する処理)パイプラインの構築、dbt(data build tool、データ変換ロジックをSQLで書き、テスト・ドキュメント・依存関係をコードとして管理するツール)によるデータモデルの実装、スキーマ(テーブル・カラムの構造)設計、データ品質の監視、そしてそれらの仕様をドキュメントとして残す作業が中心になる。

[エンジニア・開発職における生成AI活用事例](engineer-development-ai-use-cases.md)がソフトウェア開発全般のSDLC(開発ライフサイクル)運用を扱うのに対し、本ページは**データパイプライン・データ基盤の開発運用**という特定領域に絞り、「dbtモデル・SQLの生成」「パイプライン障害の調査」「データ品質異常のトリアージ」「スキーマ設計とドキュメント生成」という、データエンジニア固有の作業に生成AIがどう組み込まれているかを整理する。BIダッシュボードを使って数字を読み解く[データアナリスト/BIアナリスト職における生成AI活用事例](data-analyst-ai-use-cases.md)や、システム基盤の安定運用を担う[SRE・インフラエンジニアにおける生成AI活用事例](sre-infrastructure-engineer-ai-use-cases.md)とは、「データそのものの構造と品質を作り込む」という点で役割が異なる。

## 仕組み・背景

データエンジニアリングにおける生成AI活用が急速に進んだ背景には2つの技術的な追い風がある。

1. **dbtという「型」との相性の良さ**: dbtはSQL(構造化データを扱う定型的な言語)でデータ変換ロジックを書き、テスト・ドキュメント・依存関係(lineage)をコードとして管理する。SQLは生成AIが最も精度高く書ける言語の一つであり、かつdbtの `schema.yml`(モデルの列定義やテストを書く設定ファイル)や `manifest.json`(dbtプロジェクト全体の構造情報)という構造化されたメタデータが存在するため、AIエージェントに「何をどう作ればよいか」を渡しやすい。dbt Labs自身も2025年に「dbt Copilot」という、自然言語からSQL・テスト・ドキュメント・セマンティックモデルを自動生成するAI機能をdbt Cloudに統合している([出典](https://www.getdbt.com/blog/ai-data-engineering))。
2. **「仕様書ドリブン」への接続**: [エンジニア・開発職における生成AI活用事例](engineer-development-ai-use-cases.md)で触れた「仕様書を先に固めてからAIに実装させる」流れは、データエンジニアリングでは「Data Contract(データの構造・型・品質要件をYAML形式などで定義した契約書)を先に書き、それをAIエージェントに渡してパイプラインコードを生成させる」という形で応用されている(後述の電通総研の事例)。

一方で、SQL・dbtモデルはBIダッシュボードや機械学習モデルなど下流の多数のシステムに影響するため、「文法的に正しいが集計ロジックが業務的に間違っている」コードが生成されても気づきにくいという、この職種特有のリスクがある([データアナリスト/BIアナリスト職における生成AI活用事例](data-analyst-ai-use-cases.md)の「仕組み・背景」で触れたセマンティックレイヤーの問題と同根)。そのため、以下の事例に共通するのは「AIに書かせて終わり」ではなく、命名規約・テストマクロ・レビュー体制といった**ガードレール(逸脱を防ぐ仕組み)を先に設計してからAIを使う**という運用の工夫である。

## 使いどころ・使い分け

### 業務フェーズ別の活用マップ

| 業務フェーズ | AIに任せやすい作業 | 人が担うべき判断 | 主なツール種別 |
|---|---|---|---|
| 要件の言語化・スキーマ設計 | テーブル設計案のたたき台、命名規約に沿ったDDL(テーブル定義)の下書き | 業務上の意味付け(このカラムは何を表すか)、正規化の妥当性 | 汎用チャットAI、AIコーディング支援 |
| dbtモデル・SQL生成 | 定型的な変換ロジック、テストコード(primary key・not null等)の生成 | 集計ロジックの業務的な正しさ、JOIN条件の妥当性 | AIコーディング支援(Cursor、Claude Code)、dbt Copilot |
| パイプライン障害調査 | エラーログの要約、過去の類似障害の自然言語検索、原因候補の絞り込み | 本番影響範囲の判断、ロールバック要否の意思決定 | 汎用チャットAI、データオブザーバビリティツール |
| データ品質異常のトリアージ | 異常検知アラートの一次要約、影響テーブルの洗い出し | アラートが「本当の異常」か「仕様変更による正常な変化」かの判断 | データオブザーバビリティツール(Monte Carlo等) |
| ドキュメント・カタログ整備 | テーブル・カラムのdescription下書き、lineage図の説明文生成 | 用語の社内標準との整合、機微情報(個人情報カラム等)のマスキング要否 | dbt Copilot、汎用チャットAI |

### 使うべきでない場面

- **本番データへの書き込み・DDL実行をAIエージェントに単独で任せる**: マイグレーション(スキーマ変更)や本番データの削除・更新は、人間のレビューと承認を経てから実行する。AIエージェントに直接実行権限を渡す設計は、後述の10Xの事例のように「信頼できる(Trusted)データ層」を明確に区切り、エージェントがアクセスできる範囲を限定した上で導入するのが実務的な線引きである
- **個人情報(PII)を含むテーブルをそのまま汎用チャットAIに貼り付けて相談する**: スキーマ相談やエラー調査であっても、実データではなくダミーデータやカラム名・型情報だけを渡す
- **AIが生成したSQL・dbtモデルの集計結果を検証なしに経営指標として下流に流す**: 特に売上・KPIに関わるモデルは、生成後に必ずテスト(dbtのtestやアサーション)と既存値との突き合わせを行う

## 導入事例カタログ

### Uber(米国・配車/フードデリバリー、グローバル展開) — 対象業務: 社内データへの自然言語SQL生成(QueryGPT)
- **導入形態**: 内製(自社開発のAIエージェント)
- **段階**: 全社展開
- **やったこと**: 社内のデータプラットフォームチームが、自然言語の質問をSQLクエリに変換する「QueryGPT」を開発。LLM(大規模言語モデル)とRAG(検索拡張生成、関連する過去クエリやスキーマ情報を検索してAIに渡す仕組み)を組み合わせ、類似の過去クエリ・テーブルスキーマをベクトル検索で取得してからSQLを生成する構成にしている。データエンジニア・アナリスト・オペレーション担当者が日常的に使うツールとして全社展開されている
- **効果**: 月間約120万件のインタラクティブなクエリのうち、1件あたりの平均SQL作成時間を約10分から約3分に短縮(2024年時点、Uber公式ブログでの自社公表)
- **学べること**: 「AIにゼロからSQLを書かせる」より「社内の過去クエリ・スキーマ情報をRAGで検索して渡す」設計の方が、業務文脈に沿った精度の高いSQLが出やすい
- **出典**: [QueryGPT – Natural Language to SQL Using Generative AI(Uber公式ブログ)](https://www.uber.com/us/en/blog/query-gpt/) / 最終確認日: 2026-09-10

### Pinterest(米国・SNS/画像共有プラットフォーム) — 対象業務: 社内BIツールへのText-to-SQL機能の組み込み
- **導入形態**: 内製(自社開発の社内ツールへの機能追加)
- **段階**: 全社展開
- **やったこと**: データエンジニアリングチームが、社内のSQLクエリツール「Querybook」(自社開発のオープンソースのビッグデータSQLクエリツール)に、自然言語の分析質問をSQLに変換するText-to-SQL機能を組み込んだ。既存の社内メタデータ(テーブル定義・過去クエリ)を活用して生成精度を高める設計にしている
- **効果**: 社内アナリスト・エンジニアがSQLを一から書かずに分析質問から直接クエリを生成できるようになった(2024年時点、Pinterest公式エンジニアリングブログでの自社公表。定量的な削減率は非公開)
- **学べること**: 汎用チャットAIに頼らず、既存の社内ツールにText-to-SQL機能を組み込むことで、社内の権限管理・監査ログの仕組みをそのまま流用できる
- **出典**: [How we built Text-to-SQL at Pinterest(Pinterest Engineering Blog)](https://medium.com/pinterest-engineering/how-we-built-text-to-sql-at-pinterest-30bad30dabff) / 最終確認日: 2026-09-10

### ラクスル株式会社(日本・印刷/物流のBtoBプラットフォーム) — 対象業務: dbtモデル開発の高速化とガードレール設計
- **導入形態**: 汎用チャットAI活用(Cursor、Claude Codeなどの汎用AIコーディング支援ツール)
- **段階**: 部門展開
- **やったこと**: データエンジニアリングチームが、dbtプロジェクトの命名規則の揺れ・レビュー負荷・オンボーディングの時間がかかるという課題に対し、Cursorの「Project Rules」機能(繰り返し使える指示セットを `.cursor/rules` に配置してAIエージェントの挙動を制御する仕組み)や、主キー用のカスタムテストマクロ、Claude Codeのカスタムコマンドで肥大化したプルリクエストを自動的に分割・作成する仕組みを整備した
- **効果**: dbt開発のレビュー負荷とオンボーディング時間の低減(2025年12月時点、自社テックブログでの自社公表。定量的な削減率は非公開)
- **学べること**: AIコーディング支援ツールを「そのまま使う」のではなく、命名規約・テストマクロ・PR分割ルールをAIエージェント向けの設定ファイルとして先に整備することが、チーム開発でのAI活用を安定させる鍵になる
- **出典**: [生成AI で dbt の開発を加速させるための「ガードレール」とTips(RAKSUL TechBlog)](https://techblog.raksul.com/entry/2025/12/09/000000) / 最終確認日: 2026-09-10

### 株式会社MonotaRO(日本・工業用間接資材のEC) — 対象業務: AI活用によるデータパイプライン開発スタイルの刷新
- **導入形態**: 汎用チャットAI活用(AIコーディング支援ツールをデータパイプライン開発に適用)
- **段階**: 部門展開
- **やったこと**: データ部門が「言えば作れる」を掲げ、AIコーディング支援ツールを使ってデータパイプラインの実装を進める開発スタイルへの移行を進めた。要件を自然言語で伝えるとパイプラインのコードが生成される流れを構築し、次世代の開発スタイルとして社内テックブログで発信している
- **効果**: パイプライン開発における実装スピードの向上(2025年6月時点、自社テックブログでの自社公表。定量的な削減率は非公開)
- **学べること**: 「AIを使えば速くなる」という単純な導入ではなく、開発スタイル自体(要件の伝え方、レビューの入れ方)を見直すセットで進めると定着しやすい
- **出典**: [『言えば作れる』時代の到来:AI×データパイプラインで実現した次世代開発スタイル(MonotaRO Tech Blog)](https://tech-blog.monotaro.com/entry/2025/06/05/090000) / 最終確認日: 2026-09-10

### 株式会社10X(日本・ネットスーパーSaaS「Stailer」) — 対象業務: dbt開発・データ調査へのAIエージェント導入とガードレール設計
- **導入形態**: 汎用チャットAI活用(Claude Code、Devinなどの汎用AIコーディング/自律エージェントツール)
- **段階**: 部門展開
- **やったこと**: データエンジニアリングチームが、Claude Codeでdbt開発を行う際のガードレール(dbtのメタデータで「信頼できる(Trusted)データ」層を明示し、アドホックなデータマートはエージェントから見えないようにする、など)を設計。加えて自律型AIエージェント「Devin」と組んでデータエンジニアの定型的な困りごと(調査・軽微な修正)を解消する取り組みも進めている
- **効果**: dbt開発におけるAIエージェント活用時の誤ったクエリ生成・意図しないデータアクセスのリスク低減(2025年時点、自社カンファレンス発表資料での自社公表。定量的な効果は非公開)
- **学べること**: AIエージェントに「何を見せて何を見せないか」というデータアクセス範囲の設計が、dbt特有のメタデータ(YAML定義)を使えば比較的容易に実現できる
- **出典**: [dbt開発 with Claude Codeのためのガードレール設計(10X Speaker Deck)](https://speakerdeck.com/10xinc/dbtkai-fa-with-claude-codenotamenogadorerushe-ji) / 最終確認日: 2026-09-10

### 株式会社電通総研(日本・SIer/コンサルティング) — 対象業務: Data Contractを起点にしたデータパイプラインコードの自動生成
- **導入形態**: 内製(検証段階のAI駆動開発手法)
- **段階**: PoC
- **やったこと**: エンジニアリング部門が、ODCS(Open Data Contract Standard)形式のData Contract(テーブル構造・型・品質要件をYAMLで定義した契約書)を生成AIに渡し、そこからdbtの変換ロジック(型キャスト、計算ロジック、JOIN条件、増分処理などのincremental設定)を自動生成する手法を検証した。生成されたコードがData Contractの定義通りに実装されているかを確認するというアプローチを取っている
- **効果**: Data Contractに定義した仕様通りのdbtモデル(型キャスト・計算ロジック・JOIN条件・incremental設定)が意図通り生成されることを確認(2025年12月時点、自社テックブログでの自社公表。本番導入の効果ではなく検証段階の結果)
- **学べること**: 自然言語のあいまいな指示ではなく、構造化されたData Contract(仕様書)を先に用意してAIに渡すことで、パイプラインコードの再現性・検証可能性が上がる
- **出典**: [データエンジニアリングのAI駆動開発: Data Contractを応用したデータパイプラインの生成(電通総研テックブログ)](https://tech.dentsusoken.com/entry/2025/12/08/%E3%83%87%E3%83%BC%E3%82%BF%E3%82%A8%E3%83%B3%E3%82%B8%E3%83%8B%E3%82%A2%E3%83%AA%E3%83%B3%E3%82%B0%E3%81%AEAI%E9%A7%86%E5%8B%95%E9%96%8B%E7%99%BA:_Data_Contract%E3%82%92%E5%BF%9C%E7%94%A8%E3%81%97) / 最終確認日: 2026-09-10

### 事例から見える傾向

現時点(2026年9月)の事例を見渡すと、進んでいるのは「①自然言語→SQL生成(Text-to-SQL)」と「②dbt開発へのAIコーディング支援ツールの組み込み」の2つで、いずれも共通して**「AIに何でも自由にやらせる」のではなく、アクセス範囲・命名規約・テストの形でガードレールを先に設計してから使う**という運用が定着しつつある。一方、Data Contractを起点にした自動生成(電通総研)のような、より高度な「仕様書からパイプライン全体を生成する」取り組みはまだPoC段階が多く、本番の全社展開に至った事例は少ない。日本企業ではdbtを既に採用している組織(EC・SaaS系企業が目立つ)がAIコーディング支援ツール(Claude Code、Cursor)を追加導入する形で始めるパターンが主流で、データ品質監視AI(データオブザーバビリティ)の本格導入事例は、国内では英語圏のベンダー事例に比べてまだ少ない。

## 実務での使い方(活用パターン)

### コピペで使えるプロンプト例

**1. 自然言語の要件からdbtモデルのたたき台を生成する**

```
あなたはデータエンジニアです。以下の要件から、dbtモデル(SQL)とschema.ymlのテスト定義を作成してください。

# 要件
- ソーステーブル: raw.orders(列: order_id, customer_id, order_status, order_amount, created_at)
- 作りたいもの: 日次の注文サマリーテーブル
  - 集計単位: 日付(created_atの日部分)
  - 指標: 注文件数、合計金額(order_amountの合計)
  - 条件: order_statusが「cancelled」の行は除外する
- incremental(増分)モデルにしたい。unique_keyはorder_dateとする

# 出力してほしいもの
1. models/marts/daily_order_summary.sql (dbtのincrementalモデルとして)
2. models/marts/schema.yml (not_null, uniqueのテストを含む)
3. 集計ロジックの前提(除外条件など)をコメントで明記
```

**2. パイプラインのエラーログを要約し原因の当たりをつける**

```
以下はAirflow(ワークフロー管理ツール)のタスク失敗時のログです。
1. 何のタスクが、どの処理で失敗したか
2. 考えられる原因を確度が高い順に3つ
3. 本番データへの影響範囲(このテーブルを参照している下流モデルがあれば注意喚起)
4. 次に確認すべきログ・テーブルの候補
を日本語で整理してください。個人情報や実データの値は書かれていない前提で、ログの構造から判断してください。

--- ログここから ---
(エラーログを貼り付け)
--- ログここまで ---
```

**3. テーブル・カラムのドキュメント(description)下書きを生成する**

```
以下はdbtモデルのSQLとカラム一覧です。schema.yml用に、各カラムのdescriptionの下書きを日本語で作成してください。
- 業務的な意味が推測できないカラムは「(要確認: 用途不明)」と明記する
- 個人情報に該当しそうなカラム(氏名・メールアドレス・電話番号等)には「PII」のタグ候補を付ける

(SQLとカラム一覧を貼り付け)
```

### ツール横断の対応付け(2026年9月時点)

| やりたいこと | 汎用チャットAIで足りる範囲 | 専用ツールが必要になる境目 | 代表的なツール |
|---|---|---|---|
| SQL・dbtモデルの生成 | 単発のSQL・小さいモデルの下書き(ChatGPT/Claude/Geminiにスキーマ情報を貼って相談) | 社内スキーマ・過去クエリを踏まえた自動生成、リポジトリ全体の一括編集 | GitHub Copilot(Business: 1ユーザー月19ドル)、Cursor(Pro: 月20ドル、Teams: 1ユーザー月40ドル)、Claude Code、dbt Cloud統合の「dbt Copilot」 |
| パイプライン障害調査 | ログ・エラーメッセージを貼って一次切り分け | 本番環境への横断的なlineage(依存関係)追跡、自動異常検知 | データオブザーバビリティ専用SaaS(Monte Carlo等) |
| データ品質異常の検知・トリアージ | 単発の異常値についてAIに壁打ちする | 継続的な監視、freshness(鮮度)・volume(件数)異常の自動検知と根本原因分析 | Monte Carlo、Databricksのデータ品質監視機能、dbtのtest機能 |
| スキーマ・カタログのドキュメント化 | 少数テーブルのdescription下書き | 大量テーブルの一括生成、Data Contract(YAML仕様書)からのコード生成 | dbt Copilot、Snowflake Cortex AI、内製のData Contract連携ツール |

料金は為替や契約形態により変動するため、導入検討時は各社公式サイトで最新の金額を確認すること。

## 注意点・よくある誤解

- **「文法的に正しい」と「業務的に正しい」は別物**: AIが生成したSQL・dbtモデルは実行できてしまうため、集計ロジックの誤り(キャンセル行の除外漏れなど)に気づきにくい。生成後は必ず既存の集計値との突き合わせ、またはdbtのテストで検証する
- **AIエージェントに渡すスキーマ情報は最小限に**: テーブル定義・カラム名・型情報だけを渡し、実データ(特にPIIを含む値)は貼り付けない。dbtのメタデータ機能で「信頼できるデータ層」を明示し、エージェントのアクセス範囲を限定する設計(10Xの事例を参照)が有効
- **本番DDL・マイグレーションの自動実行は避ける**: スキーマ変更や本番データへの書き込みは、AIが下書きを作っても実行は人間が承認するフローを残す
- **ガードレールを先に作ってからAIを使う**: 命名規約、テストマクロ、PRの分割ルールなど、チームの開発規約をAIエージェント向けの設定ファイル(Cursorの `.cursor/rules`、Claude Codeのカスタムコマンド等)として明文化してから導入すると、レビュー負荷の増大を防ぎやすい(ラクスル・10Xの事例を参照)
- **ドキュメント生成は「叩き台」であり最終責任は人にある**: AIが生成したカラムのdescriptionは、社内の用語定義やPIIタグの要否を人が確認してから公開する

## 最初の一歩

自分が普段書いているdbtモデル1つを選び、そのSQLとカラム定義を汎用チャットAI(ChatGPT・Claude・Geminiなど)に貼り付けて、上記の「テーブル・カラムのドキュメント下書き生成」プロンプトを試し、生成されたdescriptionを自分の理解と照合してみることから始めるとよい。
