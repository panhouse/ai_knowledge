# LLMの得意・不得意と挙動の特性

## これは何か

LLM(大規模言語モデル、Large Language Model)は、文章の生成・要約・翻訳では人間顔負けの流暢さを見せる一方、単純な四則演算や「文字を1つずつ数える」ような作業で平気で間違え、しかもその間違いを自信満々な口調で答える。この「得意・不得意の凸凹」は気まぐれな不具合ではなく、LLMの動作原理そのものに由来する構造的な性質であり、業務で使う場面ごとに予測できる。この凸凹を知らずに「AIだから何でも正確にできるはず」と思い込むと、計算ミスや古い情報をそのまま資料に転記してしまう事故につながる。逆に凸凹を知っていれば、どの作業をAIに任せ、どこで検算・裏取りを挟むべきかを事前に設計できる。

## 仕組み・背景

LLMの得意・不得意は、突き詰めると次の5つの動作原理から説明できる。それぞれの詳しい仕組みは他ページに譲り、ここでは「なぜその得意・不得意が生まれるか」の要点だけを押さえる。

1. **文章を「トークン」という断片に分割してから、次に来そうなトークンを確率的に予測している**(トークンの仕組み自体は[トークンとは何か](what-are-tokens.md)、次トークン予測の全体像は[LLMの仕組み:確率的単語予測と学習プロセス](llm-mechanism-basics.md)を参照)。この方式は「文章としてそれらしい続き」を作ることには非常に強いが、数値を1つの量として扱って正確に演算する仕組みや、文字を1文字ずつ数え上げる仕組みを内部に持たない。たとえば「strawberry」という単語が s-t-r-a-w-b-e-r-r-y と1文字ずつ処理されるのではなく "straw" "berry" のような塊(トークン)として処理されるため、「rは何回出てくるか」を尋ねると数え間違えることが知られている(いわゆる「ストロベリー問題」)。桁数の大きい掛け算・割り算も同様に、パターンの丸暗記に近い処理になりやすく、桁数が増えるほど誤りが増える。
2. **学習データは特定の時点までしか含まれない(ナレッジカットオフ)**。モデルは「訓練を終えた時点までにインターネット上に存在した情報」しか土台として持っておらず、それ以降に起きた出来事・発表された最新の価格や仕様・当日の株価や天気などは、Web検索やRAG(検索拡張生成)などの外部機能と組み合わせない限り原理的に答えられない。カットオフの日付はモデルごとに異なり、しかも同じ会社の中でも世代によってばらつく。たとえばOpenAIの公式モデルページは2026年7月投入のGPT-5.6のナレッジカットオフを2026年2月16日としているが、モデル自身に直接尋ねると「2025年12月」と自己申告することがあり、公式値と自己認識にズレが生じる場合がある。Anthropicは「training data cutoff(学習データの範囲)」と「reliable knowledge cutoff(内容が充実・正確な範囲)」を区別して公表しており、System Cardによれば2026年6月投入のClaude Sonnet 5は2026年1月、2026年7月投入のClaude Opus 5は2026年5月がカットオフとされる。Googleも2026年7月投入のGemini 3.6 Flashでカットオフを2026年3月まで進めており(ベースのGemini 3系は2025年1月)、いずれも新モデルほどカットオフは新しくなるが、「最新モデルだから当日の情報も知っている」わけではない点は変わらない。カットオフより後の話題を聞かれても、モデルは「わかりません」ではなく、それらしい推測で埋めてしまうことがある点は要注意。
3. **コンテキストウィンドウ(一度に読み書きできる文章量の上限)には限りがあり、長くなるほど内容の一貫性が落ちる**。上限自体の考え方や主要モデルの数値は[トークンとは何か](what-are-tokens.md)で扱っているためここでは繰り返さないが、実務で影響が出るのは「上限に収まっているか」だけでなく、長い文章・長い会話ほど途中の内容が軽視されやすい「Lost in the Middle」現象や、長時間の雑談・ロールプレイの中で最初に設定したキャラクター設定・話し方・ルールが徐々にぶれていく現象がある点。人間が長時間の作業で集中力が落ちるのに近いイメージで捉えておくと実務判断がしやすい。
4. **「わからない」より「自信を持って答える」方が学習・評価上有利になりやすい**。指示への忠実さを鍛えるアライメント(RLHFなど、詳細は[LLMの仕組み:確率的単語予測と学習プロセス](llm-mechanism-basics.md)を参照)の過程で、モデルは「断定して答える」応答を好まれやすく訓練される傾向があり、根拠が薄い質問にもそれらしい答えを作文してしまう。これが事実と異なる内容をもっともらしく生成する「ハルシネーション」の一因になる。ハルシネーションの発生要因・対策プロンプト・ファクトチェック体制の作り方は[ハルシネーションとは何か・対策](../part04-risk-security/hallucination-and-countermeasures.md)に譲り、本ページでは「得意・不得意の一種」として位置づけるにとどめる。
5. **統計的な相関パターンを学習しているだけで、因果関係や物理法則、ピクセル単位の正確さを内部に「モデル」として持っているわけではない**。文章生成の場合と同様に、画像を扱う際もLLM(正確にはマルチモーダル対応のモデル)は画像を「パッチ」と呼ばれる小さな断片に分割してから処理するため、グラフの目盛りの間隔や小さな数字、細かい罫線といった厳密なピクセル単位の値を正確に読み取るのは苦手で、近い値を"それらしく"答えてしまうことがある。2026年の研究では、定型的な書類読み取り(DocVQA)や標準的なグラフ読み取り(ChartQA)は最新モデルで95%・89%超まで正答率が上がっている一方、より難しい図表(複数系列の重なり、専門的な科学的可視化など)を対象にした新しいベンチマーク(ChartQAPro・VisuLogic・ChartMuseumなど)では正答率が大きく落ち込み、「見た目の分かりやすいグラフは得意になったが、複雑な図表はまだ解けていない」という二極化が報告されている。定型フォーマットの読み取りが得意になったからといって、非定型・専門的な図表まで信頼してよいとは限らない。同様に、学習データの中で「AとBが同時に起こりやすい」という相関パターンは拾えても、「AがBを引き起こす」という因果関係は相関から推測しているにすぎず、内部に検証済みの因果モデルを持っているわけではない。医療・経済分析などで「なぜそうなるか」を尋ねると、相関関係を因果関係であるかのように断定してしまうことがある。さらに、複数ステップにまたがる論理推論も各ステップをその場ごとに「それらしく」生成しているため、前半で立てた前提と後半の結論が矛盾する、同じ内容を聞き方を変えて尋ねると答えが変わる、といった一貫性の崩れが多段階になるほど起きやすいことが2025〜2026年の研究で指摘されている。

## 使いどころ・使い分け

### 得意な作業と不得意な作業の見取り図

| 得意(そのまま使いやすい) | 不得意(必ず一工夫か検証が必要) |
|---|---|
| 流暢な文章生成(メール・提案書・SNS投稿などの下書き) | 正確な四則演算・桁数の大きい計算 |
| 要約・翻訳(手元にある文章を対象にする場合) | 文字・単語の正確な数え上げ(「〇〇は何回出てくるか」等) |
| アイデア出し・ブレインストーミング・構成案の複数提示 | 学習時点より後の出来事・当日の株価や天気などのリアルタイム情報 |
| コードのドラフト生成・既存コードの説明・レビュー支援 | 長い会話・長文の中盤の内容を一貫して踏まえ続けること |
| 文章のトーン調整・言い換え・校正 | 長時間のやり取りでキャラクター設定・話し方・ルールを維持し続けること |
| 定型フォーマットへの整形・表形式への変換 | 「わからない」と言うべき場面で自信満々に誤った答えを出すこと(ハルシネーション) |
| 分類・仕分け(問い合わせ内容のカテゴリ分け、感情分析、スパム判定、大量文書への一次タグ付けなど) | 相関関係と因果関係の混同(データの相関を「原因と結果」であるかのように断定してしまう) |
| パターン認識・傾向把握(大量データからの類似文書グルーピング、異常の兆候の指摘、傾向の言語化) | 画像・グラフ・表内の細かい数値の正確な読み取り(目盛りの間隔、小さな文字、罫線のズレなど) |
| | 複数ステップにまたがる厳密な論理推論の一貫性維持(前提と結論の矛盾、聞き方を変えると答えが変わる) |

得意な作業は「文章としての自然さ・もっともらしさ」が評価基準になるものが多く、不得意な作業は「唯一の正解が存在し、それを一字一句・一桁も違えず出す必要がある」ものが多い、という軸で整理すると覚えやすい。

### 業務での信頼度早見表

同じ「LLMに任せる」でも、そのまま信じてよい作業・人間の確認を必須にすべき作業・そもそもLLM単体に向かない作業は分けて考える必要がある。

| 信頼度 | 作業の特徴 | 具体例 |
|---|---|---|
| **そのまま使ってよい** | 唯一の正解がなく、誤りがあっても実害が小さい。文章としての品質が評価基準 | アイデア出し・構成案作成、文章のトーン調整・言い換え、手元のテキストの要約下書き、雑談・壁打ち相手 |
| **必ず人が検証する** | 正解は存在するが、AIが間違える確率が無視できない | 計算結果・数量の集計、日付・固有名詞・引用の正確性、翻訳の最終稿(特に契約・対外文書)、生成されたコードを実行する前のレビュー、専門分野の事実主張 |
| **LLM単体には向かない(別の手段を使う)** | 唯一の正解が必須、かつAIの原理的な弱点に正面から当たる作業 | 当日・直近のリアルタイム情報(株価・為替・天気・速報ニュース)、大量データの正確な集計・統計処理、法的効力を持つ最終判断、再現性が保証された計算 |

判断基準はシンプルに「この作業の正解は1つに定まるか」「間違えたときの実害はどれくらいか」の2軸で見る。正解が1つに定まり、かつ実害が大きいほど、上の表の下側(人間の検証・別手段)に倒す。業務タスクごとの「AIに向く/向かない」の判断枠組みそのものは[生成AIに向く業務・向かない業務の切り分け](../part12-business-practice/ai-task-suitability.md)で詳しく扱っているため、あわせて参照するとよい。

## 実務での使い方

### タスクをAIに振る前の判断チェックリスト

新しい作業をLLMに任せられるかどうか迷ったら、依頼前に次の項目を確認する。1つでも該当すれば、そのまま鵜呑みにせず、人間の確認か専用ツールとの組み合わせを前提にする。

```
□ この作業の「正解」は1つに定まるか(定まる場合は必ず検証する)
□ 間違えたときの実害はどれくらいか(対外公開・金額・法的判断に関わるなら人間レビュー必須)
□ 画像・グラフ・表内の数値を正確に読み取る必要があるか(必要ならOCR専用ツールや原本での再確認を挟む)
□ 「なぜそうなるか」という因果関係を答えさせていないか(相関と因果を混同していないか根拠を確認する)
□ 学習データのカットオフより後の情報が必要か(必要ならWeb検索・RAGを使わせる)
□ 複数ステップの推論を要求していないか(要求する場合は途中経過を出力させ、前提と結論が矛盾しないか確認する)
```

### 分類・パターン認識はLLMが強い領域だが、境界線の甘さに注意

問い合わせメールのカテゴリ分け、アンケート自由記述の感情分析、大量文書への一次タグ付けといった分類・パターン認識はLLMが比較的得意とする作業で、ルールベースの分類ロジックを個別に組むより速く着手できる。ただし「境界線上の微妙なケース」を人間と同じ基準で判断できるとは限らないため、誤分類の許容度が低い業務(与信審査・コンプライアンス関連の仕分けなど)では、分類結果に確信度や分類理由も出力させ、確信度が低いものだけ人間が見直す運用にすると効率と精度を両立しやすい。

```
以下のテキストを与えられたカテゴリ一覧のいずれかに分類してください。
分類結果に加えて、判断の決め手になった箇所の引用と、
自分の分類にどれくらい自信があるか(高/中/低)を必ず添えてください。
「低」と判定したものは一覧の末尾にまとめて出力してください。
```

### 因果関係を尋ねるときは、相関との違いを明示的に区別させる

「なぜ売上が下がったのか」「この施策が効果があったと言えるか」のような因果関係を問う質問は、LLMが相関関係を因果関係のように断定しがちな典型的な不得意領域。次のように、相関と因果を切り分けて答えさせる指示を添えると、根拠のない断定を減らせる。

```
このデータから読み取れる関係について回答してください。回答の際は次を厳守してください。

1. 単なる相関(同時に起きている、傾向が似ている)と、因果関係(一方が他方の原因である)を明確に区別する
2. 因果関係を主張する場合は、それを裏付ける根拠(時系列の前後関係、比較対象群の有無、他の要因を排除できているか)を示す
3. 根拠が不十分な場合は「相関は確認できるが、因果関係は未検証」と明記する
```

真に因果関係を検証したい場合は、LLMの説明をそのまま採用せず、A/Bテストや統計的な因果推論の手法(差分の差分法など)による裏付けを別途行う。

### 画像・グラフ・表の数値を読み取らせるときは、必ず二重チェックする

決算資料のグラフや紙のアンケート集計表をAIに読み込ませて数値を抜き出させると、見た目には自然でもらしい値がまとまっているだけで、実際の目盛りとはズレていることがある。重要な数値ほど、以下のように読み取り結果を検証可能な形で出力させ、原本と突き合わせる一手間を省略しない。

```
この画像のグラフから、各項目の数値を表形式で抜き出してください。
読み取りに自信が持てない値には「概算」の注記を付けてください。
可能であれば、軸の目盛りと照らし合わせた根拠も一言添えてください。
```

抜き出した数値は、金額・法定開示資料などの重要書類では必ず元の画像・原本と目視で突き合わせる。桁数が多い表や大量の帳票を扱う場合は、AIの目視的な読み取りに頼らず、専用のOCR(光学文字認識)ツールや会計ソフトの読み取り機能と組み合わせる方が安全。

### 計算はLLMに「暗算」させず、コード実行機能を使わせる

LLMがテキスト予測として計算するのではなく、実際にプログラムを実行して答えを出す仕組み(コードインタープリタ/コード実行ツール)を持つツールでは、これを使わせた方が精度は大きく上がる。

| ツール | 機能名 | 使い方の場所 |
|---|---|---|
| ChatGPT | Advanced Data Analysis(旧Code Interpreter)。GPT-5.5では複雑な計算時に自動でPythonを呼び出すことがあるが、明示的に指示するとより確実 | プロンプトに「Pythonで計算して」と一言添える、またはファイルアップロード時に自動起動 |
| Claude | コード実行ツール(サンドボックス内でPython等を実行) | Claude.aiのチャットで自動的に使われることがある。API利用時は`code_execution`ツールを有効化 |
| Gemini | コード実行機能(Code Execution) | Gemini アプリ・AI Studioで数値計算を含む質問をすると自動で使われることがある |
| Copilot | Copilot Analyst等のPythonベースの分析エージェント | Copilotの「分析」系エージェントを明示的に選択 |

コピペで使える指示例(桁数の大きい計算・集計をさせるとき):

```
以下の計算は、文章として推測せず、必ずコードを実行して正確な値を算出してください。
実行に使ったコードと、実行結果の数値の両方を提示してください。

(ここに計算内容を書く)
```

### 文字・単語の数え上げをさせるとき

「何回出てくるか」を数えさせる場合は、目視の推測ではなく1件ずつ列挙させると精度が上がる。

```
以下の文章中に「◯◯」という語が何回出てくるか数えてください。
出てきた箇所をすべて番号付きで抜き出してから、最後に合計件数を答えてください。
推測でまとめて答えず、必ず1件ずつ数え上げてください。
```

それでも大量のテキスト・完全な正確性が求められる集計(例: 数百件のアンケート自由記述の頻度集計)は、LLMの目視的な数え上げに頼らず、Excelの関数やPythonのコードを実行させる、あるいは検索・集計ツールに任せる方が安全。

### 最新情報を扱うときはWeb検索・情報源の明示を必須にする

ナレッジカットオフより後の情報が必要な場面では、モデルの「記憶」だけに頼らせず、検索機能を使わせるか、社内の最新資料を都度読み込ませる。

```
この質問については、あなたの学習データの記憶だけに頼らず、
Web検索を使って直近の情報を確認したうえで回答してください。
情報の取得日と出典URLを必ず明記してください。
```

検索機能の有効化場所や、検索を使っても幻覚が残るケースへの対処は[ハルシネーションとは何か・対策](../part04-risk-security/hallucination-and-countermeasures.md)にまとめてあるので、そちらを参照。

### 長い会話でキャラクター設定・ルールがぶれてきたら

社内チャットボットやAIエージェントに口調・禁止事項などのルールを与えている場合、会話が長くなるほど当初の設定から外れやすくなる。対策として、

- 一定のやり取り数・トークン数を超えたら新しいチャット(セッション)に切り替える
- 長時間運用するボットには、システムプロンプトに書いたルールを一定間隔で再掲する仕組みを入れる
- 重要なルールほど、システムプロンプトの冒頭と末尾の両方に書く(冒頭・末尾は読み落とされにくいため)

という運用でぶれを抑えられる。

### 苦手な領域を補う3つの工夫(まとめ)

ここまで個別に紹介した対策は、突き詰めると次の3つの型に集約できる。新しい業務でLLMを使う際は、この3つのどれで弱点を補うかをセットで設計しておくと事故が減る。

| 工夫 | 何を補うか | 具体例 |
|---|---|---|
| **ツール連携**(コード実行・専用ソフト) | 計算・数え上げ・正確な集計・画像のOCR | Advanced Data Analysis / コード実行ツール、Excel・BIツール、専用OCRソフト |
| **RAG・検索連携** | ナレッジカットオフ・社内固有の最新情報・因果関係の一次資料 | Web検索機能、社内文書を参照させるRAG・NotebookLM、causal inference専用ツールでの検証 |
| **人間レビュー体制** | ハルシネーション・因果関係の断定・長文/多段階推論での一貫性崩れ | 二段階チェック(作成者確認→別担当レビュー)、確信度が低い分類結果のみ人手で見直す運用 |

## 注意点・よくある誤解

- **「最新の高性能モデルだから計算・数え上げも得意になっているはず」は誤解**: モデルの世代が上がって精度は改善傾向にあるが、テキスト予測という仕組み自体は変わっていないため、桁数の大きい計算やトークンをまたぐ文字数え上げの弱点は原理的に残り続ける。「精度が上がった」と「原理的な弱点が消えた」は別問題。
- **「検索機能をオンにすれば最新情報も完璧」ではない**: 検索結果を参照しても、モデルが検索結果を誤読・誤要約することがある。出典を実際に開いて確認する一手間は省略できない(詳細は[ハルシネーションとは何か・対策](../part04-risk-security/hallucination-and-countermeasures.md))。
- **ナレッジカットオフの日付はモデルごとに異なり、しかも「学習データの範囲」と「内容が充実している範囲」がずれることがある**: 同じモデルでも「知っている」と「正確に・詳しく知っている」は別で、カットオフ直前の情報は断片的にしか反映されていないことがある。重要な意思決定に関わる情報は、カットオフの前後を問わず一次情報を確認する。
- **不得意な作業ほど、出力は一見もっともらしく見える**: 計算ミスも、存在しない最新情報も、崩れたキャラクター設定も、文章としては自然に整っているため、注意して見ないと誤りに気づけない。「読んで違和感がないから正しい」という判断基準は通用しない。
- **「相関が説明できている=因果関係が証明された」ではない**: LLMは「もっともらしい理由付け」を作文するのが得意なため、データの相関を根拠に、いかにもそれらしい因果関係のストーリーを断定的に語ってしまうことがある。重要な意思決定(施策の効果検証、原因分析など)では、LLMの説明を鵜呑みにせず、A/Bテストや統計的な因果推論の手法による裏付けを別途行う。
- **画像・グラフの数値読み取りは「読めているように見えて微妙にズレている」ことがある**: 複雑な図表やスキャン画質の悪い資料になるほど正答率が下がることがベンチマークで報告されている。誤りに気づきにくいのは、間違った数値も表としては整った体裁で出力されるため。金額や法定開示に関わる数値は必ず原本と目視で突き合わせる。
- **不得意分野を回避する一番簡単な方法は「その作業を専用のツールに渡す」こと**: 計算はコード実行・表計算ソフト、最新情報は検索エンジン・一次情報、正確な集計はデータベース・BIツールというように、LLMを「なんでも屋」にせず適材適所で組み合わせるのが実務上もっとも安定する。

## 最初の一歩

普段よく使うプロンプトを1つ選び、その中に計算・集計・日付・固有名詞が含まれていないか確認する。含まれていれば、次に使うときに「コードを実行して正確な値を出してください」「出典URLと取得日を明記してください」の一文を追加して、結果がどう変わるか試してみる。
