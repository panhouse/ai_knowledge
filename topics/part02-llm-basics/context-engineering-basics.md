# コンテキストエンジニアリングとは何か

## これは何か

コンテキストエンジニアリング(context engineering)とは、LLM(大規模言語モデル)が1回の応答を作る際に読み込む「[コンテキストウィンドウ](context-window-basics.md)の中身」を、タスクの各段階で何を・どの順番で・どれだけ入れるかまで含めて設計する実践のこと。Anthropicは公式ドキュメントで「推論の各時点で最適なトークン集合を見極め、維持し続けるための戦略群」と定義している。

「プロンプトをどう書くか(言い回し・指示の出し方)」を扱う[プロンプトエンジニアリング](../part05-prompt-engineering/prompt-basic-structure.md)や、「関連文書を検索してコンテキストに差し込む」という特定の技術である[RAG](../part07-data-analysis/rag-basics.md)とは扱う範囲が異なる。コンテキストエンジニアリングはこの2つを内包する、より上位の設計課題であり、システムプロンプト・過去の会話・検索結果・ツールの実行結果・添付ファイルなど、コンテキストウィンドウに入り得るすべての情報源を「何を残し、何を捨て、いつ読み込むか」という視点で扱う。AIエージェントに複数ステップの業務を任せる機会が増えたことで、「良い指示文を1回書けば終わり」では立ち行かなくなり、この設計が独立した名前を持つ実務スキルとして扱われるようになった。

## 仕組み・背景

### なぜ「プロンプトの書き方」だけでは足りなくなったのか

一問一答のチャットであれば、指示文(プロンプト)の書き方を工夫するプロンプトエンジニアリングだけでも十分に精度を上げられる。しかし、AIエージェントに「資料を調べて」「複数のツールを使って」「何十ターンもかけて」タスクを進めさせる場面では、状況が変わる。エージェントは動くたびに検索結果・ツールの実行結果・過去の作業ログをコンテキストウィンドウに積み増していくため、何もしなければ数ターンでウィンドウが低品質な情報で埋まり、[コンテキスト腐敗(context rot)](context-window-basics.md)によって指示の遵守率も回答精度も落ちていく。課題は「今回、何と書けば伝わるか」ではなく、「このタスクを最後まで完遂させるために、各時点でモデルに何を見せ続けるべきか」という継続的な設計問題に変わる。これがコンテキストエンジニアリングという呼び方が2025年後半以降に定着した背景である。

### コンテキストウィンドウに入るもの(復習)

内訳の詳細は[コンテキストウィンドウの基本](context-window-basics.md)に譲るが、コンテキストエンジニアリングが設計対象とするのは主に次の要素である。

- システムプロンプト(役割・ルールの設定)
- Few-shot例(お手本となる入出力例)
- それまでの会話履歴・過去のやり取りの要約
- RAGで検索してきた文書の断片
- ツール(Function Calling)の定義そのものと、その実行結果
- 添付されたファイル・画像などの入力
- 長期記憶(メモリ機能が過去のセッションから持ち越す情報)

これらはすべて同じ1つの枠を共有してトークン数を消費するため、「何をこの枠に入れる価値があるか」を取捨選択する作業が必要になる。

### 具体的なテクニック

Anthropicのエンジニアリングブログ「Effective context engineering for AI agents」や、後述のRAG実装者・エージェント開発者の知見で共通して挙げられる代表的な手法は次のとおり。

- **トークン予算管理(token budget management)**: コンテキストウィンドウに入れる前の段階で、シグナル(有用な情報)の低いコンテンツを削る。RAGの検索結果を渡す前にリランキング(関連度で並べ替えて上位だけ残す処理)で絞り込むのも一種のトークン予算管理。
- **圧縮・要約(compaction)**: 会話やツール実行ログが長くなってきたら、そのまま蓄積せず要約して置き換える。会話全体を1つの新しい要約に畳み込んで作り直す「フル圧縮」と、新しく増えた分だけを追記していく「差分要約」がある。ただし近年はプロンプトキャッシュ(同じ入力を再利用してコストを抑える仕組み)の普及により、「要約せずそのまま持ち続ける方が、コスト・速度・記憶の正確さのいずれでも有利」なケースがあると報告されており、要約は万能策ではなく状況次第の選択肢として扱う。
- **構造化ノートテイキング(外部メモリへの書き出し)**: エージェント自身に、コンテキストウィンドウの外にある「メモファイル」に進捗・重要事項を書き出させ、必要になった時だけ読み戻す。ウィンドウが上限に達しても、メモを見れば作業を再開できる。
- **Just-in-Time retrieval(必要になった時点での取得)**: 関連しそうな情報を最初から全部コンテキストに積むのではなく、ファイルパスやIDのような軽量な参照だけを持たせておき、実際に必要になった時点で都度取得する設計。RAGの検索タイミングを「事前に全部」から「必要な瞬間だけ」に絞る発想。
- **サブエージェントへの分割**: 調査や実行を、親エージェントとは別のコンテキストウィンドウを持つサブエージェントに任せ、親には結論の要約(数千トークン程度に凝縮したもの)だけを返させる。1つの巨大なコンテキストに情報を溜め込まず、役割ごとに枠を分ける考え方([マルチエージェント運用の基本](../part11-ai-agents/multi-agent-orchestration-basics.md)も参照)。
- **配置の工夫**: [Lost in the Middle](context-window-basics.md)への対策として、絶対に守ってほしい指示や重要な条件は、長いコンテキストの冒頭・末尾に近い位置に置く。

## 使いどころ・使い分け

「プロンプトエンジニアリング」「コンテキストエンジニアリング」「RAG」は対立する選択肢ではなく、扱う階層が異なる。

| 観点 | プロンプトエンジニアリング | コンテキストエンジニアリング | RAG(検索拡張生成) |
|---|---|---|---|
| 扱う範囲 | 1回の指示文の言い回し・構成 | タスク全体を通じて「何をコンテキストに入れ続けるか」の設計 | 関連文書を検索してコンテキストに追加する、具体的な一手法 |
| 位置づけ | コンテキストエンジニアリングの構成要素の1つ | プロンプトエンジニアリングとRAGを内包する上位の設計思想 | コンテキストエンジニアリングが使う手段の1つ |
| 向いている場面 | 単発の質問・生成タスクで出力の質を上げたい | 複数ステップ・長時間動くAIエージェント、大量のツール実行結果を扱うタスク | 大量・頻繁更新の社内文書から根拠付きで回答させたい |
| 効かない場面 | タスクが長時間・多段階になり、蓄積する情報量そのものが問題になっている場合 | 単純な一問一答で、そもそも渡す情報が少ない場合(オーバーエンジニアリングになる) | 「口調を変える」「振る舞いを矯正する」といった知識ではない要件 |

判断の目安はシンプルで、**「言い回しを変えれば直る問題か」「そもそも何を読ませているかを見直すべき問題か」**で切り分ける。指示を書き直しても改善しない、ターンを重ねるごとに精度が落ちる、ツールの実行結果で画面が埋まって肝心の指示を見失う、といった症状が出たらコンテキストエンジニアリングの出番。[ファインチューニング・RAG・プロンプトの使い分け](finetuning-vs-rag-vs-prompting.md)で扱った3手法の選択も、コンテキストエンジニアリングという枠組みの中の一部分(「何を外部知識としてコンテキストに載せるか」)に位置づけられる。

## 実務での使い方

### ツール横断の対応付け

概念としては新しいが、実際にはすでに主要ツールの機能として実装されている。「コンテキストに何を常設し、何を都度渡すか」を設定する画面は以下のように対応する(詳細な手順は各ツールのページを参照)。

| ツール | 「常設のコンテキスト」を設定する機能 | 詳細ページ |
|---|---|---|
| ChatGPT | カスタム指示(Custom Instructions)+メモリ機能(Memory)+プロジェクト機能のファイル添付 | [ChatGPTのカスタム指示](../part03-ai-chat-tools/chatgpt-custom-instructions.md)、[ChatGPTのメモリ機能](../part03-ai-chat-tools/chatgpt-memory-feature.md)、[ChatGPTのプロジェクト機能](../part03-ai-chat-tools/chatgpt-projects-feature.md) |
| Claude | プロジェクトの「カスタム指示」欄+プロジェクトナレッジ(ファイルアップロード) | [Claudeの基本](../part03-ai-chat-tools/claude-basics.md) |
| Gemini | Gemsのカスタム指示+ファイルアップロード | [Google Geminiの基本](../part03-ai-chat-tools/google-gemini-basics.md) |
| Claude Code / Cursor / GitHub Copilot などコーディングエージェント | リポジトリに置く常駐ファイル(`CLAUDE.md` / `.cursorrules` / `AGENTS.md` / `copilot-instructions.md`)をセッション開始時に自動で読み込ませる | [Claude Codeの基本](../part11-ai-agents/claude-code-basics.md) |
| API経由の自作エージェント | システムプロンプト+[MCP](../part09-api-development/mcp-basics.md)などで外部ツール・データソースを接続 | [MCPの基本](../part09-api-development/mcp-basics.md) |

各ツールの「メモリ」「記憶」機能の違いをさらに横断比較したい場合は[AIチャットツールの記憶・コンテキスト管理比較](../part03-ai-chat-tools/ai-chat-tools-memory-and-context-comparison.md)も参照。

### コピペで使える「コンテキスト設計チェックリスト」

長時間タスクをAIエージェントに任せる前に、以下を埋めて設計を確認する。

```
## コンテキスト設計チェックリスト

1. 常時見せておくべき情報(システムプロンプト・ルール)は何か:
2. 都度検索・取得すれば十分な情報(全部を最初から積む必要がない情報)は何か:
3. ツールの実行結果のうち、要約して残せば十分なものはどれか:
4. 会話・作業ログが長くなった場合、どのタイミングで要約(圧縮)するか:
5. 最も守ってほしい指示・条件は、コンテキストの冒頭と末尾のどちらにも置いたか:
6. 古くなった/使われなくなった記憶(メモリ機能の内容)を見直す頻度は:
```

### エージェントに「進捗メモ」を書かせるプロンプト例

構造化ノートテイキングを手動のチャットでも簡易的に再現する例。長い作業を1つのチャットで続けるときに使う。

```
これから複数ステップにわたる作業を行います。
各ステップの終わりに、次の形式で「進捗メモ」を出力してください。
これは後でコンテキストが長くなった際に、要点だけを振り返るためのものです。

## 進捗メモ(ステップ◯まで)
- 完了したこと:
- 決定した方針:
- 次にやること:
- 特に注意すべき制約・条件:
```

## 注意点・よくある誤解

- **「コンテキストウィンドウが大きい=何でも詰め込んでいい」ではない**。[コンテキストウィンドウの基本](context-window-basics.md)で扱った「コンテキスト腐敗」のとおり、詰め込む情報が増えるほど関連性の低いノイズが混ざり、精度が落ちる。コンテキストエンジニアリングの目的は「たくさん入れる」ことではなく「必要なものだけを、必要なタイミングで入れる」こと。
- **検索結果を大量に渡す=精度が上がる、ではない**。RAGの検索でヒット件数を増やしすぎると、関連度の低い文書が紛れ込んでかえって回答が悪化することがある。件数を絞る・リランキングで並べ替えるといった「引き算」の設計もコンテキストエンジニアリングの一部。
- **プロンプトエンジニアリングが不要になったわけではない**。コンテキストエンジニアリングはプロンプトエンジニアリングを置き換えるものではなく、内包する上位概念。指示文の質を上げる工夫(役割設定・Few-shot例など)は引き続き有効で、両方を組み合わせて初めて効果が出る。
- **要約(圧縮)すれば必ず良くなる、とも限らない**。会話やログを都度要約すると情報の欠落が起きることがあり、プロンプトキャッシュを使える環境では「要約せずそのまま持ち続ける方が、コスト・速度・正確さのいずれでも有利」という報告もある。要約するかどうかはコストと精度のトレードオフとして都度判断する。
- **古いメモリがかえって害になることがある**。ChatGPTのメモリ機能のように、過去のセッションの情報を自動で持ち越す仕組みは便利な反面、状況が変わった後も古い前提を引きずって誤った回答をすることがある。定期的にメモリの内容を見直し、不要になったものは削除する。
- **ツールの実行結果をそのまま溜め込むと、あっという間にコンテキストが埋まる**。エージェントに複数のツールを使わせる場合、実行結果は「読んだら要約して圧縮する」「不要なら破棄する」という運用ルールを最初から設計に組み込んでおく。

## 最初の一歩

今使っているAIエージェント、またはよく使うカスタムAI(ChatGPTのカスタム指示・Claudeのプロジェクトなど)の設定内容を1つ開き、「本当に毎回読ませる必要がある情報か」を1項目ずつ見直す。使われていない古い指示や情報があれば、削るところから始める。
