# LLMの仕組み:確率的単語予測と学習プロセス

## これは何か

LLM(大規模言語モデル、Large Language Model)は、それまでの文脈を読んで「次に来る可能性が高い言葉の断片(トークン)」を確率的に予測し、それを1つずつ繋げていくことで文章を生成するプログラムである。これは「知識をデータベースから検索して答えている」のとは根本的に違う仕組みであり、この違いを知らないと、AIが自信満々に間違った情報を言う理由(ハルシネーション)や、同じ質問をしても答えが毎回微妙に変わる理由、長文を読ませると途中から精度が落ちる理由が理解できず、「AIは壊れている」「信用できない」という短絡的な結論に至りやすい。仕組みを知っておくことで、プロンプトの書き方や、どこまでAIの出力を信じてよいかの判断に活かせる。

## 仕組み・背景

**トークンとは何か**
LLMは文章を単語そのものではなく「トークン」という単位に分割して処理する。トークンとは、LLMが文章を扱う際の最小の処理単位(文字や単語の断片)のことで、主要LLMの多くはBPE(Byte Pair Encoding、頻繁に隣り合って出現する文字列を繰り返し1つの単位にまとめていく統計的手法)やその派生アルゴリズムでこの単位を決めている。英語ではほぼ1単語=1トークン程度になることが多いが、日本語は漢字・かなをさらに細かく分割することが多く、1文字が1〜3トークンに分かれる。同じ内容の文章でも、日本語は英語よりトークン数が約2.3倍多くなる一方、文字数は英語の0.6倍程度で済むという報告もある。つまり「文字数は少ないのにトークン消費は多い」のが日本語の特徴であり、料金やコンテキストウィンドウ(後述)の使い方に直結する。

**次トークン予測(確率的生成)**
モデルは「これまでの文脈が与えられたとき、次に来る可能性が高いトークンは何か」を、学習データの統計パターンから算出した確率分布として出力する。実際の生成時には、その確率分布から都度サンプリング(ランダム性を持たせた抽出)で1トークンを選び、文の末尾に追加して、また次のトークンを予測する……という処理をひたすら繰り返して文章を完成させる(この繰り返しの方式は「自己回帰的生成」と呼ばれる)。これが「確率的単語予測」の実態であり、モデルは事実を検証する機構を内部に持たない。統計的に「それっぽい」続きを生成しているだけなので、学習データに少ない情報や、もっともらしい誤りのパターンを、自信満々に事実のように述べてしまうことがある(ハルシネーション)。また生成のたびにランダムなサンプリングが入るため、同じ質問でも毎回言い回しや結論が微妙に変わることがある。なお、2024年後半以降広がった「推論モデル(Reasoning Model、Thinkingモデルとも)」も根本の仕組みは同じで、最終回答を出す前に内部で長い「考える過程」のトークンを自己回帰的に生成してから答えを組み立てているにすぎない。詳細は[推論モデル(Reasoning Model)とは何か](reasoning-model-basics.md)を参照。

**学習プロセスは2段階**

1. **事前学習(pre-training)**: インターネット上の大量のテキストを使い、「次のトークンを当てる」という単純なタスクを何十億回も繰り返させることで、文法・知識・文脈理解といった基礎能力を身につけさせる段階。人間が正解ラベルを付ける必要がない「自己教師学習」という方式のため、Web全体のような巨大データを使える。この段階を終えたモデルは、指示に従う訓練を受けていないため、そのままでは行儀の良い応答をするとは限らない「素材」の状態にある。
2. **アライメント(ファインチューニング/RLHF・DPO・RLAIF)**: 事前学習済みモデルに、「人間の指示に従う」「有用で安全な回答をする」ように追加調整をかける段階。古典的な手法がRLHF(Reinforcement Learning from Human Feedback、人間のフィードバックによる強化学習)で、①人間が複数の回答例を見て指示への従い方を教える、②人間が複数の回答を比較して良い方を選び、その好みのパターンを学習した「報酬モデル」を作る、③報酬モデルからの評価が高くなるように元のモデルを強化学習で調整する、という3ステップで行われる。2026年時点では、報酬モデルを介さず好みのペアデータから直接モデルを調整するDPO(Direct Preference Optimization)や、人間の代わりにAIが回答を評価するRLAIF(Reinforcement Learning from AI Feedback)を組み合わせ、人手による評価作業を減らしながら調整するのが主流になっている(例: DeepSeek-R1は人手による思考過程の教師データをほとんど使わず、正解かどうかのルールベースの採点だけで強化学習するGRPOという手法で推論能力を鍛えている)。手法が変わっても目的は同じで、「指示に忠実で、丁寧で、有害な内容を避ける」という今のチャットAIらしい振る舞いを仕上げる工程であることに変わりはない。

覚え方としては、**事前学習が「知識と地力」を作り、RLHF・DPO・RLAIFなどのアライメントが「振る舞いと従順さ」を仕上げる**、と捉えるとよい。

**巨大化しても速度・コストを抑える設計(MoE)**
2026年時点の主要フロンティアモデルの多くは、Transformer内部の一部を「MoE(Mixture of Experts、専門家混合)」という構造にしている。これは、モデル全体を1つの巨大な回路として毎回フル稼働させるのではなく、多数の「専門家(小さなネットワークの束)」を用意しておき、入力されたトークンごとに一部の専門家だけを選んで計算させる方式である。パラメータ数(モデルの規模を表す数値)の総量は巨大でも、実際に毎回動く計算量はその一部で済むため、巨大なモデルでも応答速度と計算コストを抑えられる。「総パラメータ数◯兆」という発表を見たときは、実際に毎回使われる計算量はそれよりずっと小さいことが多い、と割り引いて読むとよい(アーキテクチャの詳細は[Transformer・Attention機構とスケーリング則の基本](transformer-attention-and-scaling-laws.md)を参照)。

## 使いどころ・使い分け

この仕組みを理解しておくと、業務での判断に直結するポイントが見えてくる。

| 知っておくべきこと | 実務での影響 |
|---|---|
| 確率的生成であり、事実検証機能を持たない | 数値・法令・医療情報など正確性が必須の業務では、AIの回答をそのまま使わない。出典の提示を求めるか、社内文書を参照させる仕組み(RAG=検索拡張生成)と組み合わせる |
| 日本語はトークン消費が多い | 日本語で長文をやり取りする業務(要約・翻訳・議事録作成など)では、想定より早くコンテキスト上限やコスト上限に達する。長文を扱うならコンテキストウィンドウが大きいモデルを選ぶ |
| 長文の中間は読み落としやすい(Lost in the Middle) | 超長文を丸ごと読ませて要約・検索させる用途では、重要な指示や質問は文章の「最初」か「最後」に置く。可能なら章ごとに分割して処理する |
| RLHF・DPO・RLAIFなどのアライメントで「従順」に調整されている | 指示に従おうとする性質が強く、誤った前提の質問にもそのまま同調してしまう(こびへつらい、sycophancy)ことがある。重要な判断は角度を変えて複数回確認する |

判断基準としては、「これは事実の正確性が求められる作業か」「文章量はどれくらいか」の2軸で、①AIの出力をそのまま採用してよいか、②人によるチェックを挟むべきか、③コンテキストウィンドウが大きいモデルに切り替えるべきか、を決めるとよい。

## 実務での使い方

**トークン数の目安を持っておく**
- 英語: おおよそ1トークン=4文字前後が目安。
- 日本語: ひらがな1文字あたり1〜2トークン、漢字1文字あたり1〜3トークン程度。日本語1,000字はおよそ1,000〜3,000トークンになる、と幅を持って見積もっておく。
- 実際のトークン数を確認する: OpenAIの公式Tokenizerツール(platform.openai.com/tokenizer)に自分の原稿を貼ると、トークン数を実際に確認できる。API利用は原則トークン数課金のため、日本語コンテンツは想定より課金額が増えやすい点に注意。

**コンテキストウィンドウ(一度に読める文章量)の目安(2026年7月時点)**
コンテキストウィンドウとは、AIが一度のやり取りで参照できる文章量(入力+出力の合計トークン数)の上限のこと。これを超えた古い発言は、AIの「記憶」から外れていく。

| モデル(2026年7月時点) | コンテキストウィンドウ | 目安 |
|---|---|---|
| Claude Opus 4.8 / Sonnet 5(Anthropic) | 100万トークン | 最大出力12.8万トークン。長文プレミアム(追加料金)なしで100万トークンまで利用可 |
| Claude Haiku 4.5(Anthropic・軽量モデル) | 20万トークン | 最大出力6.4万トークン。軽量・高速・低コストが売り |
| GPT-5.6 Sol/Terra/Luna(OpenAI、2026年7月9日GA) | 約105万トークン | 最大出力12.8万トークン。用途別に3段階の料金帯(Sol=最上位、Terra=標準、Luna=低コスト)に分かれる |
| Gemini 3.1 Pro(Google) | 100万トークン | 標準的な業務用途向け |
| Gemini 3.5 Pro(Google、2026年6月GA) | 200万トークン | 2026年7月時点で量産フロンティアモデルとして最大級のコンテキストウィンドウ |

※コンテキストウィンドウや価格は数か月単位で更新されるため、実際に使う際は各社公式ドキュメント(Anthropic「Models overview」、OpenAIの料金ページ、Google Gemini APIドキュメント)で最新値を確認すること。

**日々の使い方で意識すべきポイント**
- 長い会議の議事録やレポートを要約させるときは、「一番重要な指示(何を出力してほしいか)」を文章の冒頭と末尾の両方に書くと、中間で見落とされにくい。
- 生成AIの回答に数値・法令名・固有名詞が出てきたら、モデルは「それらしい」文字列を生成しているだけの可能性があることを念頭に、必ず出典を確認する。
- 「毎回同じ質問をしても答えが変わる」のは故障ではなく、確率的サンプリングの仕様。再現性を重視する定型文書生成などでは、同じプロンプト・同じ設定を使い、生成結果をテンプレート化して固定するとよい。

## 注意点・よくある誤解

- **「LLMは知識をデータベースのように検索している」は誤解**: 実際は学習データの統計パターンから「次に来そうな言葉」を予測しているだけなので、学習データに少ない情報や統計的にありがちな誤りのパターンを、事実のように生成してしまうことがある(ハルシネーション)。重要な事実は必ず別途確認する。
- **「コンテキストウィンドウが大きい=長文を全部きちんと理解できる」も誤解**: Lost in the Middle(コンテキストの中間部分の情報が軽視されやすい現象)が知られている。「入る」ことと「精度良く使える」ことは別。
- **「日本語だから料金が安くなる」も誤解**: 文字数は少なくても、トークン数は英語より多くなりやすいため、API課金や文字数制限は日本語の方が不利になりやすい。
- **アライメント(RLHF・DPO・RLAIF)は「賢さ」を上げるものではなく「振る舞い」を整えるもの**: これらの手法によって丁寧・従順になった結果、ユーザーの誤った前提にも同調してしまう(こびへつらい)副作用が知られている。AIが「その通りです」と言ったからといって、それが正しさの証明にはならない。
- **「総パラメータ数◯兆」は「常にその全てを使って考えている」ことを意味しない**: MoE(専門家混合)構造を採る現在の主要モデルは、入力ごとに一部の専門家だけを呼び出して計算するため、公表されたパラメータ数と、実際に1回の応答で動く計算量は別物である。パラメータ数の大きさだけでモデルの優劣を判断しない。

## 最初の一歩

自分がよく使うプロンプトや資料の一部をOpenAIの公式Tokenizer(platform.openai.com/tokenizer)に貼り、日本語と英語でトークン数がどれくらい違うかを一度確認してみる。
