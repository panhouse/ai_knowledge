# 情報システム(IT)部門における生成AI活用事例

## これは何か

情報システム(IT)部門、いわゆる「情シス」は、社内からの問い合わせ対応・障害対応・手順書整備・SaaSやライセンスの管理といった、地味だが止められない運用業務を日々抱えている。しかも2026年時点では、全社員が個人の判断でChatGPTやGeminiなどを使い始める「シャドーAI」への対応や、社内向け生成AIツールのアカウント管理・SSO連携といった、これまでになかった新しい仕事まで情シスに降ってきている。本ページは、研究開発部門やエンジニアが「コードを書くために」AIを使う話ではなく、情シスという部門自身が**自分たちの運用業務を回すために**生成AIをどう使うかに絞って、ヘルプデスク・障害対応・ガバナンス・ドキュメント整備・コスト管理の5つの実務シーンごとに、使うツール・コピペで使えるプロンプト・注意点を整理する。

## 仕組み・背景

情シスの業務に生成AIが効きやすい領域には、共通する構造がある。

1. **問い合わせ・アラートの「一次対応」を大量にさばく必要がある**: パスワードリセット、VPN接続不可、経費精算システムの操作方法といった問い合わせは、同じような質問が繰り返し発生する。障害対応も同様に、アラートの一次切り分け(緊急度判定・原因の当たりをつける作業)が大量に発生する。生成AIはこの「型がある一次対応」を高速化するのが得意。
2. **社内マニュアル・過去の障害記録という「参照すべき資料」が既に存在する**: 情シスには手順書・FAQ・過去のインシデント記録が蓄積されており、これをAIに検索させて回答させる仕組み(RAG、AIが回答前に社内文書を検索し、その内容を根拠に答える仕組み。詳細は[RAG(検索拡張生成)の基本](../part07-data-analysis/rag-basics.md))と相性がよい。
3. **情シス自身が「AI利用の主管部署」という立場を新たに担っている**: 生成AIの社内導入が進むほど、「どのAIツールを許可するか」「誰が何をどう使っているか」「使いすぎている部署はどこか」を把握・統制する役割が情シスに集中する。これは技術的な運用業務であると同時に、社内ガバナンスの実務そのものでもある。

社内ヘルプデスクの現場では、生成AIチャットボットの回答精度が運用開始直後の約50%から、FAQの継続的な追加・改善を通じて約80%まで向上した事例が報告されている([RICOH Chatbot Service](https://promo.digital.ricoh.com/chatbot/column/detail238/))。また障害対応の領域では、AIOps(AI for IT Operations、ログ・アラートに機械学習やAIを適用してIT運用を効率化する仕組み)プラットフォームに生成AIが組み込まれ、障害発生時のログから障害報告書(ポストモーテム)のドラフトを自動作成したり、チャット形式で過去の類似インシデントの対処法を提案したりする機能が実用段階に入っている([renue](https://renue.co.jp/posts/aiops-it-operations-automation-predictive-incident-response))。AIOps市場は2026年時点で193.3億ドル規模、年平均成長率21.1%で拡大が続いている([Selector](https://www.selector.ai/ja/learning-center/aiops-4-components-and-4-key-capabilities/))。

一方で、生成AIの社内利用が広がるほど、情報システム部門の許可を得ずに従業員が無断でAIツールを使う「シャドーAI」の問題が大きくなる。この現象自体の実態・ガバナンス設計の考え方は[シャドーAI(無許可利用)対策](../part04-risk-security/shadow-ai-basics.md)に譲り、本ページでは情シスが実際にどのツール・手順で可視化と統制を実行するかという「実装」に絞って扱う。

## 使いどころ・使い分け

### 情シス業務とAI活用の対応マップ

| 業務領域 | 主なタスク | 向くAI活用 | 主なツール系統 |
|---|---|---|---|
| 社内ヘルプデスク | パスワードリセット、VPN・PC設定、各種システムの操作方法問い合わせ | 向く(定型質問の一次自動応答)。個別のアカウント権限変更や機密性の高い判断は人が担当 | RAGベースの社内FAQボット(Dify、NotebookLM、Copilot Studio等) |
| IT運用・障害対応 | アラートの一次切り分け、障害原因の当たりづけ、インシデント要約・ポストモーテム作成 | 向く(大量ログの要約・過去事例の検索)。最終的な原因断定・復旧判断は人が担当 | AIOpsツール(Datadog Bits AI、ServiceNow Now Assist等)、汎用チャットAI |
| シャドーAI・利用状況の可視化 | 無許可AIツールの検知、OAuth連携の棚卸し、利用実態アンケートの設計・集計 | 向く(大量データの集計・分類)。統制方針の最終決定はガバナンス設計側の仕事 | SaaS管理ツール(Admina、Josys等)、CASB/SASE |
| ツール選定・アカウント管理 | 社内向けAIツールの選定比較、SSO連携設定、利用状況モニタリング | 向く(比較表作成、利用ログの要約)。契約可否の最終判断・予算承認は人が担当 | 各AIツールの管理者コンソール(Entra ID連携等) |
| ドキュメント整備 | 手順書・システム仕様書の下書き作成・更新、議事録の要約 | 向く(既存資料の言い換え・構造化)。手順の正確性の最終確認は必須 | 汎用チャットAI、ドキュメント生成AI |
| ライセンス・コスト管理 | 複数AIツールの利用量・料金の可視化、未使用ライセンスの特定 | 向く(データ集計・比較表作成)。解約・契約変更の意思決定は人が担当 | SaaS管理ツール、FinOps系ツール |

判断の軸は他の職種と同様に、「大量の候補・下書き・一次判定を出して人が選ぶ・確認する」仕事はAIに任せやすく、「最終的な原因断定」「契約の解約」「アカウント権限の最終承認」のように後戻りしにくい判断は人が主導する、という切り分けになる。

### 社内ヘルプデスクのボット化: 従来型チャットボットとの違い

| 観点 | シナリオ型チャットボット(従来型) | 生成AI(RAG)型ヘルプデスクボット |
|---|---|---|
| 回答の作り方 | 事前に用意した想定Q&Aから最も近いものを選ぶ | 社内マニュアル・FAQを検索し、その内容をもとに文章を生成して回答 |
| 想定外の質問への対応 | 弱い(「わかりません」で終わりやすい) | 表現の揺れ(言い換え・誤字・口語表現)にも比較的強い |
| 立ち上げの手間 | 想定問答の作り込みに時間がかかる | 既存マニュアルを読み込ませれば始められるが、精度は運用しながら改善が必要 |
| 精度が上がるまでの期間 | 作り込み次第 | 導入直後は回答精度が低め(実例では約50%)で、FAQ追加・改善を重ねて数か月で向上(同実例で約80%) |

## 実務での使い方

### シーン1: 社内ヘルプデスクFAQボットの立ち上げ(RAG活用)

社内マニュアル・過去の問い合わせ履歴をAIに読み込ませ、一次回答を自動化する。構築手順そのものは[RAG(検索拡張生成)の基本](../part07-data-analysis/rag-basics.md)を参照し、ここでは情シス特有の「投入する一次データの作り方」を扱う。過去の問い合わせ履歴をそのままAIに渡すのではなく、次のようにQ&A形式に整形してから投入すると検索精度が上がりやすい。

```
以下は過去1年分の情シスへの問い合わせ履歴(自由記述のメモ)です。
これをFAQボットに登録するためのQ&A形式に整形してください。

【問い合わせ履歴】
(問い合わせ内容と対応内容のメモを貼り付け)

【出力条件】
- 「質問(利用者が実際に使いそうな言葉遣いで)」「回答」の1問1答形式にする
- 同じ内容の問い合わせは1つのQ&Aにまとめ、言い換えのバリエーションを
  「別の聞き方」として3つ程度添える
- 回答には社内システム名・申請フォームのリンク先(仮のプレースホルダーでよい)を含める
- パスワードや個人情報など、回答に含めてはいけない情報が元メモにあれば
  マスキングした上で「要確認」の注記を付ける
```

### シーン2: 障害対応時のログ解析・インシデント要約

障害発生時、汎用チャットAIやAIOpsツールにログを読み込ませ、一次切り分けと報告書ドラフト作成を高速化する。ログに含まれる個人情報・顧客情報の有無は事前に確認し、社外の汎用AIに投入する場合は法人契約プラン(学習利用なし)を使う。

```
以下は直近30分のエラーログです。この障害の一次切り分けを手伝ってください。

【エラーログ】
(ログを貼り付け)

【出力条件】
1. ログから読み取れる「発生していそうな事象」を3つ以内の仮説として挙げる
   (断定はせず、それぞれの根拠となったログの行を示す)
2. 各仮説について、切り分けのために次に確認すべきコマンド・画面を提案する
3. 過去に似た障害が起きていそうか(ログのパターンから推測できる範囲で)コメントする
4. 最後に、障害報告書のたたき台として「発生日時」「影響範囲」「暫定対応」
   「原因(調査中/確定次第追記)」の見出しだけ用意する
```

AIOpsツール(Datadog Bits AI、ServiceNow Now Assistなど)を導入済みの場合は、アラート発生時に自動でポストモーテムのドラフトを生成し、過去の類似インシデントをチャット形式で提示する機能を使うと、上記のようなプロンプトを都度書かなくても同様の一次対応が得られる。ただしAIが示す原因の仮説は必ず一次情報(実際のログ・メトリクス)で裏取りしてから復旧作業・報告に反映する。

### シーン3: シャドーAIの可視化・棚卸し(情シス主導の実務)

シャドーAI対策の全体設計(禁止一辺倒にしない分業モデルなど)は[シャドーAI(無許可利用)対策](../part04-risk-security/shadow-ai-basics.md)に譲り、ここでは情シスが最初に着手する「棚卸し」の具体的な進め方を扱う。まず着手すべきは、既存のSaaS管理台帳やIDプロバイダー(Entra ID、Google Workspace等)のログから、従業員がどのAIサービスにOAuth連携・ソーシャルログインしているかを洗い出す「OAuth連携の棚卸し」である。SaaS管理ツール(Admina、Josys等)を使うと、契約中のSaaSだけでなく個人がソーシャルログインで使い始めたサービスの検知まで対応できるものがある。

```
以下は自社のIDプロバイダー(Entra ID)から出力した、
過去90日間の外部サービスへのログイン連携ログです。

【ログイン連携ログ】
(サービス名・連携ユーザー数・最終ログイン日のリストを貼り付け)

【出力条件】
1. AI関連サービスと思われるものを一覧化する(ChatGPT、Gemini、Claude、
   Perplexity、Notion AI等の名称パターンをもとに判定)
2. 会社として法人契約している既知のツール一覧(下記【契約済みツール】)と
   突き合わせ、契約外で使われている疑いのあるサービスを抽出する
3. 利用ユーザー数が多い順に並べ、次にヒアリングすべき部署の優先順位を提案する

【契約済みツール】
(例: ChatGPT Business、Microsoft Copilot)
```

### シーン4: 手順書・システム仕様書の下書き作成

既存の設定情報・運用メモをAIに渡し、社内向け手順書の体裁に整形させる。ゼロから作らせるのではなく、実際の設定画面のスクリーンショットや操作メモを土台にする方が誤りが少ない。

```
以下は新入社員向けPCキッティング作業の担当者メモ(箇条書き)です。
これを手順書の体裁に整形してください。

【担当者メモ】
(作業メモを貼り付け)

【出力条件】
- 「事前準備」「手順(番号付き)」「完了確認チェックリスト」「トラブル時の連絡先」の構成
- メモにない手順を推測で補わない(不明な箇所は「要確認」と明記する)
- 手順ごとに、想定される所要時間の目安があれば併記する
```

生成した手順書は、必ず実際にその手順を再現できるか(記載漏れがないか)を担当者が一度なぞって確認してから正式版として公開する。AIは「文章の型に整える」ことは得意だが、実際の設定画面の仕様変更までは把握していないため、最新の画面と食い違っていないかの確認は人の仕事になる。

### シーン5: ライセンス・コスト管理(複数AIツールの利用量可視化)

社内で複数のAIツール(ChatGPT、Gemini、Copilot、Claude等)を並行契約している場合、部署ごとの利用量・アクティブ率を集計し、契約プランの見直し材料にする。

```
以下は各AIツールの管理者コンソールから出力した、
部署別の月間アクティブユーザー数とライセンス数の一覧です。

【データ】
(ツール名・部署名・契約ライセンス数・月間アクティブユーザー数を貼り付け)

【出力条件】
1. ツールごとに「稼働率(アクティブユーザー数/契約ライセンス数)」を計算する
2. 稼働率が50%を下回るツール・部署の組み合わせを一覧化する
3. 複数ツールを併用している部署がないか確認し、あれば統合の余地を指摘する
4. 上記を踏まえた次回契約更新時の削減・見直し候補を3つ提案する
   (最終判断はしないこと。あくまで「検討候補」として提示する)
```

### ツール横断の対応付け(管理者向け機能の比較、2026年7月時点)

| 観点 | ChatGPT(Business/Enterprise) | Gemini(Google Workspace) | Microsoft Copilot | Claude(Team/Enterprise) |
|---|---|---|---|---|
| SSO/ID連携 | SAML SSO・SCIM対応 | Google Workspace管理コンソールで一元管理 | Entra ID(旧Azure AD)連携・条件付きアクセス | Team/Enterpriseはワークスペース単位で管理 |
| 利用状況モニタリング | 管理コンソールでDAU/WAU/MAU等をリアルタイム分析 | Workspace管理コンソールの利用状況レポート | Microsoft 365管理センターの利用状況ダッシュボード | 管理者ダッシュボードでの利用状況確認 |
| 料金の目安(2026年7月時点) | Business: 年払い1ユーザー月20ドル(月払い25ドル)。Enterpriseは個別見積り(年額1ユーザー10〜15万円程度が目安) | Google Workspaceのプランに含まれる形態が中心 | Microsoft 365 Copilotは既存M365ライセンスに追加課金 | Team/Enterpriseは個別見積りが中心 |

社内向けAIツール全体のSSO統一・アカウントライフサイクル管理の考え方は[生成AI利用における情報漏洩対策](../part04-risk-security/information-leakage-prevention.md)、社内ガイドラインという文書側の整備は[社内AI利用ガイドラインの作り方](../part04-risk-security/ai-internal-guideline-basics.md)を参照。

## 注意点・よくある誤解

- **ヘルプデスクボットは「作ったら即・高精度」にはならない**: 実際の導入事例では、運用開始直後の回答精度が約50%からスタートし、FAQの追加・改善を継続することで約80%まで向上している。立ち上げ直後の精度の低さで「使えない」と判断せず、数か月単位で改善を続ける運用体制(誰がFAQを更新するか)を最初から決めておく
- **AIの障害原因の仮説は「当たりをつける」ためのものであり、確定診断ではない**: AIOpsツール・チャットAIが示す原因候補は、ログのパターンマッチングに基づく推測であり、実際の原因と異なることがある。復旧作業や障害報告書の最終版には、必ず実機・実データでの裏取りを経てから反映する
- **シャドーAI対策ツールを導入しただけでは終わらない**: SaaS管理ツールやCASBは「何が使われているか」を可視化するところまでで、そのあとの利用申請フロー整備・現場への周知・分業体制の構築が伴わなければ効果が薄い(全体設計は[シャドーAI(無許可利用)対策](../part04-risk-security/shadow-ai-basics.md)を参照)
- **手順書・仕様書のAI生成は「最新の画面・仕様」を保証しない**: AIは投入したメモをもとに文章を整形するのは得意だが、実際のシステムの最新仕様までは把握していない。生成した手順書は必ず実際に手を動かして再現確認してから公開する
- **障害ログや社内システムの機密情報を汎用AIに入力する際は契約形態に注意する**: 無料版・個人アカウントの生成AIに障害ログや顧客影響のある情報を入力すると、意図せず外部に情報が渡るリスクがある。法人契約プラン(学習利用がデフォルトで無効になっているもの)を使う([生成AI利用における情報漏洩対策](../part04-risk-security/information-leakage-prevention.md)を参照)
- **ライセンスの稼働率が低い=即解約、ではない**: 稼働率の低さは「使われていない」以外に「試験導入中」「特定の繁忙期だけ使う」といった事情もあり得る。AIが出す削減候補はあくまで検討材料であり、契約更新の最終判断は利用部署へのヒアリングを経て行う

## 最初の一歩

自部門(情シス)が今抱えている「同じ質問が繰り返し来る」問い合わせを1つ選び、過去の対応メモをシーン1のプロンプトでQ&A形式に整形してみる。それだけでもFAQボット化・マニュアル整備の最初の材料になる。
