# 情報セキュリティ担当者(SOC/CISO)における生成AI活用事例

## これは何か

SOC(Security Operation Center、セキュリティ監視・分析を専門に行う組織)のアナリストやCISO(最高情報セキュリティ責任者)は、日々大量に発生するアラートの一次切り分け、フィッシングメールの真偽判定、インシデント発生時の報告書作成、山積みの脆弱性(CVE)の対応優先順位付けといった、時間との勝負になる作業に追われている。1人のアナリストが1シフトで500件以上のアラートを見ており、その約半分は誤検知(false positive)だとも言われる状況では、人手だけで全件を丁寧に見るのは現実的に不可能になっている。本ページは、[情報システム(IT)部門における生成AI活用事例](information-systems-ai-use-cases.md)がヘルプデスクや障害対応など**情シス全般**の運用業務を扱うのに対し、**セキュリティ専門チーム(SOC/CISO)自身**が自分の業務(アラート対応・脅威分析・報告書作成・研修コンテンツ作成)に生成AIをどう使うかに絞って整理する。なお、生成AIを使う側が晒される「攻撃・防御」の一般的なリスク(プロンプトインジェクション、ジェイルブレイク、シャドーAIなど)は[Part 4 リスク管理・セキュリティ](../part04-risk-security/_index.md)の各ページが本流であり、本ページでは深掘りしない。

## 仕組み・背景

セキュリティ運用に生成AIが効きやすいのは、次の3つの構造による。

1. **「大量のログ・アラートを読み、要約し、当たりをつける」作業が定型化しやすい**: アラートの内容、関連するログ、過去の類似インシデントを突き合わせて「これは緊急か、様子見か」を判定する一次トリアージは、大量のテキストを読んで要点を抜き出すというLLM(大規模言語モデル)が得意な作業そのものである。Gartnerは2026年末までに75%のSOCがAIアナリスト(AIエージェントによる自動トリアージ・調査の仕組み)を導入すると予測している([UnderDefense](https://underdefense.com/blog/ai-soc-analyst/))。
2. **攻撃側も生成AIを使うため、防御側も同じ土俵で戦う必要が生まれている**: 生成AIで作成したフィッシングメールは自然な文章になり、人手を加えたものはクリック率が56%に達したという報告もある([日経クロステック](https://xtech.nikkei.com/atcl/nxt/column/18/00676/100700207/)、[rocket-boys](https://rocket-boys.co.jp/security-measures-lab/11818/))。もはや「日本語の不自然さ」で見破れる時代ではなく、防御側もLLMを使ったフィッシング判定(例: NTTセキュリティの「ChatSpamDetector」はLLMにメール本文を解析させ、判定理由まで提示する)で対抗する構図になっている([NTTセキュリティ・ジャパン](https://jp.security.ntt/insights_resources/tech_blog/chatspamdetector-ai/))。
3. **脆弱性(CVE)の発見・報告ペースが人力の処理能力を超えている**: 2026年のCVE(共通脆弱性識別子)公開件数は年間6万6千件規模に達する見通しで、脆弱性の公開から悪用コードが出回るまでの期間は2020年の745日から2026年には12時間未満まで短縮したとの分析もある([Bitsight](https://www.bitsight.com/blog/end-of-the-exploit-window-frontier-ai-cve-prioritization))。全件を人手で精査して優先順位を付けるのはもはや不可能で、生成AIによる自動タグ付け・優先順位付けの支援が実務レベルで使われ始めている(TenableはCVEが「ランサムウェアに悪用されている」「実際に悪用が確認されている」などをAIで自動タグ付けする機能を提供)。

このような背景から、SIEM(Security Information and Event Management、ログを集約・相関分析するセキュリティ監視基盤)やEDR(Endpoint Detection and Response、端末上の不審な挙動を検知・対応する仕組み)にAIコパイロット(操作を助言・代行するAIアシスタント機能)を組み込む「AI SOC」「エージェント型SOC」が主要ベンダーの共通戦略になっている。Microsoft Security Copilot、Google SecOps(旧Chronicle)のGemini、CrowdStrike Charlotte AIが代表例で、国内でもNTTドコモビジネスが2026年5月に「AI SOC」サービスの提供を開始し、アラート対処の約95%を自動化できるとしている([NTTドコモビジネス](https://www.ntt.com/about-us/press-releases/news/article/2026/0520.html))。ただし、いずれのベンダーも「封じ込め(端末隔離・アカウントロックなど)の実行は人間の最終承認を前提とする」という設計を崩していない点は共通しており、完全無人運用は2026年時点でもまだ推奨されていない。

## 使いどころ・使い分け

### セキュリティ業務とAI活用の対応マップ

| 業務領域 | 主なタスク | 向くAI活用 | 最終判断は誰が担うか |
|---|---|---|---|
| アラート一次トリアージ | 大量アラートの要約・重複排除・緊急度の当たりづけ | 向く(パターンマッチ・要約が中心) | 封じ込め・エスカレーション可否はアナリストが判断 |
| フィッシング・不審メール解析 | メール本文・ヘッダーの分析、悪意の有無の一次判定 | 向く(文面パターンの判定・利用者向け注意文の作成) | 最終的な「隔離/削除/警告メール送付」の実行判断は人が担当 |
| インシデントレポート作成 | 発生事象・影響範囲・時系列のドラフト作成 | 向く(構造化・言語化)。事実関係の正確性は必須確認 | 経営報告・対外説明の内容は責任者が最終承認 |
| 脆弱性管理の優先順位付け | CVEの悪用状況・自社資産への影響度のタグ付け・要約 | 向く(大量CVE情報の集約・要約)。実際のパッチ適用計画は人が決定 | パッチ適用の順序・停止判断は人が最終決定 |
| セキュリティ意識向上研修 | 標的型メール訓練文面、eラーニング教材のドラフト作成 | 向く(文面のバリエーション生成) | 実際に配信する訓練メールの内容は最終レビューが必須 |
| ポリシー・規程のドラフト作成 | 社内セキュリティポリシーの下書き、既存規程の見直し | 向く(既存文書の言い換え・構造化) | 法務・経営層の承認を経てから正式版とする |

判断の軸は他の職種と同様で、「大量の候補・下書き・一次判定を出して人が選ぶ・確認する」仕事はAIに任せやすく、「封じ込めの実行」「対外的な最終報告」「パッチ適用の停止判断」のような後戻りしにくい意思決定は人が主導する。

### 汎用チャットAI vs 専用AIセキュリティコパイロットの使い分け

| 観点 | 汎用チャットAI(ChatGPT/Gemini/Claude等) | 専用AIセキュリティコパイロット(Security Copilot/Charlotte AI/Gemini in SecOps) |
|---|---|---|
| 導入のハードル | 低い(既存の法人契約があればすぐ使える) | 高い(SIEM/EDR等の既存環境との連携設定が必要) |
| 得意なこと | ログ・メール文面の要約、レポートの文章化、研修教材の下書き | 自社のテレメトリ(ログ・アラート・資産情報)に直結した調査・自動トリアージ・過去事例の突き合わせ |
| ログ・アラートとの連携 | コピー&ペーストで都度渡す必要がある | SIEM/EDR上のデータに直接アクセスして自動分析 |
| コスト構造 | 既存のチャットAI契約に含まれることが多い | 追加のライセンス・従量課金(後述)が発生することが多い |
| 向く組織 | セキュリティ専任者が少なく、まず文章作成・要約から始めたい組織 | SOCを24時間体制で運用し、アラート件数が人力の限界を超えている組織 |

小規模組織や専任のSOCを持たない企業は、まず汎用チャットAIでの「フィッシングメール解析」「インシデントレポート下書き」から始め、アラート件数がボトルネックになってきた段階で専用コパイロットの導入を検討する、という段階的な使い分けが現実的である。

## 実務での使い方

### シーン1: アラートの一次トリアージ・ログ要約

汎用チャットAIにログとアラート内容を貼り付け、緊急度の当たりをつける。個人情報・顧客情報を含むログを社外の汎用AIに投入する場合は、必ず法人契約プラン(学習利用なし)を使う([生成AI利用における情報漏洩対策](../part04-risk-security/information-leakage-prevention.md)を参照)。

```
以下はEDRが検知したアラートと関連ログです。SOCアナリストとして
一次トリアージを手伝ってください。

【アラート内容】
(アラート種別・発生時刻・対象端末・検知ルール名を貼り付け)

【関連ログ】
(プロセス起動履歴、通信先IP、ファイル操作履歴などを貼り付け)

【出力条件】
1. このアラートが「誤検知(業務上正当な動作)」である可能性と、
   「実際の脅威」である可能性を、それぞれログのどの部分を根拠にしたか示しながら評価する
2. 緊急度を「即時対応/当日中に確認/様子見」の3段階で提案する(断定はしない)
3. 過去に似たパターンの攻撃手口があれば、名称(例: 特定のMITRE ATT&CK手法名)を挙げる
4. 次に人間が確認すべきコマンド・ログの種類を3つ以内で提案する
```

専用のAIセキュリティコパイロット(後述)を導入済みの場合は、このプロンプトを都度書かなくても、アラート発生時に自動で同様の一次判定と根拠が提示される。ただし提示された緊急度・脅威判定は「当たりをつける」ためのものであり、封じ込め(端末隔離・アカウントロックなど)の実行判断は必ずアナリストが行う。

### シーン2: フィッシング・不審メールの解析と利用者向け注意喚起文の作成

従業員から転送された不審メールを解析し、危険性の一次判定と、他の従業員への注意喚起文を同時に作らせる。

```
以下は従業員から「不審なメールかもしれない」と転送されてきたメールです。
セキュリティ担当者として一次解析を手伝ってください。

【メール本文・送信元アドレス・件名】
(貼り付け)

【出力条件】
1. フィッシング・詐欺メールの可能性を「高い/中程度/低い」の3段階で判定し、
   判断の根拠(送信元ドメインの不自然さ、緊急性を煽る文言、
   リンク先URLの怪しさなど)を具体的に示す
2. 社内の全従業員向けに送る注意喚起メールの文面を、
   「今回確認された手口の特徴」「取ってはいけない行動」
   「不審に思ったときの連絡先」の3段落で作成する(専門用語は避け、平易に)
3. このメールに実際にURLリンクや添付ファイルが含まれる場合、
   絶対にクリック・開封せず、判定のみに留めるよう注意喚起を添える
```

生成AIによるフィッシングメール自体も年々巧妙化しており、「日本語の不自然さ」だけを根拠に安全と判断しないよう、送信元ドメインの実在性やリンク先URLなど機械的に確認できる項目と組み合わせて判定することが重要である。

### シーン3: インシデントレポート・ポストモーテムのドラフト作成

障害対応・インシデント対応後、時系列の生ログ・対応メモを正式な報告書の体裁に整形する。

```
以下は今回のセキュリティインシデント対応中に記録した、
時系列のメモ(社内チャットのログ)です。
これをインシデント報告書のドラフトにしてください。

【時系列メモ】
(対応中のチャットログ・メモを貼り付け)

【出力条件】
- 「概要」「発生日時と検知経緯」「影響範囲(判明している範囲のみ、推測は書かない)」
  「実施した暫定対応」「根本原因(調査中の場合はその旨明記)」「再発防止策(案)」の構成
- メモに書かれていない事実を補って書かない。不明な点は「要確認」と明記する
- 経営層向けの要約(3行程度)を冒頭に追加する
```

生成した報告書は、事実関係(発生時刻・影響範囲・原因)を必ず一次情報(実際のログ・関係者へのヒアリング)で裏取りしてから正式版として提出する。AIは「文章の構成を整える」ことは得意だが、事実の正確性を保証しない。

### シーン4: 脆弱性(CVE)対応の優先順位付け支援

大量に公開されるCVE情報を、自社の資産状況と突き合わせて優先順位の当たりをつける。

```
以下は今週新たに公開されたCVEのリストと、自社で使用している
主要ソフトウェア・バージョンの一覧です。

【CVEリスト】
(CVE番号、CVSSスコア、対象製品名を貼り付け)

【自社の主要ソフトウェア一覧】
(製品名・バージョン・重要度を貼り付け)

【出力条件】
1. 自社の利用製品に該当するCVEを抽出する
2. 各CVEについて、CVSSスコアに加えて「実際の悪用が報告されているか」
   「ランサムウェアに使われた実績があるか」がリストの情報からわかる範囲で分かれば付記する
3. パッチ適用の優先順位を「即時/1週間以内/次回定期メンテナンス」の3段階で提案する
   (最終決定はしないこと。あくまで検討材料として提示する)
4. 判断材料が不足しているCVEは「情報不足のため個別に脅威インテリジェンスを確認」と明記する
```

CVEの実際の悪用状況(Exploited in the Wild、KEV: Known Exploited Vulnerabilities、実際に悪用が確認された脆弱性の一覧)は、AIの一般知識だけでは最新性が保証できない。CISAのKEVカタログなど一次情報源と併用し、AIの提案はあくまで「大量のリストを整理する下準備」として使う。

### シーン5: セキュリティ意識向上研修・標的型メール訓練コンテンツの作成

標的型攻撃メール訓練の文面バリエーションや、社内向けeラーニング教材のドラフトを作成する。

```
標的型攻撃メール訓練用の訓練メール文面を3パターン作成してください。

【条件】
- 業種: (自社の業種)
- 想定シナリオ: (例: 「取引先を装った請求書送付」「社内システムのパスワード
  期限切れ通知」など)
- 訓練対象: (例: 全社員/経理部門のみ)
- 難易度: (例: 「不自然な日本語を含む初級」「自然な文面の中級」)

【出力条件】
- 件名・本文・差出人名(実在の組織名は使わない)をセットで3パターン提示する
- 各パターンについて、開封・クリックしてしまった従業員に気づいてほしい
  「不審に思うべきポイント」を解説として添える
- 実際の攻撃に悪用されないよう、本文中に実在のURLやドメインは含めない
```

作成した訓練メールは、配信前に必ず内容を最終レビューする(実在の取引先名を誤って使っていないか、あまりに巧妙すぎて訓練の意図を超えて実害が出ないかなど)。

## 注意点・よくある誤解

- **AIの判定は「当たりをつける」ものであり、確定診断ではない**: アラートの緊急度判定・フィッシングの真偽判定・脆弱性の悪用有無は、いずれもAIによる推測であり、実際と異なることがある。封じ込め・隔離・パッチ適用停止といった後戻りしにくいアクションの実行は、必ず人間の最終承認を経る(主要ベンダーのAI SOC製品も、この「Human in the Loop」設計を前提にしている)
- **攻撃側も同じ生成AIを使っている**: フィッシングメールの自然さ・巧妙さは生成AIの進化とともに年々向上しており、「日本語が不自然だから安全」という従来の見分け方は通用しなくなっている。防御側の生成AI活用は、攻撃側の生成AI活用に対抗する「同じ土俵での戦い」だという前提を持つ
- **機密性の高いログ・インシデント情報を汎用AIに入力する際は契約形態に注意する**: 攻撃の痕跡ログや顧客影響のある情報を無料版・個人アカウントの生成AIに入力すると、意図せず外部に情報が渡るリスクがある。法人契約プラン(学習利用がデフォルトで無効になっているもの)を使う([生成AI利用における情報漏洩対策](../part04-risk-security/information-leakage-prevention.md)を参照)
- **専用AIセキュリティコパイロットは「導入したら終わり」ではない**: SIEM/EDRとの連携設定、社内データでのチューニング、誤検知率のモニタリングといった運用が伴わなければ効果が薄い。またSCU方式の従量課金は使い方次第でコストが跳ね上がるため、まず自社の想定アラート量で試算してから本格導入を判断する
- **標的型メール訓練の文面生成は「実害」に注意する**: AIが作った訓練メールが巧妙すぎたり、実在の取引先名・ドメインを誤って使ってしまったりすると、訓練の域を超えて実害や不要な混乱を招く。配信前の内容レビューは省略しない
- **AIエージェントによる自動対応の権限設計は、他の業務エージェント以上に慎重に**: セキュリティ業務のAIエージェントは、誤作動時の被害(誤って正当な業務端末を隔離してしまう等)が大きい。権限範囲の設計は[プロンプトインジェクションとは何か](../part04-risk-security/prompt-injection-basics.md)で扱う「エージェント型AIの権限設計」の考え方と合わせて検討する

## 最初の一歩

直近で従業員から転送された不審メール(または過去のフィッシングメールのサンプル)を1件選び、シーン2のプロンプトで一次解析と注意喚起文の作成を試してみる。法人契約の汎用チャットAIがあれば、専用のセキュリティコパイロットを導入していなくても今日から始められる。
