# Function Calling(Tool Calling)の基本

## これは何か

ChatGPTや業務用チャットボットに「今日の東京の天気は?」「A社の在庫は残り何個?」と聞いても、AIモデル自身は天気予報サービスにも社内システムにもアクセスできないため、本来は答えられない(学習データにない情報や、リアルタイムで変わる情報だから)。Function Calling(ファンクションコーリング。Tool Callingとも呼ばれる)は、この「AIが知らないこと・できないこと」を、外部の関数・API・社内システムを呼び出すことで解決させる仕組みである。AIモデルが直接システムを操作するのではなく、「この関数をこの引数で呼んでほしい」という指示を構造化データ(JSON)で返し、それを実際に実行するのは開発者側のプログラムだ、という役割分担がポイントになる。

## 仕組み・背景

Function Callingの処理は、次の4ステップで進む。

1. **関数の定義を渡す**: 開発者が「こういう名前・説明・引数を持つ関数が使える」というリスト(スキーマ)をAPIリクエストに含める。例:「`get_weather`という関数があり、`location`(地名)という引数を取る」
2. **モデルが呼び出しを判断**: ユーザーの質問を見て、モデルが「この関数を、この引数の値で呼ぶべきだ」と判断し、通常の文章ではなく構造化データ(関数名+引数のJSON)を返す。この時点ではモデルは実際に関数を実行していない
3. **開発者側が関数を実行**: アプリケーション側のプログラムがそのJSONを受け取り、実際に天気APIや社内DBを呼び出して結果を取得する
4. **結果をモデルに戻す**: 実行結果を再度モデルに渡すと、モデルがそれを踏まえて自然な文章で最終回答を生成する

つまりAI自身がインターネットや社内ネットワークに直接アクセスするわけではなく、「何を呼ぶべきか」を判断する頭脳の役割に徹し、実行(実際にAPIを叩く・DBを検索する)は必ず開発者が用意したプログラムが担う。この分離があるからこそ、「勝手に注文を確定させる」「勝手に社外に情報を送信する」といった暴走を防ぎつつ、AIに実務システムとの連携をさせられる。

**JSON Schema(JSONスキーマ)**という、引数の型や必須項目を定義する共通フォーマットで関数の仕様を書くのが業界標準になっており、OpenAI・Claude・Geminiのいずれも基本的にこの考え方を採用している(細部のフィールド名は異なる)。

なお「Function Calling」という呼び方はOpenAIが最初に広めた名称で、Anthropic(Claude)は「Tool use(ツールユース)」、Googleは「Function calling」という名称を使っており、業界全体では「Tool Calling」という総称も定着している。**RAG(検索拡張生成。社内文書を検索してから回答させる仕組み)との違い**にも注意したい。RAGは「文書を検索して参照させる」ことに特化した仕組みで、Function Callingは「検索に限らず、天気取得・在庫確認・予約作成・メール送信など任意の処理を呼び出せる」より汎用的な仕組みという関係になる(RAGの検索機能自体をFunction Callingの1つのツールとして実装することも多い)。

## 使いどころ・使い分け

| やりたいこと | 向いている仕組み |
|---|---|
| 社内文書やマニュアルの内容を検索して答えさせたい | RAG(検索拡張生成) |
| 今日の天気・為替レートなどリアルタイム情報を答えさせたい | Function Calling(外部APIを呼ぶ) |
| 「在庫は何個?」「注文番号◯◯の配送状況は?」など社内システムに問い合わせたい | Function Calling(社内APIやDBクエリを呼ぶ) |
| チャットから「会議室を予約して」「見積書を作成して」など実際の処理を実行させたい | Function Calling(書き込み系のAPIを呼ぶ) |
| 決まった形式(JSONなど)で出力させたいだけで、外部システム連携は不要 | Structured Outputs / JSON モード(出力形式の指定だけで完結する、より軽量な機能) |
| 複数のツールを状況に応じて自律的に使い分けながら複数ステップの作業をこなさせたい | Function Callingを土台にした「AIエージェント」構成 |

判断の目安はシンプルで、**「AIの外にある最新情報・社内データ・実際の処理」が必要になった時点でFunction Callingの出番**になる。逆に、モデルが元々知っている知識の範囲で答えられる質問や、出力の体裁を整えたいだけの場合はFunction Callingを使う必要はない。

## 実務での使い方

### 最小構成のイメージ(在庫確認ボットの例)

ノーコードツールを使う場合でも裏側の考え方は共通なので、まず開発者向けAPIでの最小例を示す。ここでは「商品名を渡すと在庫数を返す社内APIがある」という想定で、OpenAIのAPI形式(2026年7月時点、Chat Completions APIの`tools`パラメータ)を例にする。

**1. 関数の定義(開発者がAIに渡す「道具のカタログ」)**

```json
{
  "type": "function",
  "name": "get_stock",
  "description": "商品名を指定して、社内在庫システムから現在の在庫数を取得する",
  "parameters": {
    "type": "object",
    "properties": {
      "product_name": {
        "type": "string",
        "description": "在庫を確認したい商品名(例: ノートPC A型)"
      }
    },
    "required": ["product_name"]
  }
}
```

**2. ユーザーの質問**: 「ノートPC A型の在庫ある?」

**3. モデルからの応答(実行はまだしない、呼び出したい内容の提案)**

```json
{
  "type": "function_call",
  "name": "get_stock",
  "arguments": "{\"product_name\": \"ノートPC A型\"}"
}
```

**4. 開発者側のプログラムが実際に社内在庫APIを呼び出し、結果を取得**: 例)「在庫数: 3」

**5. その結果をモデルに送り返すと、モデルが最終回答を生成**: 「ノートPC A型の在庫は現在3台です。」

この一連の流れ(質問 → 関数呼び出しの提案 → 実行 → 結果を戻す → 最終回答)がFunction Callingの基本サイクルであり、天気予報・為替レート・CRMの顧客情報照会・スプレッドシートの検索など、外部に問い合わせが必要な場面はすべて同じパターンで実装できる。

### 主要API・ツールでの名称と設定場所の対応

| ツール | 呼び方 | 設定・実装の場所 |
|---|---|---|
| OpenAI API | Function Calling(関数はAPIリクエストの`tools`パラメータに`{"type": "function", "name": ..., "parameters": ...}`の形で渡す) | 開発者がコードでリクエストに`tools`配列を含める。`tool_choice`パラメータで「自動判断(auto)」「必ず1つ呼ぶ(required)」「特定の関数を強制」を指定可能 |
| Anthropic Claude API | Tool use(ツールユース。引数のスキーマは`input_schema`というフィールド名で定義) | `messages.create`リクエストの`tools`配列で定義。モデルの応答は`tool_use`という種類のブロックで返り、開発者は結果を`tool_result`ブロックとして送り返す |
| Google Gemini API | Function calling(関数は`function_declarations`というリストにまとめる) | `generateContent`呼び出しの`tools`パラメータに渡す。モデルの応答は`functionCall`、実行結果は`functionResponse`として送り返す |
| Dify | 「エージェント」ノードに組み込みツール(50種類以上)を追加、またはOpenAPI/Swagger仕様で自作APIを「カスタムツール」として登録 | ワークフロー画面の「エージェント」ノード内でツールを選択・追加(画面操作のみ。JSONスキーマは意識しなくてよい) |
| n8n | 「AIエージェント」ノードに「Tool」系サブノード(HTTP Request Tool、Code Toolなど)を接続 | AIエージェントノードの下に、呼び出したい処理ごとにToolサブノードを追加してつなぐ |
| Make | 「AIエージェント」モジュールにツールとして他のモジュール(HTTPリクエスト等)を登録 | シナリオ内でAIエージェントモジュールを配置し、ツールとして使うモジュールを紐づける |

ポイントは、Difyやn8n、Makeのようなノーコードツールでは、開発者が書くようなJSON Schemaを自分で書かなくても、画面上で「このツールを使えるようにする」とチェックを入れるだけでFunction Callingの仕組みが動く、という点である。裏側の動作原理(モデルが「呼びたい処理」を提案し、ツール側が実行して結果を返す)は共通しているため、エンジニアと会話する際にこの対応関係を知っておくと話が噛み合いやすい。

### 業務シナリオ例(CRM連携)

「先週契約した顧客の担当者名を教えて」という社内チャットボットへの質問を例にすると、流れは次のようになる。

1. ユーザー: 「先週契約したA社の担当者は誰?」とチャットボットに入力
2. モデル: 「`search_crm`という関数を、`company_name: "A社", contract_period: "先週"`という条件で呼びたい」と判断して構造化データを返す
3. システム側: 実際にCRM(顧客管理システム)のAPIにその条件で問い合わせ、「担当者: 山田太郎」という結果を取得
4. モデル: 結果を受け取り、「A社の担当者は山田太郎さんです。」と自然な文章で回答

このように、Function Callingがあることで、AIチャットボットは「一般的な受け答え」から「自社のCRM・在庫システム・予約システムと連携した実務ツール」へと役割を広げられる。

## 注意点・よくある誤解

- **モデルは実行しない、判断するだけ**: モデルが返すのは「この関数をこの引数で呼びたい」という提案(JSON)であり、実際にAPIを叩く・DBを更新するのは必ず開発者側のプログラムである。この分離を理解していないと「AIが暴走して勝手に処理を実行した」という誤解が生じる(裏を返せば、実行前に確認ステップを挟むといった安全対策も設計次第で可能ということ)。
- **引数の値をそのまま信用しない**: モデルが必須の引数を推測で埋めてしまうことがある(例: 場所を指定していないのに「東京」と補って呼び出す)。金額の確定や送信・削除など取り返しのつかない処理を任せる場合は、実行前に人による確認を挟む、確認なしで実行してよい範囲をツールの説明文で明示する、といった設計上の工夫が要る。
- **関数の説明文(description)の質が精度を左右する**: モデルは関数名や引数名だけでなく、`description`に書かれた説明文を読んで「いつこの関数を使うべきか」を判断する。説明が曖昧だと、不要な場面で呼び出したり、逆に必要な場面で呼び出さなかったりする。関数の目的・使うべき条件・使うべきでない条件を具体的に書くのがコツ。
- **ツールを増やしすぎない**: 使えるツールの数が多すぎると、モデルがどれを使うべきか迷い、精度が落ちることがある。業務で本当に必要なツールに絞り込む、または類似ツールを1つに整理するといった工夫が有効。
- **セキュリティ・権限管理が必須**: 社内システムに書き込み権限を持つ関数を公開する場合、その関数を呼べるAIの利用範囲(誰がどの用途で使えるか)や、実行前のログ記録・承認フローを別途設計する必要がある。Function Calling自体はアクセス制御の仕組みではない点に注意。
- **命名や細部の仕様は各社で異なる**: OpenAI・Claude・Geminiで「関数」「ツール」の呼び方やJSONのフィールド名(`parameters`か`input_schema`か等)が異なるため、複数モデルを併用するシステムを作る場合は、ツール定義を各API向けに変換する層が必要になる。

## 最初の一歩

社内で「AIに聞いても答えられない情報」(例: 在庫数、最新の受注状況、社内カレンダーの空き状況)を1つ思い浮かべ、それを取得できる社内APIやスプレッドシートがすでにあるかをエンジニアや情報システム部門に確認してみる。すでにAPIがあれば、それがそのままFunction Callingの「関数」の候補になる。
