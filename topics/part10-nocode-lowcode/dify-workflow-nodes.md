# Difyワークフローの主要ノードと組み立て方

## これは何か

Difyのワークフロー画面を開くと、丸みを帯びた四角い部品(ノード)が矢印でつながった図が表示される。「開始」「LLM」「知識取得」といった名前は書いてあるものの、種類が多く、どれをどう組み合わせれば思い通りの処理になるのか分からず手が止まる、という悩みに応えるのが本ページである。ノードは「1つの処理ステップ」を表す部品で、これを矢印(処理の流れ)でつなぐことで、プログラミングなしに「問い合わせ内容を判定→回答を作る→返す」といった一連の業務ロジックを組み立てられる。

## 仕組み・背景

Difyのワークフローは、ノード(処理の箱)とエッジ(ノード同士をつなぐ矢印)で構成される図(ワークフローエンジンでは一般に「DAG: 有向非巡回グラフ」と呼ばれる、処理が一方向に流れ、ループしない図)で、上流ノードの出力が下流ノードの入力として渡される。1つのノードの設定画面では「どの変数を受け取るか」「何を出力するか」を指定でき、その出力は `{{#ノードID.出力名#}}` のような変数として下流のノードから参照できる。

Difyには2種類のアプリタイプがあり、使えるノード構成が少し異なる。

- **ワークフロー(Workflow)**: バッチ処理・定型業務の自動化向け。「開始」ノードで始まり、必ず1つの「終了(End)」ノードで終わる。会話形式ではなく、1回の実行で入力から出力までを一気に処理する。
- **チャットフロー(Chatflow)**: チャットボット向け。「開始」ノードで始まり、「回答(Answer)」ノードで終わる。回答ノードは会話の途中でも配置でき、1つのフローの中に複数配置できる(例: 一次回答を先に返し、詳細を追って返す、といった段階的な応答が可能)。

また「開始」ノードには2種類の起動方法がある。ユーザーが入力するかAPI経由で呼び出されると動く**User Input型**(通常のチャットボット・業務アプリはこちら)と、スケジュールや外部サービスのイベント(Webhookなど)をきっかけに自動実行される**Trigger型**(2025年後半に追加された比較的新しい機能)である。この2つは同じキャンバス上に共存できず、どちらか一方を選ぶ。本ページで扱う例はすべてUser Input型を前提とする。

## 使いどころ・使い分け

主要なノードの役割と、使うべき場面を一覧にした。

| ノード名 | 一言でいうと | こういう場合に使う |
|---|---|---|
| **開始(Start)** | ワークフローの入口。ユーザーの質問やフォーム入力を受け取る | 全てのワークフロー・チャットフローに必須(キャンバスに1つだけ) |
| **LLM** | プロンプトをAIモデルに送り、文章生成・要約・翻訳などの結果を受け取る | 文章の生成・判断・変換をさせたいとき。ワークフローの主役になることが多い |
| **知識取得(Knowledge Retrieval)** | 事前に登録したナレッジベース(社内文書など)から、質問に関連する文章を検索して取り出す | 社内規程・マニュアル・FAQなど自社データに基づいて回答させたいとき(RAG=検索拡張生成の中核部品) |
| **条件分岐(IF/ELSE)** | 変数の値を判定し、ルールに沿って処理を2方向以上に分岐させる | 「金額が1万円以上か」「特定のキーワードを含むか」など、条件がはっきり書けるとき |
| **質問分類器(Question Classifier)** | LLMに「この質問はどのカテゴリか」を意味的に判定させ、分岐させる | 「クレーム/使い方の質問/契約の相談」のように、ルールでは書きにくい曖昧な分類をしたいとき |
| **ツール(Tool)** | Web検索・画像生成・Slack通知など、Difyに組み込まれた外部サービス連携を1ノードとして呼び出す | 既製の連携機能で足りるとき(50種類以上のツールが用意されている) |
| **HTTPリクエスト** | 任意のAPIエンドポイントに直接リクエストを送る | 自社システムのAPIなど、組み込みツールに無い外部サービスと連携したいとき |
| **コード実行(Code)** | Python または JavaScript(Node.js)のコードをその場で実行する | 文字列の整形、日付計算、複雑なデータ加工など、既存ノードでは組みにくい細かい処理をしたいとき |
| **テンプレート(Template)** | Jinja2という書式でテキストを組み立てる(変数を差し込んだ定型文の生成) | 「〇〇様、お問い合わせありがとうございます。回答: {{answer}}」のような定型文を作りたいとき |
| **変数集約(Variable Aggregator)** | 条件分岐などで枝分かれした複数ルートの出力を、1つの変数にまとめる | 分岐後にどのルートを通っても、後続ノードから同じ変数名で結果を参照したいとき |
| **パラメータ抽出(Parameter Extractor)** | 自由文からLLMを使って特定の項目(日付・金額・氏名など)を構造化データとして抜き出す | ユーザーの雑多な入力から必要な情報だけをフォーム的に取り出したいとき |
| **イテレーション(Iteration)** | リスト(配列)の要素1つ1つに同じ処理を繰り返す | 複数件のデータ(問い合わせリストなど)をまとめて一括処理したいとき |
| **エージェント(Agent)** | LLMに複数のツールの使用可否・使用順序を自律的に判断させる | 定型フローでは対応しきれない、状況に応じて動的にツールを選ばせたい高度なケース |
| **回答(Answer)** | チャットフロー専用。会話にテキストを返す | チャットフローの終端、または会話途中の中間応答に使う |
| **終了(End)** | ワークフロー専用。処理結果を最終出力として確定する | ワークフローの終端(1つだけ配置可能) |

**判断に迷いやすい2つの使い分け**

- **条件分岐 vs 質問分類器**: 「合計金額が10,000円以上」のようにルールで明確に書ける条件は条件分岐(IF/ELSE)、「これはクレームか問い合わせか」のように文脈次第で判断が変わる曖昧な分類は質問分類器、と使い分ける。質問分類器は内部でLLMを呼び出すため、条件分岐より応答が遅く・コストがかかる点も判断材料になる。
- **ツール vs HTTPリクエスト vs コード実行**: Difyの組み込みツール一覧にある機能(Web検索、画像生成など)はツールノードで足りる。自社の独自APIを叩きたいならHTTPリクエスト。API呼び出しを伴わない純粋なデータ整形(日付フォーマット変換など)はコード実行、が基本の順番。

### 主要ツールでの対応関係

Difyのノードと似た概念は、他の自動化ツールでは次のように呼ばれる。記事や社内資料でツールを横断して説明する際の対応表として使える。

| 概念 | Dify | n8n | Make |
|---|---|---|---|
| 条件で処理を分ける | 条件分岐(IF/ELSE) | IFノード | Router(ルーター) |
| 意味で処理を分ける | 質問分類器 | (LLM+IFで代用が多い) | (LLM+Routerで代用が多い) |
| コードで加工する | コード実行(Code) | Codeノード | (JavaScriptモジュール) |
| 外部APIを直接叩く | HTTPリクエスト | HTTP Requestノード | HTTP モジュール |
| 分岐後の結果を1本化 | 変数集約 | Mergeノード | (Router後の各ルートで個別処理が一般的) |

## 実務での使い方

### ノードの追加・接続の手順(画面操作)

1. Difyの管理画面で「アプリを作成する」→「最初から作成」を選び、「チャットフロー(Chatflow)」または「ワークフロー(Workflow)」を選択してアプリ名を入力し作成する
2. 作成直後のキャンバスには「開始」ノードが自動で1つ置かれている
3. ノードの右端の丸い接続点にマウスを乗せると表示される「+」をクリックすると、追加できるノードの一覧がプルダウンで表示されるので、目的のノード(例: LLM)を選ぶ
4. 追加されたノードをクリックすると右側に設定パネルが開く。「変数を選択」の欄をクリックすると、これまでのノードが出力した変数の一覧が表示されるので、使いたい変数を選ぶ
5. ノード同士を離れた位置に配置した場合は、片方の接続点からもう片方の接続点までドラッグして線を引くと接続できる
6. 条件分岐や質問分類器のように出力が枝分かれするノードでは、各分岐の先に別々のノードをつなげられる。分岐後に処理を1本化したい場合は「変数集約」ノードを分岐の合流点に置く
7. 画面右上の「実行」または各ノード右上の再生アイコンから、ノード単体・フロー全体をテスト実行して、途中経過(各ノードの入出力)を確認できる(ステップ実行)
8. 動作確認ができたら画面右上の「公開する」でアプリを本番反映する

### 具体例: 問い合わせ内容を分類してカテゴリ別に回答するチャットボット

社内のカスタマーサポート一次対応を想定した、4ノード+分岐構成の最小構成例。

1. **開始(User Input)**: `sys.query`(ユーザーが入力した問い合わせ文)を受け取る
2. **質問分類器**: 入力変数に `sys.query` を指定し、分類先として「製品の不具合」「使い方の質問」「契約・請求」「その他」の4クラスを定義する。分類にはGPT-4o miniのような軽量・低コストなモデルで十分なことが多い
3. 分類結果ごとに枝分かれした先に、それぞれ**LLMノード**を配置し、カテゴリ別のシステムプロンプトを設定する
   - 「製品の不具合」の枝の前には**知識取得ノード**を挟み、製品マニュアルのナレッジベースを検索させてからLLMに渡すことで、社内文書に基づいた回答にする
   - 「契約・請求」の枝は個人情報を含みやすいため、LLMの回答は要点整理のみに留め、最後に「担当部署に転送します」という定型文を付ける設計にする
4. **変数集約**: 4つの枝それぞれのLLM出力(型はすべて文字列に揃える)を1つの変数 `final_answer` にまとめる。どの枝を通っても後続ノードは `final_answer` という同じ名前で結果を参照できる
5. **回答(Answer)**: `final_answer` の内容をユーザーに返す

LLMノードのシステムプロンプト例(「使い方の質問」の枝、コピペして調整可能):

```
## 役割
あなたは自社SaaS製品のカスタマーサポート担当です。

## 回答方針
- ユーザーの質問: {{#sys.query#}}
- 上記の「使い方」に関する質問に、丁寧語で3文以内に要点をまとめて回答してください
- 不明な点がある場合は、推測で答えず「サポート窓口へお問い合わせください」と案内してください
```

### コストの考え方

Dify Cloud版は「メッセージクレジット」という単位で従量制の枠が決まっており、LLMノード・質問分類器・エージェントノードなど、AIモデルを呼び出すノードを1回実行するたびにクレジットを消費する(2026年7月時点の目安: Professionalプラン月額$59で月5,000クレジット、Teamプラン月額$159で月10,000クレジット。金額・クレジット数は変更されやすいため公式サイトdify.ai/pricingで要確認)。条件分岐やコード実行、変数集約のようにAIモデルを呼ばないノードはクレジットを消費しない。つまり「分岐を増やすこと」自体はコストに影響しないが、「分岐の先にLLMノードをいくつ置くか」がコストに直結する。上記の例のように分岐ごとにLLMを1つずつ置く設計は分かりやすい反面、カテゴリ数が増えるほど消費クレジットも比例して増える点は設計時に意識する。

## 注意点・よくある誤解

- **回答ノードと終了ノードは別物で混在できない**: チャットフローは「回答」、ワークフローは「終了」という、アプリタイプ専用のノードを使う。ワークフローで作り始めたのに会話的なアプリにしたくなった場合、ノードを差し替えるだけでは済まず設計を見直す必要がある
- **変数集約はデータ型を揃える必要がある**: 最初に接続した変数が文字列なら、他の分岐からの変数もすべて文字列にしないとエラーになる。数値や配列が混ざる設計をする場合は、集約前にテンプレートノードなどで型を揃える
- **知識取得ノードは「ナレッジベースが空」だと何も返さない**: 事前にドキュメントを取り込んでインデックスを作成しておかないと、LLMに渡す参考情報がゼロのまま回答が生成され、精度が落ちる。ワークフローを作る前にナレッジベース側の準備を済ませておく
- **条件分岐と質問分類器を混同しやすい**: 「キーワードが完全一致するか」で済む単純なルーティングに質問分類器(LLM呼び出し)を使うと、遅く・高くつくだけで精度も上がらない。まず条件分岐で書けないか検討し、書けない曖昧な判定だけ質問分類器に任せる
- **公開前に必ずステップ実行で確認する**: 分岐が絡むワークフローは、想定したルートを本当に通っているか、途中の変数の中身が期待通りかを、公開前にステップ実行(テスト実行)で1本ずつ確認する。分岐の見落としは本番で気づきにくい

## 最初の一歩

Difyでチャットフローアプリを新規作成し、「開始→質問分類器(2クラスだけでよい)→それぞれのLLMノード→回答」という最小構成(4ノード)を組んで、実際に2種類の問い合わせ文を入力してステップ実行で分岐の挙動を確認してみる。
