# Difyワークフローの基本

## これは何か

「社内FAQに答えるだけのボットは作れたが、問い合わせ内容によって処理を振り分けたり、複数の判断・確認ステップを挟んだ業務フローをコードなしで自動化したい」——そんな一歩進んだニーズに応えるのがDifyの「ワークフロー」機能である。[「Difyとは何か」](./dify-basics.md)で触れた通り、Difyのアプリタイプは大きく「チャットボット(1問1答の単純な会話アプリ)」と「ワークフロー(複数の処理ステップをフローチャートのようにつないだ処理フロー)」に分かれる。本ページはワークフローを実際に組み立てる実践編の入口として、ノードの全体像・RAG(検索拡張生成、社内文書などを検索してAIの回答に反映させる仕組み)やAPI連携との関係を扱う。ノード1つ1つの詳しい使い分けは[Difyワークフローの主要ノードと組み立て方](./dify-workflow-nodes.md)、RAGの実装手順は[DifyでのRAG実装](./dify-rag-implementation.md)、外部システムからの呼び出しは[DifyのAPI連携](./dify-api-integration.md)にそれぞれ分けて詳述している。

## 仕組み・背景

ワークフローは、キャンバス上に「ノード」と呼ばれる処理ブロックを配置し、線でつないで実行順序を定義する仕組みである。各ノードは入力変数を受け取り、処理結果を後続ノードに変数として渡す。プログラミングでいう「関数を順番に呼び出す」処理を、コードを書かずに視覚的に組み立てられるのが最大の特徴。

Difyには「ワークフロー」に加えて、会話の文脈(前のやり取りの記憶)を保持しながら複数ステップを実行する「チャットフロー」という派生タイプもある。ワークフローは呼び出しごとに完全に独立した処理(バッチ処理・API連携向き)であるのに対し、チャットフローは対話の継続を前提とする点が異なる。本ページでは主にワークフロー(非対話型)を中心に扱う。

### 主要ノードの種類

| ノード | 一言説明 |
|---|---|
| 開始(Start) | ワークフロー実行に必要な入力変数を定義する起点。全ワークフローに必須。ユーザー入力・API呼び出しで動く通常型のほか、下記「トリガー」を起点に設定することもできる |
| トリガー(Trigger) | スケジュール(毎朝9時など)、Webhook、Slack・Googleカレンダー等の外部イベントをきっかけに、人の操作なしでワークフローを自動起動する起点ノード。2025年後半に追加された比較的新しい機能で、「開始」ノードの発展形にあたる |
| LLM | 指定したAIモデル(GPT・Claude・Gemini等)にプロンプトを送り、生成結果を得る中心ノード |
| 知識取得(Knowledge Retrieval) | ナレッジベースに対してRAG検索を行い、関連する文書の断片(チャンク)を取得する |
| 条件分岐(IF/ELSE) | 指定した条件に応じて処理を2方向以上に分岐させる |
| 質問分類(Question Classifier) | ユーザーの入力をあらかじめ定義したカテゴリにLLMで自動分類する |
| 人間の入力(Human Input) | ワークフローの実行を一時停止し、担当者にフォームを送って承認・修正・差し戻しなどの判断を仰いでから処理を再開する(2026年前半にv1.13で追加)。Web App画面またはメール経由で回答者に通知できる |
| コード実行(Code) | Python/Node.jsのコードを実行し、他ノードでは対応しにくいデータ加工を行う |
| テンプレート(Template/Jinja2) | Jinja2テンプレート記法で複数の変数を組み合わせ、文字列を整形する |
| HTTPリクエスト | 外部API・社内システムにHTTPリクエストを送り、データを取得・送信する |
| パラメータ抽出(Parameter Extraction) | 自由文からLLMが構造化パラメータ(日付・金額などの項目)を抽出する |
| イテレーション(Iteration) | リストの各要素に対して同じ処理を繰り返す(配列の要素ごとに独立して処理する並列的なループ) |
| ループ(Loop) | 終了条件を満たすまで処理を繰り返す(前回の実行結果を次の回に引き継ぐ点がイテレーションと異なる。無限ループ防止のため最大実行回数を必ず設定する) |
| ドキュメント抽出(Document Extractor) | アップロードされたPDF・Word等のファイルからテキストを抽出する。LLMは添付ファイルをそのままは読めないため、ファイルを扱うワークフローでは実質必須 |
| リスト操作(List Operator) | 配列データを条件でフィルタ・並べ替え・件数指定して取り出す(例: 複数ファイルのうち画像だけを後続ノードに渡す) |
| 変数集約(Variable Aggregator) | 複数の分岐から来た変数を1つにまとめ、後続ノードの設定を簡略化する |
| エージェント(Agent) | ツールを自律的に選択・実行しながら複数ステップの意思決定を行う(2025年以降ワークフロー内のノードとしても利用可能) |
| ツール(Tool) | Difyに組み込まれた50以上の外部ツール(Web検索・画像生成等)を呼び出す |
| 終了(End) | ワークフローの最終出力を定義する |

ノードの数が多く迷いやすいため、判断に迷いやすい組み合わせの詳しい使い分け(条件分岐 vs 質問分類器、ツール vs HTTPリクエスト vs コード実行など)は[Difyワークフローの主要ノードと組み立て方](./dify-workflow-nodes.md)にまとめている。

### RAG実装の流れ(概要)

社内文書を検索して回答に活かす「知識取得」ノードは、①「ナレッジ」メニューでナレッジベースを作成しファイルをアップロード→②自動でチャンク分割・ベクトル化・インデックス登録→③ワークフローに「知識取得」ノードを追加し検索対象を指定→④その出力を後続のLLMノードのプロンプトに `以下の資料に基づいて回答してください: {{#knowledge_retrieval.result#}}` のように埋め込む、という流れで組み立てる。チャンク分割方式(自動/親子チャンク)やインデックス方式(高品質=embeddingベースのベクトル検索/経済的=キーワードベース)の選び方まで含めた詳しい手順は[DifyでのRAG実装](./dify-rag-implementation.md)を参照。

## 使いどころ・使い分け

| やりたいこと | 適したアプリタイプ |
|---|---|
| FAQ・社内問い合わせへの一問一答対応 | チャットボット([Difyとは何か](./dify-basics.md)で解説) |
| 分類→生成→条件分岐→承認など複数ステップの処理を自動化したい | ワークフロー |
| 対話の文脈を保ちながら複数ステップの処理をしたい(ヒアリング→提案など) | チャットフロー(ワークフローの会話特化版) |
| 完成した処理を他のアプリから部品として呼び出したい | ワークフロー(「ツール」として公開し他のワークフロー/チャットフローから呼び出す) |
| 毎朝の定期実行・外部サービスのイベント発生時に自動起動したい | ワークフロー(開始ノードを「トリガー」に設定) |
| AIが作った成果物を、人が確認・承認してから確定させたい | ワークフロー(生成ノードの後に「人間の入力」ノードを挟む) |

Dify・n8n・Makeの住み分けは、[Difyとは何か](./dify-basics.md)で触れた通り「Difyは生成AI呼び出しに特化したエンジン、n8n/Makeは業務システム全般をつなぐオーケストレーター」という整理が目安になる。ワークフロー機能で複雑な条件分岐を組みたくなった段階でも、外部SaaSとの連携が主目的ならn8n/Makeの検討価値がある一方、LLMのプロンプト調整・RAG精度の作り込みが主目的ならDifyのワークフローが適している。

## 実務での使い方

### 画面操作の基本手順

1. Difyのダッシュボードで「最初から作成」をクリック
2. アプリタイプの選択画面で「Workflow」を選ぶ(「Chatflow」はチャットボットの発展形として別枠にある)
3. 編集画面左側のノード一覧から必要なノードをキャンバスにドラッグ&ドロップし、ノードの右端の丸をドラッグして次のノードに接続する
4. 各ノードをクリックすると右側にパラメータ設定パネルが開く(プロンプト、モデル選択、変数の紐付けなど)
5. 画面右上の「実行」でテスト実行し、各ノードの入出力をステップごとに確認する
6. 問題なければ右上の「公開する」でバージョンを公開する

### 実務ユースケース例:問い合わせメールの分類・返信案作成ワークフロー

問い合わせメールの本文を受け取り、カテゴリに分類したうえで、カテゴリ別のテンプレートで返信案を作成するワークフロー。構成は「開始→LLM(分類)→条件分岐→LLM(返信案生成、カテゴリ別に分岐)→変数集約→終了」。

**LLMノード(分類)のプロンプト例(コピペ可)**

```
あなたは問い合わせ内容を分類するアシスタントです。
以下の問い合わせ本文を読み、次の4カテゴリのうち最も当てはまるもの1つだけを、
カテゴリ名のみで出力してください(説明や理由は不要)。

カテゴリ: 料金について / 技術的な不具合 / 契約・解約 / その他

問い合わせ本文:
{{#start.inquiry_text#}}
```

**LLMノード(返信案生成、分岐後)のプロンプト例(コピペ可)**

```
あなたはカスタマーサポート担当者です。
以下の問い合わせに対する返信メールの文案を、丁寧なビジネス日本語で作成してください。

【カテゴリ】料金について
【問い合わせ本文】
{{#start.inquiry_text#}}

【回答のポイント】
- 現在の料金プラン一覧ページへの案内を含める
- 詳細な見積りが必要な場合は担当者から改めて連絡する旨を伝える
```

条件分岐ノード(IF/ELSE)または質問分類ノードで、直前のLLMノードが出力したカテゴリ文字列を条件に使い、カテゴリごとに異なる返信案生成ノードへ振り分ける。分岐後の出力は「変数集約」ノードで1本にまとめてから終了ノードに渡すと、後続の設定がシンプルになる。

**発展形: 送信前に人の確認を挟みたい場合**

返信案をそのまま自動送信せず、担当者の目視確認を挟みたい場合は、返信案生成ノードの直後に「人間の入力(Human Input)」ノードを追加する。担当者にWeb App画面またはメールでフォームが届き、「承認」「差し戻し」などのボタンを押すと、その選択に応じてワークフローが再開・分岐する。クレーム対応や金額を含む返信など、誤送信のリスクが高い場面での安全弁として使える。

### API連携で外部システムから呼び出す(概要)

ワークフローを「公開する」で確定させ、左サイドバーの「アクセスAPI(API Access)」からAPIキーを発行すると、`POST https://api.dify.ai/v1/workflows/run` にAPIキーを付けてリクエストするだけで、社内システムやWebサイトのチャットウィジェットなど、Dify以外の画面・システムからこのワークフローを部品として呼び出せるようになる。同期/非同期(`response_mode`)の使い分けや実行結果のポーリング方法など、外部連携の詳しい手順は[DifyのAPI連携](./dify-api-integration.md)を参照。

## 注意点・よくある誤解

- **ノードが増えるとスパゲッティ化しやすい**: 条件分岐や並列処理が増えるほど全体像が把握しにくくなる。ノードに分かりやすい名前を付ける、処理単位でワークフローを分割し「ツール」として呼び出す構成にする、といった工夫で可読性を保つ
- **RAGの精度はチャンク分割とナレッジベースの整備次第**: 表組みや複雑なレイアウトを含むPDFをそのまま読み込ませると、チャンク分割の境目で情報が分断され検索精度が落ちやすい。あらかじめAIが読み取りやすい形式に整えておくと精度が上がる([AIが読みやすいデータ形式](../part07-data-analysis/ai-friendly-data-formats.md)を参照)
- **料金プランによる実行回数・メッセージクレジットの制限**: Difyクラウド版はLLM呼び出し1回ごとに「メッセージクレジット」を消費する従量制で、Sandbox(無料)は総量200クレジットのみ・APIレート制限も厳しい。業務利用の目安はProfessional(月額59ドル/ワークスペース、月5,000クレジット)以上で、Team(月額159ドル/ワークスペース、月10,000クレジット)はメンバー数・ナレッジ容量も拡大する(2026年7月時点、価格は変更されやすいため公式サイト dify.ai/pricing で最終確認)。詳細は[Difyとは何か](./dify-basics.md)のプラン表も参照
- **ループ・イテレーション・エージェントノードはコストが跳ねやすい**: これらのノードは内部でLLM呼び出しを繰り返すため、1回のワークフロー実行で消費するメッセージクレジットが急増しやすい。ループには必ず最大実行回数を設定し、想定外の入力で無限ループ・高額請求にならないようテスト実行で確認する
- **トリガーで自動起動する場合はセキュリティ設定を忘れない**: Webhookトリガーは推測しにくいURL・シークレットキーでの検証を必ず行う。外部に公開したトリガーURLが漏れると第三者に不正実行される恐れがある
- **本番公開前のテストが必須**: 条件分岐が増えるほど想定外の入力パターンが生まれる。代表的な入力例を複数用意し、テスト実行で各分岐の挙動を確認してから公開する

## 最初の一歩

Difyのダッシュボードで「最初から作成」→アプリタイプ「Workflow」を選び、「開始ノード→LLMノード(入力文章を要約させるだけ)→終了ノード」という最小構成を組んでテスト実行してみる。
