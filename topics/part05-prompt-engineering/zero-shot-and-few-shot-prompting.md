# Zero-shot・Few-shotプロンプティング

## これは何か

Zero-shot(ゼロショット)は「お手本(例示)を一切見せず、指示だけでAIにタスクをやらせる」方法、Few-shot(フューショット)は「やってほしいことの見本を2〜5個ほどプロンプトに入れてから本番の入力を渡す」方法である。同じ指示文でも、出力の形式・トーン・分類基準がバラつく、期待した書式で返ってこない、といった悩みの多くは「例示を入れていない」ことが原因であり、この2つの違いと使い分けを知らないと、毎回プロンプトの文章を工夫するだけで精度を上げようとして遠回りしてしまう。

## 仕組み・背景

大規模言語モデルは大量のテキストから「次に来そうな単語」を予測するように学習されているため、プロンプトの中に具体的な入出力のペア(例示)を置くと、そのパターンを文脈から読み取って(in-context learning、文脈内学習)本番の入力にも同じルールを当てはめようとする。これがFew-shotプロンプティングの原理であり、モデルの重み(パラメータ)を追加学習させる「ファインチューニング」とは異なり、プロンプトを書くだけで即座に効果が出る点が特徴。

呼び方は例示の数で変わる。

- **Zero-shot**: 例示ゼロ。指示・背景・出力形式の説明だけで実行させる
- **One-shot**: 例示1個
- **Few-shot**: 例示2〜5個程度(複数形のshotsからこう呼ばれる)

なお「Zero-shotだから精度が低い」わけではない。近年の高性能モデルは指示追従(instruction following)の学習が進んでいるため、明確な指示さえ書けばZero-shotでも実務の大半のタスクはこなせる。Few-shotが真価を発揮するのは、「言葉で説明しにくいが、見せれば一発でわかる」パターン(独自の分類基準、癖のある文体、決まった出力フォーマットなど)を伝えたいときである。

## 使いどころ・使い分け

| 観点 | Zero-shotが向く | Few-shotが向く |
|---|---|---|
| タスクの性質 | 一般的で説明しやすい(要約・翻訳・雑談・アイデア出し) | 独自ルール・社内基準・癖のある形式を伝えたい |
| 出力形式の自由度 | 多少ブレても許容できる | 完全に揃った形式・分類ラベルが必要 |
| 求める再現性 | 毎回違う表現でよい(むしろ多様性が欲しい) | 毎回同じ基準・同じフォーマットで揃えたい |
| プロンプトの手間 | 最小限で試したい・スピード重視 | 多少手間をかけてでも精度を上げたい |
| 例の用意しやすさ | 適切な例が思いつかない・用意する時間がない | 過去の実例(良い回答・悪い回答)が手元にある |

判断の目安は「口頭で説明するとしたら1分で伝わるか」。1分で伝わるならZero-shotで十分。「見せた方が早い」と感じるならFew-shotを使う。

なお、課題が「形式・トーンのブレ」ではなく「計算・条件判定のミス」である場合は、例示を増やしても解決しない。その場合は思考過程を書かせる[Chain-of-Thought(CoT)プロンプティング](chain-of-thought-prompting.md)の出番になる。実務では「まずZero-shotで試す→形式が揃わなければFew-shotを足す→計算や論理でミスが出るならCoTを足す」の順に段階的に強化するのが基本の進め方。形式と判断精度の両方を揃えたい場合は、Few-shotの例の中に思考過程まで含めて示す「Few-shot CoT」という併用もある(実例はCoTページを参照)。

**例数の目安**: 一般的には2〜5個で十分とされ、5個を超えても精度向上は頭打ちになりやすく、トークン(AIが処理する文字の単位で、料金や処理速度に影響)の無駄遣いになりやすい。タスクが複雑な場合や、扱いたいパターン(カテゴリ・エッジケース)の種類が多い場合は、カテゴリ数に応じて例を増やす。

**質と多様性が数より重要**: 似たような例ばかり並べると、AIが「例に共通する表面的な特徴」を意図せず学習してしまう(例: 例文が全部長文だと、短い入力にも長文で答えようとする)。実務では以下を意識する。

- 各カテゴリ・パターンを最低1つずつカバーする(偏った例だけだと精度が下がる)
- 判断が難しい境界事例(エッジケース)を1つは含める
- 例の順序にも注意する。モデルは直前に見た例の影響を受けやすい(近さの効果)ため、最も代表的な例・最も伝えたい例を最後に置くと効果的とする報告がある
- 例の形式(改行・記号の使い方など)を全例で統一する。フォーマットの揺れもパターンとして学習されてしまう

## 実務での使い方

### コピペで使える例1: 問い合わせメールの分類

**Zero-shot版**(基準が単純で説明しやすい場合)

```
以下の問い合わせメールを「クレーム」「質問」「resolved(対応不要な御礼など)」の
いずれか1語で分類してください。理由は不要、分類名のみ出力してください。

【メール本文】
{ここに分類したいメール本文を貼り付け}
```

**Few-shot版**(自社独自の分類基準がある場合)

```
以下の問い合わせメールを、社内基準に沿って分類してください。
分類名のみを1語で出力してください。

<example>
入力: 「先週注文した商品がまだ届きません。発送状況を教えてください」
出力: 質問
</example>

<example>
入力: 「届いた商品が説明と違います。返金してください。もう二度と使いません」
出力: クレーム
</example>

<example>
入力: 「先日は迅速に対応いただきありがとうございました。特に返信は不要です」
出力: resolved
</example>

<example>
入力: 「注文をキャンセルしたいのですが、まだ間に合いますか？急いでいます」
出力: 質問
</example>

上記の例と同じ基準で、次のメールを分類してください。

入力: 「{ここに分類したいメール本文を貼り付け}」
出力:
```

このFew-shot版では、「キャンセル希望＝クレームではなく質問」「感謝の返信＝resolved」といった、言葉で定義しにくい社内独自のニュアンスを例示だけで伝えている。

### コピペで使える例2: 文体変換(カジュアル→丁寧なビジネス文体)

**Zero-shot版**

```
次の文章を、丁寧なビジネスメールの文体に書き換えてください。

{ここに変換したい文章を貼り付け}
```

Zero-shotでも「丁寧なビジネス文体」程度の一般的な変換なら十分対応できる。一方、「うちの会社らしい言い回し」まで再現したい場合はFew-shotが必要になる。

**Few-shot版**

```
次の文章ペアは、カジュアルな文章と、当社らしいビジネス文体への変換例です。
このトーン・語尾の癖を踏襲して、最後の文章を変換してください。

<example>
カジュアル: 「明日の会議、時間変更できますか？」
変換後: 「明日ご予定いただいております会議につきまして、恐れ入りますが
開催時刻の変更は可能でしょうか。ご確認のほどよろしくお願いいたします」
</example>

<example>
カジュアル: 「資料まだ見れてないので待ってください」
変換後: 「大変恐縮ですが、資料はまだ確認できておりません。
今しばらくお時間をいただけますと幸いです」
</example>

カジュアル: 「{ここに変換したい文章を貼り付け}」
変換後:
```

### 主要ツールでの設定・書き方の対応

Few-shotは特別な機能ではなく、プロンプトの中に例を書き込むだけで、どのツールでも同じように使える。ただしAIに「これは指示ではなく例示だ」と伝える書き方には、ツールごとにクセがある。

| ツール/モデル | 例示の書き方の目安 |
|---|---|
| Claude | `<example>`〜`</example>`タグ(複数なら`<examples>`で囲む)で囲むと、指示や参照データと区別しやすく公式に推奨されている |
| ChatGPT(GPT系) | Markdownの見出しや「入力: / 出力:」のような箇条書き形式、あるいは`###`区切りで並べるのが一般的 |
| Gemini | 「例:」ラベル+箇条書き、またはJSON形式で入出力ペアを列挙する形が案内されている |
| いずれのツールも共通 | 例が多い/長い場合は、システムプロンプトやカスタム指示・Gem・プロジェクトの「指示」欄に固定登録しておくと、毎回貼り付ける手間が省ける(詳細は[プロンプトの基本構成要素](prompt-basic-structure.md)のツール対応表を参照) |

料金面では、Few-shotは例示の分だけ入力トークンが増える(=API利用の場合は課金対象が増える)ため、チャット画面での利用では体感しにくいが、API経由で大量件数を処理する業務(例: 問い合わせメールの自動分類バッチ)では、例の数と長さがコストに直結する点を意識する。

## 注意点・よくある誤解

- **「例を増やせば増やすほど良い」は誤解**: 前述の通り5個を超えると精度が頭打ちになりやすく、トークン消費が増えるだけになりがち。まず2〜3個で試し、精度が足りない箇所だけ例を追加する
- **偏った例は逆効果**: 特定のパターン・特定の答えの例ばかり並べると、AIがその偏りを「ルール」だと誤学習し、本来と違う分類・出力に偏ることがある(多数派バイアス)。カテゴリごとに最低1例を用意する
- **例の順序も結果に影響する**: 同じ例でも並べる順番を変えると出力が変わることがある。重要な例・代表的な例は最後に置く、あるいはランダム性を排除して固定順にするなど、意図的に並べる
- **フォーマットのクセまで学習される**: 例文の改行位置や句読点の使い方が不揃いだと、そのブレもパターンとして学習されてしまう。例は体裁を統一する
- **Zero-shotで指示が通らない場合、いきなりFew-shotに飛びつく前に指示文自体を見直す**: 曖昧な形容詞を具体的な条件に置き換えるだけで解決することも多い([プロンプトの基本構成要素](prompt-basic-structure.md)を参照)
- **推論(Thinking)モデルにFew-shot例を重ねると逆効果になることがある**: OpenAIは公式ガイドで、o1系をはじめとする推論モデルに過剰なFew-shot例を加えると性能が下がる場合があると案内している(Few-shot追加でZero-shotより精度が落ちた検証例も報告されている)。ChatGPTのThinking系・Claudeの拡張思考・GeminiのThinking系を使うときは、まず例なしで試し、それでも形式が揃わない場合だけ最小限の例を1〜2個足す順番が安全
- **機密情報を含む例をプロンプトに貼らない**: 実際の顧客データや社内秘の実例を例示に使う場合、SaaS版チャットツールの学習利用設定や、API利用時のログ保持ポリシーを確認してから使う

## 最初の一歩

直近でAIに依頼して「思っていた形式と違う」出力が返ってきた作業を1つ選び、そのときの「理想の出力例」を1〜2個プロンプトに追記して(Few-shot化して)、同じ依頼を投げ直し、Zero-shotのときと結果を見比べてみる。
