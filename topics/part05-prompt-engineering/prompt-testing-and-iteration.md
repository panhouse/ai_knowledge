# プロンプトの検証・反復改善の進め方(テストケース設計とバージョン管理)

## これは何か

「前はうまく動いていたプロンプトなのに、いつの間にか出力の質が落ちている」「プロンプトを少し直したら、直した箇所以外の出力までおかしくなった」——これは、プロンプトを毎回1つの入力・1回の目視だけで確認し、変更前後をきちんと比較していないために起きる典型的なトラブルである。プロンプトの検証・反復改善とは、①想定される入力パターンをいくつか集めた「テストケース」の束を用意し、②プロンプトを変更するたびに同じテストケース群に通して新旧を比較し、③AIモデルのバージョンが変わった際にも同じテストケースで再確認する、という一連のワークフローを指す。あわせて、どのプロンプトがいつどう変わったかを追える簡易な記録(バージョン管理)を残すことで、「良くなった/悪くなった」を勘ではなく根拠を持って判断できるようにする。

なお、[点数法(ルーブリック採点)プロンプティング](./rubric-scoring-prompting.md)は「1回の出力の質をどう採点するか」という物差しの作り方を扱う。本ページはその物差しを**複数のテストケース×複数のプロンプト版に繰り返し当てて、劣化や改善を追跡する運用**を扱う点で異なる。両者は組み合わせて使うと効果が高い。

## 仕組み・背景

ソフトウェア開発では、コードを変更したら自動テストを流し、「直したはずの箇所以外が壊れていないか」を確認する「回帰テスト(リグレッションテスト、変更によって既存の正常動作が壊れていないかを確認するテスト)」が当たり前に行われている。プロンプトも実質的には「AIへの指示書」というコードの一種だが、これまでは変更のたびにテストする文化が薄く、書いた人の「なんとなく良さそう」という感覚だけで運用されがちだった。

プロンプトの検証が難しい最大の理由は、同じプロンプトでも実行するたびに文言が微妙に変わる**非決定性(non-determinism、同じ入力でも毎回まったく同じ出力にはならない性質)**にある。そのため、テストの合否判定は「一言一句一致するか」ではなく、「含むべき要素が入っているか」「避けるべき表現(NGワード・トーン違反など)が入っていないか」「文字数や形式の制約を守っているか」といった**満たすべき条件**で行うのが基本になる。

もう1つの要因は、プロンプトを使うAIモデル自体が、ユーザーの知らないうちに更新されることである。ChatGPT・Claude・GeminiなどのチャットツールはPlus/Team/Enterprise問わずデフォルトモデルが定期的に新しくなり、APIも新モデルがリリースされる。モデルが変わると、同じプロンプトでも出力の癖(口調・形式の遵守度・拒否反応の出方など)が変わることがあるため、「プロンプトを変えていないのに結果が変わった」という事態が起こり得る。ベストプラクティスとして、**モデルの入れ替えとプロンプトの変更は同時に行わず、1つずつ検証する(まず新モデル×旧プロンプトを試し、そのあとでプロンプト変更を試す)**という「変数を1つずつ切り分ける」考え方が推奨されている。

## 使いどころ・使い分け

すべてのプロンプトに本格的なテスト運用を敷く必要はない。使う頻度と、間違えたときの影響度で投資レベルを判断する。

| 状況 | 検証・バージョン管理の必要度 | 理由 |
|---|---|---|
| 単発の雑談・その場限りの質問 | 不要 | やり直しのコストが低く、検証の手間に見合わない |
| 何度も使い回すシステムプロンプト・カスタム指示(GPTs/Gem/Projectsの指示欄など) | 高い(簡易版で十分) | 一度作り込めば効果が長く続く一方、劣化に気づきにくい。スプレッドシート1枚の記録でも十分効果がある |
| 顧客対応メール・社外向け文面など、失敗が信用問題に直結するプロンプト | 高い(厳格に) | 出力のブレがそのまま顧客体験・ブランドイメージのリスクになる。複数の代表的な入力で必ず確認してから配布する |
| 新しいモデルへの切り替えを検討している/自動で切り替わった | 高い(再検証必須) | モデルの癖が変わると、これまで安定していたプロンプトが急に破綻することがある |
| APIで大量に呼び出す業務システムのプロンプト | 高い(専用ツール推奨) | 手作業の比較では追いつかない件数になるため、後述のpromptfooやLangSmithのような自動化ツールへの投資が回収しやすい |
| 個人がメモ代わりに使う程度のテンプレート | 低い | 過剰な運用はかえって手間倒れになる。気になったときだけ見直す程度でよい |

判断の目安は「**使う頻度 × 間違えたときの影響度**」である。この掛け算が大きいプロンプトほど、テストケースの数を増やし、バージョン管理の粒度を細かくする価値がある。

## 実務での使い方

### ステップ1: テストケース(代表的な入力の束)を作る

まず、実際に来た問い合わせ・過去に使った依頼文などから、5〜10件程度の「代表的な入力パターン」を集める。網羅すべき類型は次の3つ。

- **典型的な入力**: 最も頻度の高いパターン(例: 標準的な問い合わせメール)
- **エッジケース**: 空欄・極端に長い文章・別の言語が混ざる・情報が不足しているなど、崩れやすい入力
- **過去に失敗した入力**: 一度誤った分類・不適切なトーン・事実誤認などが起きた実例(同じ失敗を繰り返していないか確認する定点観測になる)

### コピペで使えるテストケース表テンプレート

スプレッドシートやドキュメントにそのまま貼って使える。

```
| ID | 入力(そのまま貼る) | 満たすべき条件(NG例も) | 現行版の出力結果 | 判定(OK/NG) | メモ |
|----|----------------------|--------------------------|--------------------|--------------|------|
| 1  | (典型的な問い合わせ文) | ・分類名が4種類のいずれかである ・理由が1文で添えられている ・敬語が崩れていない | | | |
| 2  | (情報が一部欠けた問い合わせ文) | ・不明点を確認する一言が含まれる ・勝手に情報を補って断定しない | | | |
| 3  | (長文・複数の要件が混ざった問い合わせ文) | ・要件を漏れなく拾えている ・500字以内に収まっている | | | |
```

### ステップ2: バリアント比較(A/Bテスト)の進め方

プロンプトを直したら、旧版(バージョンA)と新版(バージョンB)の両方を、同じテストケース群に通して比較する。チャット画面だけで完結させる場合は、2つの会話タブでそれぞれのプロンプトを試し、出力を並べて記録する。比較を効率化したいときは、以下のように点数法プロンプティング([点数法(ルーブリック採点)プロンプティング](./rubric-scoring-prompting.md)を参照)と組み合わせて、AIに採点を手伝わせるとよい。

```
以下は、同じ入力に対する「プロンプトA」と「プロンプトB」それぞれの出力です。
下記のルーブリックで両方を採点し、どちらが優れているか、理由とともに判定してください。

【入力】
"""
[テストケースの入力文]
"""

【プロンプトAの出力】
"""
[出力A]
"""

【プロンプトBの出力】
"""
[出力B]
"""

【ルーブリック(各5点満点)】
- 正確性
- 指示された出力形式の遵守
- トーン([想定読者を記載])

表形式で採点し、末尾にどちらを採用すべきか一言で結論を書いてください。
```

複数のテストケースに対してこれを繰り返し、**Bが明確にAを上回るテストケースが多数派である場合のみ採用する**のが安全な運用。1件だけ良く見えて採用すると、他のケースで劣化していることに気づけない。

### ステップ3: モデルアップグレード時の再検証

利用中のツールでデフォルトモデルが切り替わった、あるいは自分でモデルを切り替えたときは、プロンプト文言を変えずにステップ1のテストケース群だけを再実行し、結果が変わっていないかを確認する。ここでプロンプトも同時に直してしまうと、「モデルのせいで変わったのか、プロンプトを直したせいで変わったのか」が分からなくなるため、**まずモデルだけを切り替えて確認し、必要ならその後で改めてプロンプトを調整する**という順番を守る。

### ステップ4: 軽量バージョン管理(個人・小規模チーム向け)

専用ツールを使わなくても、スプレッドシートやドキュメントに以下のような表を作るだけで十分な効果がある。

```
| バージョン | 更新日 | 変更点 | テスト結果の要約 | 採用可否 |
|-----------|--------|--------|-------------------|----------|
| v1 | 2026-06-01 | 初版 | テストケース8件中7件OK | 採用 |
| v2 | 2026-06-20 | 「敬語を崩さない」の指示を追加 | 8件中8件OK。v1でNGだったケース3が解消 | 採用 |
| v3 | 2026-07-05 | モデルを新バージョンに切替(プロンプト文言は変更なし) | 8件中8件OK。挙動に変化なしを確認 | 採用 |
```

Googleスプレッドシートであれば「ファイル→変更履歴」からも過去の状態を復元できるため、表による記録と組み合わせるとさらに安心できる([ChatGPT・Claude・Geminiのプロンプト管理 - GLASS BLOG](https://glass-inc.jp/media/ai-prompt-management-guide/))。

## 注意点・よくある誤解

- **テストケースを1〜2件で済ませない**: 1件だけ試して「うまくいった」と判断すると、たまたま相性の良い入力に当たっただけの可能性がある。典型パターン・エッジケース・過去の失敗例を組み合わせて最低でも5件前後は用意したい
- **モデルの切り替えとプロンプトの変更を同時に行わない**: 両方を同時に変えると、結果が変わった原因を切り分けられなくなる。「まずモデルだけ切り替えて確認」→「その後でプロンプトを調整」の順番を守る
- **判定基準は完全一致ではなく「満たすべき条件」で作る**: プロンプトの出力は毎回文言が変わるため、「一言一句同じか」ではなく「必須要素が入っているか」「NG表現がないか」といったチェックリスト形式にする
- **モデルは黙って新しくなることがある**: ChatGPT・Claude・Geminiのようなチャットツールはデフォルトモデルが定期的に更新される。プロンプトを変えていないのに出力の傾向が変わったと感じたら、まずモデルが変わっていないかを疑う
- **点数法(ルーブリック採点)との役割の違いを混同しない**: ルーブリック採点は「1回の出力をどう採点するか」という物差しであり、本ページのテスト運用は「その物差しを複数ケース・複数バージョンに繰り返し当てて追跡する仕組み」である。物差し(採点基準)を先に固め、それをテストのたびに使い回すと安定する
- **本格的なツールはいきなり導入しない**: promptfooやLangSmithは開発者向けの機能が中心で、非エンジニアがいきなり触るとハードルが高い。まずはスプレッドシート運用で慣れ、呼び出し頻度や重要度が上がってから専用ツールへの移行を検討するのが現実的な順序
