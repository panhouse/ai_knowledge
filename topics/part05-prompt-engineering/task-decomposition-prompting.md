# タスク分解プロンプティング(複雑な依頼をステップに分ける技法)

## これは何か

「この決算資料を読み込んで、要約して、課題を洗い出して、改善提案までまとめて」のように条件と工程が多い依頼を一度に投げると、AIが途中の工程を省略したり、前半の要約が雑なまま後半の提案に進んでしまい、結果として通しで読み直すとどこかの工程が薄い・抜けている、という失敗が起きやすい。タスク分解プロンプティングとは、こうした大きな依頼を「①要約→②課題抽出→③改善提案」のような小さな工程(サブタスク)に切り分け、1つずつ順番にAIへ処理させる技法のことだ。人間のマネジメントでいう「大きな仕事を工程表に分けて、1つずつ完了を確認しながら進める」のをAIへの指示に応用したものと考えるとわかりやすい。

## 仕組み・背景

大規模言語モデルは、1回の応答の中で扱える情報量と「注意力」に事実上の限界がある。依頼が長く工程数が多いほど、モデルは指示の一部を読み飛ばしたり、前の工程の出力精度が甘いまま後工程に引きずられたりしやすくなる。タスクを分解して1工程ずつ処理させると、モデルは毎回「今回のたった1つの仕事」だけに集中でき、各工程の出力を人間(またはAI自身)がその場でチェックできるため、誤りが後工程まで伝播する前に止められる。Anthropicはこれを「プロンプトチェイニング(prompt chaining、複数の呼び出しを連鎖させる設計)」と呼び、正確性を精度と引き換えに応答速度・手間を犠牲にする代わりに得るワークフローパターンの1つとして公式ドキュメントで解説している。研究面でも、2022年に発表された"Least-to-Most Prompting(最も易しい問題から順に解く手法)"という論文が、複雑な問題をまず小さなサブ問題に分解してから順番に解かせることで、GPT-3系モデルの構成的な推論課題(SCANベンチマーク)の正答率をChain-of-Thought単体の16%から99%以上まで引き上げたと報告しており、「分解してから解かせる」というアプローチの有効性を裏付けている。

### Chain-of-ThoughtやReActとの違い(粒度の違い)

タスク分解は、[Chain-of-Thought(CoT)プロンプティング](chain-of-thought-prompting.md)や[ReAct(Reasoning and Acting)プロンプティング](react-prompting.md)と混同されやすいが、「何を、どの粒度で分けるか」が根本的に異なる。

| 手法 | 分けるもの | 粒度 | 実行のされ方 |
|---|---|---|---|
| [CoT](chain-of-thought-prompting.md) | 頭の中の推論ステップ | 1回の応答**内**の思考の細かさ | モデルが1回の生成の中で自己完結して考える |
| [ReAct](react-prompting.md) | 推論と外部行動(検索・ツール呼び出し)のサイクル | 1つの調査タスクの中の反復 | モデルが自律的にThought→Action→Observationを繰り返す |
| タスク分解 | 依頼そのもの(工程・成果物) | **複数の依頼・複数ターン**にまたがる粗さ | 人間(または呼び出し側のプログラム)が工程を区切り、都度出力を確認しながら次を依頼する |

CoTは「1回の応答の中でどう考えさせるか」というミクロな技法であるのに対し、タスク分解は「そもそも依頼を何回・どの単位に分けて出すか」というマクロな設計の話である。実務では両者は排他的ではなく組み合わせて使う。たとえば「①要約」という1つの工程の中でも、要約の精度を上げたければその工程用のプロンプトにCoT(「まず段落ごとの要点を洗い出してから要約して」)を足せばよい。

### 自律型AIエージェントとタスク分解の関係(2026年8月時点)

2025年後半以降、主要ツールは「依頼を工程に分ける」作業自体をAI側が自動でやってくれる機能を相次いで搭載している。たとえばOpenAIは2026年7月にChatGPT Agentを改称した「ChatGPT Work」に「Plan mode(プランモード)」を実装した。`/plan`と入力するかメニューからPlanを選ぶと、ChatGPTが依頼をヒアリングしたうえで段階的な計画(ステップ一覧)を提示し、ユーザーはその計画を確認・修正してから承認して実行させられる。GoogleのGemini Deep Researchも「計画→複数ソースでの検索→反復→出力」という手順を自動生成し、実行前に人間が計画をレビュー・調整できる「collaborative planning(協調的な計画立案)」機能を備える。開発者向けには、Anthropicの[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/subagents)が、オーケストレーター役のAIが依頼をサブタスクに分解して専門化した「サブエージェント」に振り分け並列実行させる「orchestrator-workers」パターンを標準機能として提供している(これはAnthropicが"Building Effective Agents"で紹介する5つのワークフローパターン——プロンプトチェイニング・ルーティング・並列化・orchestrator-workers・evaluator-optimizer——の1つで、プロンプトチェイニング自体も「固定の工程に素直に分解できるタスク」に向くパターンとして現在も同ガイドで解説されている)。

つまり「タスクを工程に分ける」という発想は、チャット上で人間が手作業で書く技法から、エージェント機能が自動で提案し人間が承認する機能へと役割の一部が移りつつある。ただし、この技法自体が不要になったわけではない。

- **エージェントが提示する計画のレビューには、結局この技法と同じ判断力が要る**: ChatGPT WorkのPlan modeが計画を出しても、それを承認するかどうかを判断するには「この工程分けは妥当か、抜けている工程はないか」を見る目が必要で、それは本ページで説明している「工程を先に書き出せるか」という判断基準そのものである
- **日常のチャット利用では、依然として手動の分解が主流**: Plan modeやDeep Researchの自動計画機能は、長時間動く自律型タスクや調査タスクに向けた機能であり、日々の「資料を読んで要約して提案して」のような短めの依頼の大半は、本ページのパターン1・2のような手動の工程分けで対応するのが実務上一般的である

## 使いどころ・使い分け

すべての依頼を分解する必要はない。分解にはやり取りの往復・時間・(API利用時は)コストという明確なオーバーヘッドがあるため、タスクの複雑さと検証の必要性で判断する。

| タスクの性質 | 分解の要否 | 理由・具体例 |
|---|---|---|
| 単発の質問・簡単な言い換え・短文要約 | 不要 | 「この文をですます調にして」のような一発で完結する依頼を分解すると、往復が増えるだけで精度は変わらない |
| 複数の異なる種類の処理が連なる依頼 | 有効 | 要約→分析→提案、リサーチ→構成案→執筆、など「工程ごとに求められる能力・観点が違う」依頼 |
| 途中経過を人間がチェックしたい依頼 | 有効 | 契約書レビュー、経営会議資料、対外公開文書など、誤りがあると影響の大きい成果物 |
| インプットが長大で一度に読み切らせると精度が落ちる依頼 | 有効 | 数十ページの議事録・長編レポートを扱う場合、章ごと・セクションごとに区切って処理させる |
| 定型的な繰り返し作業を大量にこなす依頼 | 状況次第 | 同じ形式の処理を大量件数こなす場合は、1件ずつ分解するより「フォーマットを固定して一括処理」の方が効率的なこともある |
| 探索的な調査で次に何を調べるべきかその都度変わる依頼 | ReActが向く | 分解は「工程があらかじめ決まっている」場合に強く、探索の分岐が読めない調査はReAct的なループの方が適している |

判断の目安は「工程を先に書き出せるか」。書き出せるなら分解して各工程を1回ずつ依頼し、書き出せない(次に何をすべきかがその場の結果次第で変わる)ならReAct、単に答えの精度が足りないだけならCoT、という切り分けが実務上わかりやすい。

## 実務での使い方

### パターン1: 1メッセージ内でステップを明示する(往復を減らしたい場合)

同じチャット内で完結させたいが、工程だけは明示してAIに「一気に飛ばさせない」ようにする方法。長文レポートの整理などでよく使う型。

```
以下の資料をもとに、次の3ステップの順番で作業してください。
各ステップの見出しを付け、ステップ1を終えてからステップ2に進んでください。

ステップ1(要約): 資料全体を、章立てを保ったまま800字程度で要約する
ステップ2(課題抽出): ステップ1の要約をもとに、事業上の課題を箇条書きで
   最大5つ、根拠となる記述を添えて挙げる
ステップ3(改善提案): ステップ2の課題それぞれについて、実行可能な
   改善アクションを1つずつ提案する

【資料】
[ここに資料本文を貼る]
```

このパターンは往復が1回で済む反面、モデルが3ステップの品質を均等に保証してくれるとは限らない(特に長い資料では後半のステップが手薄になりやすい)ため、重要な資料では次の「パターン2」の方が安全度が高い。

### パターン2: 複数ターンに分けて段階的に依頼する(各工程を検証したい場合)

1ターン1工程にして、前の工程の出力を人間が確認してから次を依頼する方法。誤りの連鎖を最も防ぎやすく、重要な成果物ではこちらを基本形にするとよい。

```
[ターン1]
以下の資料を、章立てを保ったまま800字程度で要約してください。

【資料】
[ここに資料本文を貼る]

# → 出力された要約を人間が確認・手直ししてから、次のターンに進む

[ターン2]
先ほどの要約をもとに、事業上の課題を箇条書きで最大5つ、
根拠となる記述を添えて挙げてください。

[ターン3]
先ほど挙げた課題それぞれについて、実行可能な改善アクションを
1つずつ提案してください。優先度が高いものから並べてください。
```

チャット形式のツール(ChatGPT・Claude・Gemini)ではそのまま会話を続けるだけでよく、前の工程の出力が自動的に文脈として引き継がれる。API経由で組む場合は、前の呼び出しの出力を次の呼び出しの入力に自分で渡す必要がある(Anthropicはこれを「プロンプトチェイニング」と呼ぶ)。

### パターン3: ノーコードツールでノードとして分解する(繰り返し使う業務フローの場合)

同じ工程を何度も繰り返す業務(週次レポート作成、問い合わせ対応の一次仕分けなど)は、チャットで毎回手作業するより、[Difyワークフローの基本](../part10-nocode-lowcode/dify-workflow-basics.md)や[n8nの基本](../part10-nocode-lowcode/n8n-basics.md)のようなワークフローツールで「1工程=1ノード」として組んでしまうと、タスク分解を自動化・再利用できる。

- **Dify**: 「LLM」ノードを工程の数だけ並べ、前段ノードの出力変数を次のノードのプロンプトに変数として渡す。要約用・課題抽出用・提案用でそれぞれ別のLLMノードにすると、工程ごとにモデルやプロンプトを最適化できる(軽い要約は安価なモデル、提案は高精度なモデル、という使い分けも可能)
- **n8n**: 単体の「OpenAI」「Anthropic Chat Model」ノードを工程数だけつなぎ、前ノードの出力を`{{ $('要約').item.json.text }}`のような式で次ノードのプロンプトに埋め込む。Gmail・Slackなど他システムとの連携ノードを工程の間に挟めるのが強み
- 両ツールとも、各ノードの実行結果をキャンバス上で個別に確認できるため、「どの工程で出力がおかしくなったか」を1メッセージのプロンプトより特定しやすい

### ツール横断の対応付け

| 目的 | チャット形式(ChatGPT/Claude/Gemini) | ノーコードツール |
|---|---|---|
| 1回のやり取りで工程を明示 | メッセージ内に「ステップ1/2/3」を書く | 該当なし(そもそも1メッセージという概念がない) |
| 工程ごとに人間が確認しながら進める | 会話を続けて段階的に依頼する | 各ノードの実行結果をキャンバス上で確認 |
| 繰り返し使う業務として自動化する | 定型文をテンプレート保存(カスタムGPT・Gem・Copilotのプロンプトライブラリ等) | Dify「LLM」ノード、n8n「AIノード」を工程数だけ連結 |
| AIが自動生成した工程分けをレビューする(2026年時点の新しい形) | ChatGPT Workの「Plan mode」(`/plan`)、Gemini Deep Researchの計画レビュー機能で、実行前に計画を確認・修正 | 該当なし(開発者はAnthropicの[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/subagents)のサブエージェント・orchestrator-workersパターンで同種の分解を組める) |

## 注意点・よくある誤解

- **分解しすぎるとコストと手間が増える**: 工程を細かく刻むほどAPI呼び出し回数(コスト)とやり取りの往復(人間の手間・待ち時間)が増える。「その工程を分けないと精度や検証性が上がるか」を基準にし、分けても効果が薄い工程はまとめる
- **各ステップの出力を人間がチェックしないと誤りが連鎖する**: 分解の最大の利点は「途中で止めて確認できること」だが、確認を省略して全工程を機械的に流すだけなら、1メッセージで一気に依頼した場合と誤りの伝播リスクは大差なくなる。特に重要な成果物では、最低でも要となる工程(パターン2でいう最初の要約など)の出力は目を通してから次に進む
- **CoTと混同しない**: 「ステップバイステップで考えて」という指示はCoT(1回の応答内の思考の分解)であり、タスク分解(依頼そのものを複数回に分ける)とは別物。両者は併用できるが、「CoTを書いたから分解した」と思い込まないよう区別する
- **分解の粒度が業務ロジックとずれていると効果が出ない**: 「要約」と「課題抽出」のように、求められる観点や必要な情報が明確に異なる単位で切ると効果が出やすい。中途半端な切り方(例: 「前半の要約」「後半の要約」のように内容的に不可分なものを機械的に割る)は、かえって文脈の分断で精度が落ちることがある
- **長い資料は分解した上で「章ごと」に区切ることも検討する**: 資料が長大でモデルの入力上限やコンテキストウィンドウ(モデルが一度に読める情報量)に近い場合、工程を分けるだけでなく入力側も章・セクション単位に分割して渡すと、読み飛ばしのリスクをさらに減らせる
- **自律型エージェントが自動で分解した計画も、実行前レビューを省略しない**: ChatGPT WorkのPlan modeのように、エージェント側が計画を自動生成して長時間(数時間単位)無人で実行するツールが増えているが、これは「分解の手間が減る」だけであり「分解結果の検証が不要になる」わけではない。承認前に工程の抜け・順序のおかしさを確認する習慣は、手動で分解する場合と同様に重要

## 最初の一歩

次に複数の作業が絡む依頼をAIに出すとき、1つのメッセージに全部詰め込まず、「①要約→②課題抽出→③改善提案」のように工程を書き出してから、まずは①だけを依頼し、出力を確認してから②に進んでみるとよい。
