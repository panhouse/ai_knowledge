# 点数法(ルーブリック採点)プロンプティング

## これは何か

「もっと良くして」とAIに頼んでも、返ってくる出力は微妙に変わるだけで、何がどう良くなったのか分からない——という経験は多いはずだ。原因は、指示があいまいで「良い出力」の基準がAI側にも人間側にも共有されていないことにある。点数法(ルーブリック採点プロンプティング)とは、「正確性」「簡潔さ」「トーン」といった評価観点を洗い出し、それぞれを5点満点などの基準(ルーブリック、評価観点と点数の対応表)として明文化した上で、AI自身にその基準で自己採点・改善させたり、複数の案を採点して比較・選択させたりする技法である。感覚的な「もっと良くして」を、「トーンが3点なので4点にするには何を直すべきか」という具体的な改善指示に変換できるのが最大の利点になる。

## 仕組み・背景

この技法は学術的には「LLM-as-a-judge(LLMを審査員として使う手法)」と呼ばれる評価手法の応用にあたる。LLM-as-a-judgeは、人手による品質評価はコストと時間がかかりすぎるという課題を背景に、「別のLLM(または同じLLM)に、あらかじめ定めた基準で出力を採点・比較させる」ことで評価を自動化する考え方であり、2023年のG-Eval論文([arXiv:2303.16634](https://arxiv.org/abs/2303.16634))などの研究で「評価観点をChain-of-Thought(思考の連鎖。結論だけでなく途中の思考過程を書き出させる手法)で段階的に評価させると、人間の評価との相関が高まる」ことが示されている。点数法プロンプティングは、この「LLMに採点させる」発想を、開発者向けの評価パイプラインではなく、日々のチャットや業務プロンプトの中に軽量に取り込んだものと理解するとよい。

なぜ数値化すると精度が上がりやすいのか。理由は主に2つある。

1. **評価観点が分解されることで、指摘が具体化する**: 「文章が微妙」という漠然とした不満は、「正確性4点・簡潔さ2点・トーン3点」のように分解されると、「簡潔さが低いから冗長な部分を削る」という次のアクションに直結する。研究上も、1つの評価者に1つの基準だけを見させる「基準の分解(criteria decomposition)」が、複数観点を一度に判断させるより精度が上がりやすいとされる
2. **「点数を付ける」という行為自体が、AIに基準への注意を強制する**: 採点というタスク形式にすることで、AIは各観点を個別にチェックする思考の流れ(スコア算出のための一種のCoT)を踏みやすくなり、単に「良い/悪い」を判定させるより一貫性のある評価になりやすい

一方で、点数法には評価者(採点するAI)固有の癖(バイアス)があることも研究で指摘されている。詳細は後述の「注意点」を参照。

## 使いどころ・使い分け

点数法は「品質のばらつきを抑えたい」場面で効果を発揮する一方、答えが1つに定まらない発散的なタスクには不向きなことがある。

| 状況 | 点数法の向き不向き | 理由 |
|---|---|---|
| 定型業務のメール文面・議事録要約・FAQ回答 | 向いている | 「正確性・簡潔さ・トーン」など基準が明確に定義しやすく、基準通りに仕上がっているかの検証にAI自身を使いやすい |
| 広告キャッチコピー・タイトル案の選定 | 向いている(比較採点として) | 複数案を同じ基準で横並び採点させることで、選定理由を言語化しながら絞り込める |
| 社内向けのプロンプト・テンプレートの品質チェック | 向いている | 毎回人手でレビューする代わりに、ルーブリックに沿った自己採点をワークフローに組み込んで最低品質を担保できる |
| ゼロから発想を広げたいブレインストーミング・アイデア出しの初期段階 | 不向き | 点数法は「基準に沿っているか」を絞り込む収束的な思考であり、基準に寄せる圧力がかえって発想の幅を狭める。まず基準なしで数多く出させ、絞り込みの段階で点数法を使うのが良い順番 |
| 唯一の正解がない創作(小説の展開、デザインの方向性など) | 慎重に | 定量化しにくい「面白さ」「独創性」を無理に5点満点にすると、基準が形骸化し、かえって無難な出力に収束しやすい |
| 事実確認が必要な内容(数値・法令・固有名詞) | 部分的に有効、過信は禁物 | 「事実と整合しているか」を観点に含めることはできるが、AI自身の知識の誤りは自己採点でも見抜けないことが多い(いわゆるハルシネーション、AIが事実に基づかない内容をもっともらしく生成する現象) |

判断の目安は「基準を具体的な言葉で書き下せるか」「収束(絞り込み)フェーズか発散(発想)フェーズか」の2点である。基準が書けないタスクや、発散が目的のタスクには点数法を使わない。

## 実務での使い方

### コピペで使える実例(1): 自己採点・改善ループ

自分(または他部署)が書いた文章の見直しに使う。ルーブリックの観点は業務に応じて差し替える。

```
以下のルーブリックで、あなた自身が今書いた回答を5点満点で自己採点してください。
4点未満の項目があれば、その理由と具体的な改善案を挙げた上で、
改善版の全文を出力してください。

【ルーブリック】
- 正確性(事実・数値に誤りや飛躍がないか): 5点満点
- 簡潔さ(冗長な表現がなく、要点が絞られているか): 5点満点
- トーン(想定読者に対して丁寧さ・親しみやすさのバランスが取れているか): 5点満点
- 網羅性(依頼内容の抜け漏れがないか): 5点満点

【出力形式】
1. 各観点の点数と、その点数を付けた理由(1行ずつ)
2. 4点未満の項目がある場合: 改善案の要約
3. 改善版の全文
```

### コピペで使える実例(2): 複数案を比較採点させる

キャッチコピーや件名など、複数の候補から選びたいときに使う。

```
以下の3案について、下記のルーブリックで採点表を作成し、
最も点数の高い案を1つ選んで推奨してください。
同点の場合は、その判断理由も述べてください。

【案】
A) [候補1]
B) [候補2]
C) [候補3]

【ルーブリック(各5点満点)】
- インパクト(目に留まりやすいか)
- 分かりやすさ(一読して意味が伝わるか)
- ブランドトーンとの整合性([自社らしさの説明を書く])

【出力形式】
表形式(案 × 観点 × 点数)で採点し、合計点と推奨案、推奨理由を末尾に書いてください。
```

### コピペで使える実例(3): 採点基準そのものをAIに作らせる

何を評価観点にすべきか自分でも整理できていない場合、基準づくりから任せることもできる。

```
[書きたい文章の種類、例: 社外向け謝罪メール]を評価するための
ルーブリックを作成してください。評価観点は4〜5個、各観点は5点満点とし、
1点・3点・5点それぞれに該当する状態を具体的に説明してください。
```

### ツール横断の対応付け(2026年7月時点)

| 用途 | 実装イメージ |
|---|---|
| ChatGPT / Claude / Gemini(チャット画面) | 上記コピペ例をそのままプロンプトに含めて1回のやり取りで完結させる。カスタム指示・GPTs/Gemの指示欄にルーブリックを常設し、「回答の最後に必ず自己採点を付ける」ルールにしておく運用も可能 |
| Dify(ワークフロー) | 「LLMノードで下書き生成 → 別のLLMノードでルーブリックに沿って点数(JSON形式など)を出力 → 条件分岐(IF/ELSE)ノードで『合計点が基準未満なら差し戻し・再生成』を実装」という3〜4ノード構成にすると、人手を介さない品質ゲートを自動化できる。ノードの詳細は[Difyワークフローの主要ノードと組み立て方](../part10-nocode-lowcode/dify-workflow-nodes.md)を参照 |
| n8n / Make | 同様に「AIノードで生成→別のAIノードで採点→IF/Routerで分岐」という構成で組める。[n8nの基本](../part10-nocode-lowcode/n8n-basics.md)のAI Agentノードや単体LLMノードを2段構成にすることで実現できる |
| 社内のプロンプト品質チェック | 新しく作ったテンプレート・システムプロンプトを配布する前に、想定される入力パターンをいくつか用意し、点数法プロンプトで自己採点させておくと、リリース前の簡易的な品質チェックとして使える(ただし後述の通り、人間のレビューを完全に代替するものではない) |

## 注意点・よくある誤解

- **AIの自己採点は甘くなりがちである(自己評価バイアス)**: 研究では、LLMを審査員として使う際、評価対象が自分自身(または同じモデルファミリー)の出力だと、客観的に誤っている項目でも「満たしている」と誤判定する確率が最大50%高まったという報告がある([Self-Preference Bias in Rubric-Based Evaluation of LLMs](https://arxiv.org/pdf/2604.06996))。自己採点だけで完結させず、可能であれば「生成に使ったのとは別のモデル(別ベンダーのAI)に採点させる」「人間が最終チェックする」を組み合わせるとよい
- **採点基準自体が曖昧だと意味がない**: 「良い文章か: 5点満点」のような抽象的な基準では、AIも人間も何を根拠に点数を付けたか説明できず、点数が安定しない。上記コピペ例(3)のように「1点・3点・5点に該当する具体的な状態」まで書き下ろすと、採点のブレが小さくなる
- **点数の絶対値より、点数の内訳と理由を重視する**: 「4.2点」という数字自体に意味を持たせすぎず、「どの観点が低いか」「なぜその点数か」という説明部分を改善のヒントとして使う方が実務的に役立つ
- **ルーブリック修正の無限ループに注意**: AI自身に「採点基準そのものも見直して」と繰り返させると、かえって基準がぶれて評価の一貫性が落ちるという研究報告もある。基準は人間が一度固めたら、よほどの理由がない限り途中で変えない方が安定する
- **点数化になじまないタスクに無理に使わない**: 独創性や面白さのような定性的な価値を無理に数値化すると、基準に寄せようとして無難な出力に収束しやすい(発散的なタスクとの相性の悪さは前述の通り)
- **事実の誤り(ハルシネーション)は自己採点で検出しにくい**: 「正確性」を観点に入れても、AI自身がその誤りに気づいていなければ高得点を付けてしまう。数値・固有名詞など重要な事実は、点数法とは別に人間またはWeb検索等での裏取りを行う

## 最初の一歩

直近でAIに書かせたメール文面や要約を1つ選び、上のコピペ例(1)の自己採点プロンプトに貼り付けて、実際にAIがどの観点を何点にし、どこを改善したかを確認してみる。
